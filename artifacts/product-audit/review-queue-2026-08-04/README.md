# 审核队列数量与重复提案验收

## P0 / P1 / P2

- P1，已修复：`PENDING_REVIEW` API 曾返回 92 条记录，其中 61 条已经超过 `expires_at`，导致 API、首页与审核页可能出现不一致。现在读取时统一投影有效状态；待审核查询只返回尚未到期记录，到期记录在全部提案和详情中显示为 `EXPIRED`。
- P1，已验证：历史数据库存在同标的重复提案，但当前有效 SYSTEM 提案按环境、账户、交易所、精确合约、方向和策略分组的重复数为 0。自动提案仍使用事务锁、活动作用域去重和来源候选幂等；本批未删除历史审计记录。
- P1，已修复：两名创建者提交完全相同的环境、账户、精确合约、方向和冻结交易参数时，过去会各自产生一条人工待审核提案。现在使用共享事务锁复用同一活动提案；不同环境或不同冻结参数仍保持独立。启动时对既有完全重复记录保留最早或已有审核的一条，其余只标记为 `EXPIRED` 并写 `PROPOSAL_DUPLICATE_EXPIRED` 审计，不删除历史。
- P2，已修复：审核队列按最早到期排序；统计改为“待我审核 / 需两人审核 / 30 分钟内到期 / 最早到期”，避免把“全部高风险”当成无法解释的告警。
- P2，已修复：全部提案增加状态筛选；历史到期记录可明确筛选，不再伪装为仍待审核。
- P2，已验证：当前管理员默认配置 v4 明确将风险档位设为 `HIGH`、有效期 8 小时、自动提案阈值 4 周期，因此有效自动提案大多需要两名审核人，这是当前生效配置，不是前端误算。本批没有擅自改变风险策略。
- P2，已验证：独立审核人桌面页面从 34 条降为 33 条，人工判断从 2 条降为 1 条；390×844 手机视口显示同一权威数量、筛选和审核进度，导航收敛为菜单按钮。

## 五维证据

- 代码：统一提案有效状态投影；审核页优先级、说明、统计和状态筛选完成。
- API：修复后 `proposal_status=PENDING_REVIEW` 返回的记录均为 `PENDING_REVIEW`，按时钟已到期为 0；`proposal_status=EXPIRED` 均投影为 `EXPIRED`。
- 实际页面：`01-review-desktop.png` 显示有效审核队列及最早到期；`02-expired-filter.png` 显示全部提案的已过期筛选。
- 端到端：系统管理员、普通创建者、独立审核人、资金成员、只读成员、禁用成员均在实际页面切换验证。创建者直达 `/reviews` 显示权限阻断，禁用成员登录被拒绝；本次以纯独立审核人复现并验证跨创建者重复收敛。
- 测试：提案核心/页面回归覆盖；跨创建者并发复用、既有重复审计收敛、API 不重复通知和六身份后端权限均有独立测试。
