## 1. 目的

本文件规定：哪份材料回答哪类问题、发生冲突时怎样裁决、什么状态的文档可以进入实现，以及旧 Notion、原型代码和研究附件如何引用。

它不改变 [交易系统总体方案](../../交易系统总体方案.md) 中已经固定的系统原则，也不代替 [待确认决策清单](待确认决策清单.md) 中的决策状态。本文只治理文档，不签发交易、资金、生产发布或现实执行权限。

## 2. 治理原则

1. **一个问题只有一个状态真源。** 所有需要用户判断的事项，以 [待确认决策清单](待确认决策清单.md) 的 ID、状态和结论为唯一状态真源；其他文档只能引用 ID，不能自行把 `OPEN` 写成已定。
2. **一个术语只有一个规范定义。** 跨域术语以 [术语表](术语表.md) 为规范入口；专项合同可以增加字段和算法，但不能另造同名不同义。
3. **系统原则高于局部便利。** Risk Engine 最高否决、唯一订单出口、有限授权、未知禁止增险、Vault 不救仓等原则不能被产品、接口、执行器或运维文档覆盖。
4. **范围内的已批准专项合同优于宽泛示例。** 在不违反上位原则的前提下，已批准的 Binance、Hyperliquid、风险、资金、API 或状态机专项文档，对其明确作用域拥有更精确的解释权。
5. **状态先于标题。** 文件名包含“最新”“新版”或“开发需求”不代表有效；没有有效状态、owner、版本和适用范围的文件按 `REFERENCE` 或 `DRAFT` 处理。
6. **默认拒绝推断。** 文档没有定义的风险放宽、订单重试、资金划转、权限或故障恢复行为不得由实现团队自行补全；先登记决策或 ADR。
7. **历史材料只提供证据线索。** 旧 Notion、DynamicPositionSizing、low_vol_breakout_bn 和 Excel 不能直接成为生产事实、运行配置或验收结论。
8. **完整交付与能力激活分离。** 产品目标一次完整定义和工程交付，不以试制子集、场所先后或“先做一部分”拆成功能版本；真实权限仍须按认证单位完成策略、执行、风险和审核证据后独立激活。
9. **如无必要勿增实体。** 新文档、服务、领域实体或状态机必须具有不能由现有对象表达的独立权威边界、生命周期、安全边界或规模需求；派生展示、纯规则模块、流程步骤和证据环境不构成新增理由。
10. **视觉合同只有一个真源。** 深色/浅色主题、视觉语义、响应式和可访问性交互统一由 `docs/01-product/用户旅程与交互规格.md` 管理，其他文档只引用，不另建视觉规范或 UI 状态机。
11. **不预建假设能力。** 当前系统不预建独立自动代理、服务、接口、权限、数据实体或验收指标；任何辅助建议源只作为无密钥、无签名、无下单权、无资金权、无风控覆盖权的非权威输入，并须另行变更批准。

## 3. 权威层级

发生语义冲突时按以下顺序处理；高层只能被正式新版本替代，不能被下层隐式改写。

| 层级 | 内容 | 权威范围 |
| ---: | --- | --- |
| L0 | `交易系统总体方案.md` 中不可被绕过的系统原则 | 系统宪法、职责边界、风险与安全底线 |
| L1 | `待确认决策清单.md` | 决策 ID、状态、用户确认结论和安全默认的唯一状态真源；不自动替代 L0 |
| L2 | 已人工批准并生效的风险政策、资金政策、参数登记、执行附件、能力证书和 ADR | 仅对其冻结版本、账户、场所、策略和作用域有效，且不得违反 L0 |
| L3 | `策略合同与数值化验收门.md` | 主策略研究、认证、验收和能力激活基线 |
| L4 | 本套件中状态为 `APPROVED` 的产品、领域、合同、执行、安全、质量和运营专项文档 | 对其负责领域提供详细实现合同；不得改变 L0-L3 已定边界 |
| L5 | 状态为 `DRAFT` 或 `RESEARCH` 的专项文档 | 设计输入；空项和候选值不得进入生产 |
| L6 | 旧 Notion、原型、README、Excel、示例和外部说明 | `REFERENCE`；只作研究与迁移线索 |

补充规则：

- L1 的 `CONFIRMED` 只表示该决策已经获得确认。需要写入风险政策、专项合同或参数登记才能运行的内容，仍须完成对应 L2/L4 文档、审批和验证。
- 同一层级内冲突时，先比较作用域是否重叠；更具体且已批准的专项文档在其作用域内优先。若仍冲突，全部相关实现停止，新增一条 `DEC-GOV-*` 或 ADR 解决，不能按日期、提交时间或开发便利自行选择。
- 安全收紧可以按已批准紧急政策立即生效；风险放宽、资金权限、身份扩权和执行范围扩大必须先完成正式批准和对应重验。

## 4. 文档状态与效力

| 状态 | 定义 | 允许用途 | 禁止用途 |
| --- | --- | --- | --- |
| `BASELINE` | 当前治理或上位方案基线 | 指导拆分、评审和下位文档 | 不能单独签发实盘能力 |
| `APPROVED` | owner、批准人、版本和适用范围完整，已按流程批准 | 作为实现与验收输入 | 超出作用域复用；绕过能力认证 |

| `RESEARCH` | 数值或方法需要预登记实验决定 | 回测、历史重放、影子计算 | 作为隐式生产默认值 |
| `REFERENCE` | 历史、原型、示例或外部材料 | 提炼思想、识别失败、追溯来源 | 作为接口、风险、权限或执行真源 |

## 7. 冲突处理流程

1. 发现者记录冲突的文件、章节、版本、适用范围和可能安全影响。
2. 在冲突范围内立即采用更保守行为：不扩大风险、不自动划转、不恢复权限；已有保护、减仓和退出继续。
3. 检查 [待确认决策清单](待确认决策清单.md) 是否已有 ID：
   - 有 ID：不得新建重复问题；更新引用和影响，等待或执行该 ID 的状态。
   - 无 ID 且属于用户/业务判断：按领域新增 `DEC-*`。
   - 无 ID 且属于可由工程团队决定的技术取舍：新增 ADR，并说明为何不改变业务边界。
4. 完成批准后，先更新决策清单或 ADR，再更新受影响专项文档、测试和追踪矩阵。
5. 已发布配置或证书受影响时，按变更影响使其失效、降级或重新认证；不能只改文字。

## 8. 文档变更规则

每份可作为实现输入的文档至少包含：

- 文档 ID 或唯一文件路径；
- 版本、状态和状态日期；
- owner 与批准人；
- 适用范围和明确不适用范围；
- 上位文档与引用的决策 ID；
- 未决项和安全默认；
- 变更历史；
- 影响的测试、部署、参数、证书和存量仓位处理。

新增文档前还必须证明现有权威文件无法承载该内容，并在本矩阵登记其唯一负责问题和明确不负责范围。新增服务或领域实体同样必须先证明其独立生命周期、安全/故障边界或不可合并的事实所有权；仅为团队分工、页面布局、计算函数或将来的可能性不得新增。

变更影响分级：

| 变更 | 最低后果 |
| --- | --- |
| 文字澄清且不改变语义 | 文档版本增加，完成一致性检查 |
| 产品流程、接口或数据结构改变 | 更新 PRD/合同/追踪矩阵，完成兼容与回归评审 |
| 策略、风险、资金、权限或执行语义收紧 | 可按批准政策立即生效，并更新存量行为与审计 |
| 策略、风险、资金、权限或执行语义放宽 | 用户/负责人批准、重新验证、重新认证，不能热更新绕过 |
| 上位系统原则改变 | 新总体方案版本，审计全部下位文档与证书 |
