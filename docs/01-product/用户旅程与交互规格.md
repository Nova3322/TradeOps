## 1. 文档目的与使用方式

本文定义用户从“看到机会”到“完成审核、执行、管理仓位、处理异常和复盘”的产品旅程，并把每条旅程拆成页面状态、用户动作、系统回执和失败路径，作为产品设计、前端、后端和端到端测试的共同输入。

本文描述产品可见行为，不替代领域状态机、API、事件、风险或执行合同。状态名称在领域合同冻结前属于产品语义；研发应保留稳定业务 ID，不得直接把临时页面枚举当成最终领域状态。

规则：

- 已冻结决策直接作为交互合同；研究参数和外部事实只控制对应真实能力是否激活，不再产生平行 UI 选项。
- 页面不得假设请求发送成功等于业务完成。
- 页面、PWA 和 Telegram 必须以 Trading 服务端返回的权威对象版本与终态为准。
- 任一流程出现未知状态时，默认禁止继续扩大风险，并给出对账或保护路径。

## 2. 全局交互不变量

### 2.1 状态与事实

`UX-GLOBAL-001` 每个关键对象必须展示：

- 对象 ID 和版本。
- 当前状态及状态发生时间。
- 事实来源与最后更新时间。
- 当前用户是否具有下一动作权限。
- 下一允许动作、禁止动作和原因。
- 若处于处理中或未知状态，显示明确的等待、刷新、对账或人工处置路径。

`UX-GLOBAL-002` 以下状态不得混用：

1. 用户已点击或提交。
2. Trading 已受理意图。
3. 权限与 Risk Engine 已允许。
4. 订单已发送。
5. 交易所已接受。
6. 已部分成交或全部成交。
7. 原生保护已确认。
8. Trading 已完成对账。

`UX-GLOBAL-003` 所有增险操作必须展示对应提案版本、授权有效期和 Risk Engine 决定；所有减险操作必须展示作用域、目标和真实结果。

`UX-GLOBAL-004` 重复点击、双端同时操作、浏览器重试和 Telegram 延迟按钮都必须返回同一业务对象的权威结果，不得生成无法解释的第二个增险动作。审核并发必须分离 Reviewer vote 与汇总终态；禁止自审，低、中风险需要 1 名独立 Reviewer，高风险需要 2 名独立 Reviewer。

### 2.2 全局风险横幅

所有主页面顶部必须展示当前系统风险状态；移动端不得隐藏。

| 风险状态 | 用户可见含义 | 新开仓 | 自动加仓 | 减仓/退出 | 恢复 |
| --- | --- | --- | --- | --- | --- |
| `NORMAL` | 数据、风险与执行处于允许范围 | 仍需逐笔审核与风控 | 仅消费有效预授权 | 允许 | 不适用 |
| `NO_PYRAMID` | 禁止继续加仓 | 依其他预算决定 | 禁止 | 允许 | 不自动恢复 |
| `NO_NEW_POSITION` | 禁止新开仓和加仓 | 禁止 | 禁止 | 允许 | 需按恢复政策处理 |
| `REDUCE_ONLY` | 系统只允许降低风险 | 禁止 | 禁止 | 允许 | 引用 `DEC-SEC-003` / `DEC-GOV-001` |
| `KILL_SWITCH` | 严重事件，优先退出与人工接管 | 禁止 | 禁止 | 按保护合同执行 | 引用 `DEC-SEC-003` / `DEC-GOV-001` |
| `UNKNOWN` | 关键事实无法确认 | 禁止 | 禁止 | 仅经允许的保护路径 | 先对账，不可猜测 |

每个横幅必须显示触发原因、影响范围、触发时间、已采取动作、责任人和详情入口，不能只显示颜色。

### 2.3 页面数据状态

每个页面或组件至少支持：

| 状态 | 必须表现 |
| --- | --- |
| Loading | 显示正在加载的具体对象，不用旧值伪装新值 |
| Empty | 说明确实没有数据，并提供符合权限的下一步 |
| Stale | 显示最后更新时间、陈旧原因，禁用受影响增险动作 |
| Partial | 标出缺失来源和受影响功能，不用聚合总数掩盖 |
| Unknown | 显示对账中或无法确认，禁止给出成功/失败猜测 |
| Forbidden | 说明缺少的动作权限或作用域，不泄露无权信息 |
| Failed | 显示稳定原因代码、可恢复动作和关联异常 ID |
| Offline | PWA 全局只读；仅展示短 TTL、带时间戳、加密且可远程撤销的非敏感摘要 |

## 3. 信息架构与导航域

Perptape 与 Trading Console 按已确认的 `DEC-PROD-003` 保持独立故障域，以统一身份、版本化 API 和深链协作。Trading 只保留七个一级导航域；新建、审核、详情和确认都是域内流程，不再建成平行一级页面实体：

| 导航域 | 包含的流程 / 子视图 | 主要动作 |
| --- | --- | --- |
| 总览 | 风险状态、权益、Heat、服务健康、待办与异常 | 查看详情、进入待办 |
| 机会与提案 | Perptape 候选、SYSTEM 提案、MANUAL 草稿、风险预检、审核详情 | 筛选、创建、提交、批准、拒绝、退回新版本 |
| 仓位与订单 | Campaign、保护、Add、OrderIntent、场所订单、成交、PnL、退出 | 关闭加仓、收紧风险、查看对账；不旁路下单 |
| 风险与异常 | 限额、风险状态、拒绝原因、事故、自动降级、恢复证据 | 暂停、减险、申请恢复、处置异常 |
| 资金 | Vault、场所运营资金、Funding Envelope、在途和 CapitalTransfer | 发起、复核和跟踪资金授权 |
| 审计 | 提案到结算、身份、风险、订单、资金和事故时间线 | 搜索、关联查看、按政策导出 |
| 设置与权限 | 用户标签、作用域、MFA、设备、会话、能力开关、集成和通知 | 授予、撤销、冻结、进入专项变更流程 |

页面可见范围由[身份权限与审批矩阵](身份权限与审批矩阵.md)约束。Observer 按作用域查看脱敏信息，默认隐藏密钥、完整地址、个人身份、完整资金金额和敏感审计字段。

## 4. UI 视觉、主题与可访问性合同

本节是唯一表现层合同，不新增业务状态、业务对象或独立 UI 状态机。界面直接读取 [领域模型与状态机](../02-domain/领域模型与状态机.md) 的权威对象状态，并只派生“可编辑、可审核、可执行、处理中、未知”等显示属性。退回必须创建新冻结版本；并发 Reviewer vote 由服务端产生唯一 ApprovalDecision，UI 不另写规则。

### 4.1 视觉来源与适配原则

- 视觉方向以 2026-07-17 核对的 [thedankoe.com 首页](https://thedankoe.com/) 为来源：黑白主导、Poppins、重字重标题、宽字距英文小标签、大留白、极少边框和装饰。
- 核对时参考页为纯黑背景，正文近白，正文使用 Poppins `18/27`，主标题约 `52/62`、`900` 字重和轻微负字距。本系统保存这些特征，不复制其 logo、图像、文字或品牌资产。
- 参考站是内容页，Trading 是高密度工作台：页面分区保持宽松留白，表格、风险摘要、订单与仓位数据内部保持紧凑；不另设“密度模式”。
- 风险辨识、事实新鲜度、操作防错和可访问性高于视觉相似度。除风险语义外不使用装饰性彩色渐变、玻璃效果或大面积阴影。

### 4.2 语义设计令牌

字体：

- 拉丁字母和数字：`Poppins`；中文：`PingFang SC, Noto Sans SC, system-ui, sans-serif`；金额、价格、数量和时间启用 `tabular-nums`。
- Display：桌面 `52/62, 900, -0.02em`；手机 `36/42, 900, -0.015em`。
- 页面标题 `32/40, 800`；分区标题 `20/28, 700`；正文 `15/24, 400–500`；数据与表格 `13/20, 500`。
- 英文眉题/小标签 `11/16, 600, uppercase, 0.14em`；中文不强制大写或扩展字距。

颜色只允许使用语义名称，页面不得私自硬编码：

| Token | 深色 | 浅色 | 用途 |
| --- | --- | --- | --- |
| `canvas` | `#000000` | `#FFFFFF` | 页面背景 |
| `surface` | `#0A0A0A` | `#F7F7F5` | 分区和表格背景 |
| `surface-raised` | `#141414` | `#FFFFFF` | 浮层、菜单、确认框 |
| `text-primary` | `#EFEFEF` | `#111111` | 主文字 |
| `text-secondary` | `#B8B8B8` | `#606060` | 辅助文字 |
| `border-subtle` | `#2A2A2A` | `#DEDEDE` | 必要分隔线 |
| `positive` | `#5FD18B` | `#0B7A3D` | 正向事实；不等同于可增险 |
| `warning` | `#F4C95D` | `#8A5A00` | 警告 |
| `danger` | `#FF7B7B` | `#B42318` | 危险、拒绝、KILL_SWITCH |
| `information` | `#80BFFF` | `#175CD3` | 信息和处理中 |
| `unknown` | `#B692F6` | `#6941C6` | 未知、待对账 |

焦点、禁用和图表序列也必须使用语义 token，并在两主题分别通过对比度检查，不能简单反色。间距仅使用 `4/8/12/16/24/32/48/72`；圆角仅使用 `0/4/8`；默认无阴影，只有浮层可使用一级弱阴影；动效 `120–200ms` 并遵守 `prefers-reduced-motion`。

### 4.3 组件与状态最小集合

只保留以下共享表现组件：App Shell/导航/主题切换、全局风险横幅与数据新鲜度、数据表格/手机列表、文字+图标+色调状态标记、Proposal/Risk Summary、表单与价格数量输入、审批/危险动作确认/MFA、加载/空/陈旧/部分/未知/禁止/失败/离线状态、订单/审计/事故时间线。Toast 只表示请求已收到，不能代替权威业务回执。

首次访问跟随系统主题，用户可手动切换并保存偏好；主题切换不得丢失草稿、筛选、对象版本或当前业务状态。深浅主题的信息、动作、图表语义和安全能力完全等价。

### 4.4 响应式与无障碍硬门

- 桌面采用多列工作区、数据表格和并列风险摘要；手机采用单列、固定可见风险横幅和关键动作区。复杂 MANUAL 提案按已确认的 `DEC-PROD-015` 使用分步录入，提交前展示完整风险摘要。
- 手机表格转成关键字段列表；只有非关键明细允许横向滚动。有效期、最大计划损失、档位、杠杆、保护价、风险状态和允许动作不得默认折叠。
- 交互目标至少 `44×44px`，支持 PWA safe-area、横竖屏、断网只读与重连状态；主验收尺寸为 `1440×900`、`390×844`，另验证 `360px` 最小宽度无关键内容溢出。
- 目标为 WCAG 2.2 AA：普通文本对比度至少 `4.5:1`，大文本和关键图形至少 `3:1`；完整键盘导航、明显焦点、逻辑焦点顺序、200% 文本缩放、字段级错误关联和可执行修正说明均为发布硬门。
- 风险状态必须同时显示完整状态名、原因、允许动作和图标/结构，不能只靠颜色。图表必须提供同数据的文字或表格入口；动态风险变化使用可访问通知，但不持续播报普通行情。

## 5. 核心旅程

### 5.1 `FLOW-SYSTEM-001`：SYSTEM 候选到初仓

前置：候选来自 Perptape 或 Trading 策略扫描；标的已发现并具备形成提案所需的市场、账户和认证事实。

| 步骤 | 主体 | 界面行为 | Trading 行为 | 用户必须看到 |
| ---: | --- | --- | --- | --- |
| 1 | System | 候选进入候选列表 | 保存来源、数据时间、版本和健康状态 | `SYSTEM` 来源、未下单状态 |
| 2 | System | 候选转为提案预览 | 标的分类、数据/能力检查、风险定仓 | 合格、拒绝或未知及原因 |
| 3 | System | 形成冻结版本 | 保存资本快照、信封、1R、档位、数量和授权边界 | 版本号、剩余有效期 |
| 4 | Reviewer | Web/PWA 或受限 Telegram 打开审核 | 重新校验身份、作用域和提案有效性 | 完整风险摘要、自审/复核要求 |
| 5 | Reviewer | 提交批准或拒绝 | 权限、MFA、Risk Engine 和并发判定 | “已提交”不等于“已成交” |
| 6 | Trading | 显示发送前复核 | 刷新市场、账户、预算和授权 | 允许、拒绝或过期原因 |
| 7 | Trading | 进入执行跟踪 | OMS → VenueAdapter → Freqtrade → 交易所 | 订单接受、部分/全部成交或未知 |
| 8 | Trading | 仓位页出现战役 | 确认真实仓位、原生保护和风险预留 | 保护状态与对账完成标志 |

SYSTEM 提案只能由绑定 `strategy_id + strategy_version` 的服务主体创建并关联人类业务 owner。人工不能更改来源为 SYSTEM，也不能把候选直接变成订单。

失败与替代路径：

- 候选数据陈旧：不形成可审核版本或使版本过期。
- 风险不足：显示拒绝和安全上限，不签发授权。
- 审核期间市场偏离：提案过期或要求新版本，不能沿用原按钮。
- 部分成交：立即进入保护与对账，不回到“等待审核”。
- 结果未知：冻结相关标的新增风险，不盲目重试。

### 5.2 `FLOW-MANUAL-001`：人工假设到初仓

前置：用户具有 `PROPOSER` 标签及目标账户、场所、板块作用域。

| 步骤 | 界面行为 | 验收要求 |
| ---: | --- | --- |
| 1 | 用户进入新建人工提案 | 明确标记 MANUAL；展示当前风险状态和数据时间 |
| 2 | 选择场所、账户、标的、方向和周期 | 不可交易或未分类标的立即说明原因 |
| 3 | 填写方向、触发价、委托价、数量、`reduce_only`、有效期、最大风险、失效价和假设 | 字段错误就地提示；不得自动填成最大安全数量；最大风险不得越过档位上限 |
| 4 | 选择低/中/高风险及是否预授权自动加仓 | 默认关闭加仓；展示档位损失上限、杠杆上限和次数 |
| 5 | 执行风险预检 | 分开展示资金占用、1R、最大计划损失、保证金和名义仓位 |
| 6 | 用户提交 | 超额请求硬拒绝，不能静默缩量；成功后冻结版本 |
| 7 | 进入人工审核 | 保存提案人；禁止自审，按风险档执行 1 / 1 / 2 名独立 Reviewer 规则 |
| 8 | 审核后进入与 SYSTEM 相同的复核、执行和保护流程 | 来源不同，但风控、执行和审计不得降级 |

手机 PWA 必须以分步向导提供字段完整的复杂提案能力，提交前展示与桌面端相同的完整风险摘要，不得丢失字段后提交简化提案。

### 5.3 `FLOW-REVIEW-001`：审核、拒绝、过期与退回

审核详情加载时必须重新读取当前提案版本、风险状态、用户权限和剩余有效期。

| 场景 | 产品行为 |
| --- | --- |
| 审核允许 | 显示全部风险摘要；完成所需 MFA/复核后提交决定 |
| Risk Engine 拒绝 | 禁用批准；展示稳定原因码和可修复条件 |
| 权限不足 | 不显示越权信息；显示缺少的标签或作用域 |
| 自审 | 禁止批准本人提案，增加认证或 Reviewer 数量也不能覆盖 |
| 提案过期 | 所有旧按钮无效；提供查看或生成新版本入口 |
| 价格/风险事实变化 | 按合同使版本过期或重新风险定仓，不静默刷新后批准 |
| 拒绝 | 要求或允许选择结构化理由；立即终止该版本 |
| 退回修改 | 保持原版本不可变；修改后创建新版本并重新审核 |
| 多人/多端并发 | 各 vote 原子记录，按 1 / 1 / 2 名独立 Reviewer 的 quorum 汇总为唯一权威终态；客户端展示处理结果 |

Telegram 当前只打开该冻结版本的 Web 审核页；批准/拒绝和动作级 step-up 均在 Web 完成。最终授权只能由同一审批服务生成，Telegram 消息和深链本身都不是授权事实。

### 5.4 `FLOW-ENTRY-001`：初仓执行与原生保护

1. 审核完成后，页面进入“待发送前复核”，而不是直接显示成交。
2. Trading 重新校验提案有效期、价格偏离、账户事实、预算、权限版本和执行器健康。
3. 允许后创建唯一订单意图；界面显示意图 ID、执行场所和更新时间。
4. 订单接受后展示场所订单 ID；拒绝时展示映射原因。
5. 任意初仓成交立即触发保护确认，不能等待全部成交才开始保护。
6. 只有真实仓位和足额保护均确认后，状态进入“仓位已建立”。
7. 部分成交、保护缺失或结果未知进入异常中心；不得通过 UI 重复点击补足。

验收：页面刷新、PWA 重连或 Telegram 重复通知均不能产生第二个初仓意图。

### 5.5 `FLOW-ADD-001`：自动加仓候选与执行

前置：初仓已真实成交、保护已确认、自动加仓在开仓时预授权且仍有效。

| 阶段 | 用户可见信息 | 不允许的表现 |
| --- | --- | --- |
| 里程碑未到 | 当前收益、下一候选门、剩余次数 | 暗示一定会加仓 |
| 里程碑已到 | 候选已解锁、仍待回调/趋势/风险门 | 把解锁显示为订单 |
| 条件检查 | 目标杠杆、当前杠杆、目标差额、最新 MTM、预算和保护 | 使用固定比例手数 |
| 跳过 | 失败条件、时间和可否以后重新候选 | 隐形排队旧订单 |
| 发送 | Add ID、预期差额和安全缩量原因 | 绕过实时 Risk Engine |
| 部分/全部成交 | 实际成交、`target_reached`、一次 Add 已消费 | 非零成交后同级自动补单 |
| 终态零成交 | 零成交证据、Add 未消费 | 错误消费次数 |
| 结果未知 | 冻结后续增险并对账 | 猜测失败后重试 |

用户关闭自动加仓后，剩余 Add 授权与所有未消费 AddUnit 必须立即进入 `REVOKED / INVALIDATED`，已有仓位保护与退出继续。恢复风险状态不得复活它们；重新开启属于扩权，需要新提案版本和重新人工批准。

### 5.6 `FLOW-RISK-REDUCE-001`：暂停、减仓与退出

| 动作 | 固定语义 | 作用域与约束 |
| --- | --- | --- |
| 关闭某仓自动加仓 | 立即收紧，只影响未来 Add | 支持战役及上层固定作用域，向下继承 |
| 暂停新开仓 | 阻止对应范围新初仓 | 支持全局、场所、账户、板块、策略、标的和战役层级 |
| 紧急减仓 | 只允许 `reduce-only`，不得反向开仓 | 只允许预定义比例或目标安全状态 |
| 完全退出 | 关闭净仓位并对账保护/挂单 | Operator / Risk Admin 在有效作用域内发起；Telegram 只提交受限意图 |
| 恢复增险 | 不得自动发生 | 双人批准并重新读取全部事实；旧授权不复活 |

每个收紧动作必须在确认前展示：对象、账户、场所、方向、当前仓位、目标仓位、是否取消剩余 Add、可能滑点和不可撤销影响。提交后依次展示“已受理、已获准、订单发送、成交、对账”，不能以按钮变绿表示完成。

当前 `/risk` 恢复旅程由 HUMAN SYSTEM_ADMIN 填写原因并选择是否同时恢复 AUTO_ADD；页面冻结当前 RiskPolicy/AUTO_ADD version 和运行时 scope，显示 15 分钟冷却、24 小时有效期和实时 blocker；申请人之外的两名不同 HUMAN 且有 `risk.restore.review` 权限的用户（REVIEWER 或 SYSTEM_ADMIN）分别完成绑定对象当前 version 的动作级 step-up；HUMAN SYSTEM_ADMIN 执行者再次 step-up 后，服务端重验全部事实和版本才创建新 NORMAL 政策。生产未配置 LIVE scope、事实 Unknown/陈旧、对账非 MATCH 或控制漂移时，页面必须显示不可执行原因；`KILL_SWITCH` 只引导事故恢复，不显示常规恢复入口。Telegram 和离线 PWA 均无恢复动作。

### 5.7 `FLOW-EXISTING-POS-001`：系统外或既有仓位

当 Trading 启动、恢复或对账时发现没有对应有效战役的真实仓位：

1. 立即标记“外部/未归属仓位”，不得自动绑定到任一提案。
2. 禁止对其自动加仓和产生新的增险授权。
3. 展示真实仓位、订单、保护、保证金、发现时间和未知风险。
4. 立即冻结受影响账户新增风险并由人工分类；只有建立接管记录、保护和风险映射后才进入受控管理，必要时只减仓或退出。
5. 处理完成前，受影响账户和风险范围按专项合同降级。

### 5.8 `FLOW-INCIDENT-001`：异常发现、处置与恢复

| 步骤 | 系统行为 | 用户行为 |
| ---: | --- | --- |
| 1 | 产生稳定异常 ID，判定影响范围 | 收到 Web/Telegram 告警 |
| 2 | 自动进入必要的风险降级 | 查看已采取动作，不需要先点击确认才生效 |
| 3 | 异常中心生成时间线和责任角色 | 具有权限者确认接手 |
| 4 | 按运行手册执行对账、保护、减仓或隔离 | 每步记录证据和结果 |
| 5 | 根因修复后完成重放、对账和冷却 | 申请恢复，不直接恢复 |
| 6 | 按批准政策逐级解除限制 | 所有旧提案与旧授权继续失效 |

控制面故障时，原生保护、预认证 `reduce-only` 减仓与退出按固定安全路径继续。只有 UI / 通知入口失效，且 Trading、授权、Risk、账户事实与保护全部健康时，既有 Add 才可能继续；其余情况停止 Add。系统与告警 24×7 值守，备用告警至少使用两条不同供应商或网络路径；SLO 数值由运行证据冻结。

### 5.9 `FLOW-CAPITAL-001`：人工资金划转

1. 资金管理员从资金中心创建划转草稿；交易提案不能代替资金提案。
2. 系统校验源端余额、空仓与订单状态、地址/资产/网络、额度、等待期和风险影响。
3. 按资金权限策略完成独立复核与 MFA。
4. 提交后展示源端预留、提款提交、在途、目的确认、结算或未知。
5. 只在目的端真实到账并对账后计为可用；失败或未知不能退回“双边可用”。
6. 活动仓位从 Vault 救仓的请求必须拒绝。

Vault 只读、人工双向划转、自动利润归集和可选自动运营补充全部属于完整产品目标并独立授权；自动能力默认关闭，外部链路事实或能力证书缺失时保持关闭。

资金中心默认视图只展示 LIVE 来源、LIVE 预留/在途和 LIVE 净值。SHADOW 与 TESTNET 数据集中放入默认折叠的“模拟数据（SHADOW / TESTNET）”区域，并明确“不计入真实净值”；不能把 `hyperliquid-main · SHADOW` 的模拟余额放在 LIVE 概览。Binance、Hyperliquid 和 Vault 的 LIVE 槽位始终可见：Vault 没有资金事实时显示 `0 USD · MISSING / 未配置或未同步`，但该零值只是缺失占位，不是可交易资本或完整净值证据。

## 6. Telegram 交互规格

### 6.1 通知卡片与命令

当前真实 Bot 使用中文 HTML、清晰状态标题和有限必要披露；支持 `/start` 绑定、`/help` 查看边界、`/status` 查看 Bot 能力状态，并在启动时注册命令。每条可操作消息至少包含：

- 事件类型与严重度。
- 提案、仓位或异常的不可混淆短标识。
- 在确有必要时显示最小化的场所/对象摘要；完整账户、数量、风险和资金事实留在 Web。
- 当前状态、事实时间和消息生成时间。
- 对审核提案：状态、不可混淆短标识和 Web 审核深链；Telegram 不展示或完成批准。
- 对风险事件：影响范围、自动降级、当前允许/禁止动作。
- Web / PWA 详情深链。

消息不得包含 API Key、私钥、助记词、提款地址完整敏感信息或可复用授权参数。

### 6.2 允许的轻量动作

- 打开一份仍有效冻结提案的 Web 审核页；Telegram 消息本身不能批准或拒绝。
- 关闭某仓或已批准作用域内的自动加仓。
- 对仍处于 `OPENING / OPEN / REDUCING / CLOSING` 且目标仓位大于零的 Campaign，提交预定义紧急减仓或完全退出请求。
- 打开 Web / PWA 完整详情。

Telegram 禁止创建 MANUAL 提案、批准/拒绝提案、修改风险档位、增加 Add 次数、恢复增险、管理权限、改变风险政策、批准或执行资金划转、以及直接调用 Freqtrade。

### 6.3 按钮与回执

- 按钮绑定唯一对象、版本、动作、用户和短期有效期。
- 点击后先显示“正在提交”，收到 Trading 权威回执后才显示允许、拒绝、已过期、已被处理或结果未知。
- 旧消息必须更新为不可操作状态或使所有旧按钮在服务端失效。
- 关闭 Add、紧急减仓和退出先展示对象、环境、影响和版本的确认页；只有第二次点击“确认”才提交。取消不产生业务动作，提交终态后移除旧按钮。
- 账号使用 chat ID、一次性绑定和设备/Passkey 二次绑定；敏感动作只在私聊完成 step-up，转发消息无授权效力，丢失设备后撤销旧绑定。
- 通知发送、送达、已读和操作完成分别记录。

## 7. PWA 与移动交互规格

`UX-PWA-001` 在线 PWA 使用与 Web 相同的服务端权限、状态和审计，不建立独立移动授权。

`UX-PWA-002` 离线或连接质量不足时：

- 全局展示“离线只读快照”和快照时间。
- 禁用批准、恢复、减仓、退出、资金和权限等所有操作。
- 不将本地点击排队为恢复网络后自动执行的交易动作。
- 重新在线后先刷新对象版本、权限和风险状态，再恢复可操作性。

按已确认的 `DEC-PROD-010`，只允许短 TTL、带时间戳、加密且可远程撤销的非敏感摘要缓存；离线不能批准、恢复或执行交易/资金动作。

`UX-PWA-003` 移动审核摘要的关键风险信息、权限要求和剩余有效期不得折叠到默认不可见区域。按已确认的 `DEC-PROD-015`，手机端必须支持字段完整的分步 MANUAL 提案，并在提交前显示完整风险摘要。

## 8. 用户文案规则

- 使用“提案、批准、受理、发送、成交、保护、对账”准确描述阶段，禁止统一写成“交易成功”。
- 使用“最大计划损失”而非“保证最大损失”；极端滑点和故障可能穿透计划值。
- 使用“资金占用”描述 Trade Funding Envelope，不能称为风险或可亏金额。
- 使用“候选解锁”描述 30% / 50% / 100%，不能写成“到达即加仓”。
- 使用“未知/对账中”表达无法确认的事实，不能用“暂未成交”猜测。
- 拒绝文案必须提供原因和下一合法动作，但不能暗示用户可以绕过风控。
- 风险状态、日期、日终与报告币种的显示遵循 `DEC-OPS-010`。
