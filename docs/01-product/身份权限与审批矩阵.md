## 1. 文档目的

本文把“一个用户可拥有多个标签、不同标签对应不同权限”的原则展开为可实现、可测试的身份、作用域和审批合同，回答：

- 哪类主体可以对哪类资源执行什么动作。
- 多标签如何合并，哪些显式拒绝和职责分离永远优先。
- 初仓审核、风险放宽、资金划转、紧急操作和恢复如何复核。
- Web / PWA 与 Telegram 如何得到相同的权限结果。
- 标签、作用域、MFA 或会话变化后，旧页面和旧按钮如何失效。
- 每个允许或拒绝决定必须保存哪些证据。

本文不授权任何人覆盖 Trading Risk Engine，也不授予任何界面直接下单或提款能力。已冻结决策直接作为实现合同；研究参数和外部事实没有证据时，对应能力默认关闭而不是由研发猜测。

## 2. 权限模型

### 2.1 主体类型

系统至少区分：

| 主体 | 含义 | 限制 |
| --- | --- | --- |
| Human User | 通过 Web / PWA 或绑定 Telegram 操作的自然人 | 使用多标签、作用域、MFA 和职责分离 |
| Service Principal | Trading、Risk Engine、OMS、通知、对账等服务身份 | 只能执行固定机器职责，不能继承人类标签 |
| Execution Principal | 与特定 VenueAdapter / Freqtrade worker / 账户绑定的执行身份 | 只能消费已获准订单意图，不能审批或改风险 |
| Treasury Principal | CTO、受限签名器或 funding wallet 身份 | 不能发送交易订单或审核交易提案 |
| Break-glass Principal | 仅用于紧急保护或恢复的高审计身份 | 能力、保管和启用由安全专项政策定义，不等同系统管理员 |

产品固定为一个资本所有者、内部单组织、多用户多标签；不开放外部注册，不管理第三方资金。组织边界仍必须显式建模，不能用全局单一用户假设消除账户与资源作用域。

当前系统不建立任何辅助建议源专属主体。若未来另行接入通用建议输入，只能作为无权限内容来源；它不得持有密钥、签名、下单、资金或风控覆盖权，也不能签发授权。

### 2.2 授权计算顺序

每次动作使用同一服务端授权流程：

1. 验证主体、会话、设备和渠道身份。
2. 加载当前有效标签；不信任前端或 Telegram 消息中缓存的标签。
3. 计算标签允许动作的并集。
4. 与资源作用域、账户、场所、板块、风险档位、金额、时间、渠道、设备可信度和 MFA 范围求交集。
5. 应用职责分离、自审、复核人数和风险状态限制。
6. 应用所有显式拒绝；显式拒绝优先于任何允许。
7. 对交易和资金动作继续执行 Risk Engine、Treasury Policy 或其他领域硬门。
8. 返回允许或拒绝的稳定决定、原因、政策版本和短期有效边界。

授权关系可表示为：

> `Effective Permission = Role Allows ∩ ABAC Scope ∩ Session Assurance ∩ SoD Policy ∩ System State - Explicit Denies`

即使权限允许，Risk Engine 或交易/资金状态拒绝时动作仍失败。权限通过不等于订单、成交或划转成功。

### 2.3 默认规则

- 默认拒绝；没有标签或没有匹配作用域即拒绝。
- 一个用户可以拥有多个标签，但多标签不会产生隐式自审权、风控豁免或职责分离豁免。
- System Admin 不自动获得交易审核、风险放宽、资金或执行权限。
- Reviewer 不能修改正在审核的冻结提案。
- 风险、资金、交易与系统管理权限相互独立。
- UI 隐藏按钮只是体验优化，服务端必须再次授权。
- 风险状态收紧立即覆盖旧会话和旧授权；风险恢复不会自动恢复权限。
- 标签撤销和显式拒绝应立即影响未来动作，旧 Web 页面和旧 Telegram 按钮不能继续扩权。

## 3. 基础标签定义

| 标签 | 允许的核心职责 | 永久不因该标签获得的能力 |
| --- | --- | --- |
| `OBSERVER` | 查看作用域内候选、提案、仓位、风险、资金、异常和审计结果 | 创建、审核、风险变更、交易操作、资金划转、权限管理 |
| `PROPOSER` | 创建、编辑和提交 MANUAL 草稿 | 批准提案、覆盖风控、直接执行 |
| `REVIEWER` | 在作用域内批准或拒绝冻结初仓提案 | 修改提案、改风险政策、直接下单或划转资金 |
| `OPERATOR` | 关闭加仓、暂停新增风险、发起获准的紧急减仓/退出、处理异常与对账 | 新增风险、放宽止损、提高档位、资金划转 |
| `RISK_ADMIN` | 管理版本化风险政策、限额、降级和恢复申请 | 直接下单、提款、单人覆盖硬风控 |
| `TREASURY_ADMIN` | 创建、复核和追踪 Vault / 场所资金划转 | 交易审核、改变交易风险、救援活动仓位 |
| `SYSTEM_ADMIN` | 用户、标签、作用域、MFA、会话和系统配置管理 | 默认不继承观察、审核、风险、资金或交易权限 |

SYSTEM 提案只能由已认证的策略 `service_principal` 创建；`PROPOSER`、`REVIEWER` 或管理员都不因人类标签获得 SYSTEM 创建 / 提交权。`DEC-PROD-006` 只决定 owner、撤回、退役和责任归属。

- `A`：标签默认允许，但仍需 ABAC、系统状态和领域硬门。

## 5. ABAC 作用域

标签只提供动作类别，实际权限至少可以按以下属性缩小：

| 属性 | 示例 | 产品验收要求 |
| --- | --- | --- |
| Organization / Workspace | 私有工作空间、团队 | 不得跨组织检索或操作 |
| Account | Binance 账户、Hyperliquid subaccount | 每个动作明确目标账户 |
| Venue / Domain | Binance、HL Core、HIP-3 DEX | 不因同名资产继承权限 |
| Asset / Sector | BTC、加密、股指、贵金属 | 未分类资产默认拒绝 |
| Risk Tier | 低、中、高 | Reviewer 不能审批超出档位范围 |
| Action | approve、pause、reduce、transfer | 不授予界面全部能力 |
| Amount | 交易风险或资金金额区间 | 超限进入更高复核或拒绝 |
| Time | 值班时段、临时授权有效期 | 过期立即拒绝 |
| Channel | Web、PWA、Telegram | Telegram 不继承 Web 全部能力 |
| Device Assurance | 已注册设备、受信会话 | 低可信设备触发 step-up 或拒绝 |
| MFA Level | 登录 MFA、动作级重认证 | 认证强度不足不得执行高风险动作 |

作用域必须展示在审核和管理页面中。用户只有标签但没有资源作用域时，权限结果为拒绝，而不是全局允许。

## 6. 审批政策矩阵

### 6.1 初仓审核

初仓全部需要人工明确批准并通过 Risk Engine；Risk Engine 始终可以拒绝，任何角色或审核人数都不能覆盖。审批规则已经冻结：

| 场景 | Risk Engine | 人工审核 | 自审 | 备注 |
| --- | --- | --- | --- | --- |
| 低风险 1R / 3x | 必须通过；可硬拒绝 | 1 名非提案者 | 禁止 | 自动加仓仍默认关闭 |
| 中风险 2R / 5x | 必须通过；可硬拒绝 | 1 名非提案者 | 禁止 | 不继承低风险放宽 |
| 高风险 3R / 10x | 必须通过；可硬拒绝 | 2 名独立 Reviewer | 禁止 | 高风险不能因单标签自动放宽 |
| MANUAL 提案 | 必须通过；可硬拒绝 | 按风险档固定规则 | 禁止 | 保留提案人身份 |
| SYSTEM 提案 | 必须通过；可硬拒绝 | 按风险档固定规则 | 不适用（服务主体创建） | 关联策略版本与人类 owner |

无论人数如何选择：

- 提案事实、批准事实和 Risk Engine 决定必须独立保存。
- 多名审核者不能分别批准不同提案版本。
- 同一身份拥有 Proposer + Reviewer 不自动产生自审权。
- 风控拒绝时，增加审核人数也不能将其改为允许。
- 风险政策放宽、资金动作、权限扩张、生产发布和高风险初仓均需要双人独立复核。

### 6.2 风险放宽、资金、身份与恢复

| 变更 | 固定要求 | 执行规则 |
| --- | --- | --- |
| 风险政策收紧 | 可立即生效并审计 | 由有效 Risk Admin 作用域执行 |
| 风险政策放宽 | 不能自动、不能覆盖硬风控 | 提议人与最终批准人分离，双人复核 |
| 提高风险档位/增加 Add | 新交易提案与人工审核 | 使用目标风险档固定 Reviewer 人数 |
| 资金划转 | 独立于交易授权；需要资金权限与 MFA | 创建者不得最终批准，金额分级并经多签执行 |
| 标签/作用域扩大 | 不能由业务标签自行授予 | 双人复核、强认证和完整审计 |
| REDUCE_ONLY / KILL_SWITCH 恢复 | 不能自动恢复，旧提案不复活 | 双人批准，短时 break-glass 不能直接恢复增险 |

## 8. MFA、会话与动作级认证

Passkey / WebAuthn 是主要强认证方式。以下动作至少需要 MFA 或短时动作级重新认证，认证范围绑定主体、设备、动作和资源版本：

- 批准初仓。
- 风险政策放宽。
- 恢复新增风险。
- 紧急减仓或完全退出。
- 创建、批准或执行资金划转。
- 授予标签、扩大作用域、MFA 重置和高权限会话恢复。
- 使用 break-glass 身份。
- 导出敏感审计证据。

`IAM-SESSION-001` 权限判断使用动作发生时的当前标签和作用域，不使用登录时永久快照。

`IAM-SESSION-002` 标签撤销、作用域收紧、用户冻结、MFA 失效或显式拒绝新增后，旧会话下一次敏感动作必须失败；客户端收到权限变化后立即刷新可见操作。

`IAM-SESSION-003` 短时动作授权只能绑定一个主体、设备、渠道、动作、资源版本和有效期，不能复用于另一提案或资金动作。

`IAM-SESSION-004` 登录成功、Telegram 消息送达或设备受信均不能替代针对高风险动作要求的认证强度。

## 9. 身份生命周期

### 9.1 创建与授权

1. 建立用户或服务主体，分配不可变主体 ID。
2. 完成身份验证和初始 MFA。
3. 由独立有权主体授予最小标签与资源作用域。
4. 写入授予者、理由、政策版本、生效和失效时间。
5. 用户重新认证后，客户端刷新权限；旧缓存不能自动增加能力。

系统不提供外部自助注册。内部用户由独立有权管理员创建并分配最小权限；首位管理员和组织恢复必须走受控部署或 break-glass 流程并完整审计。

### 9.2 Telegram 绑定

Telegram 身份不能独立创建 Trading 用户或标签。绑定使用一次性码和已认证设备/Passkey，敏感动作只允许私聊完成 step-up；换号、重绑与设备丢失必须撤销旧绑定。绑定后 Telegram 仍按每个动作重新加载当前权限。

### 9.3 变更与撤销

- 标签增加和作用域扩大视为扩权，必须按身份治理政策复核。
- 标签撤销和作用域收紧可立即生效。
- 用户冻结应撤销所有活动会话、Telegram 动作引用和未消费的临时动作授权。
- 历史审批继续保留原身份快照；撤销不能追溯性修改历史事实。

### 9.4 离职、设备丢失与凭据异常

处理至少包括：冻结主体、撤销 Web/PWA 会话、解绑 Telegram、撤销 API/服务凭据、检查待处理审批、资金与风险操作、生成审计事件。是否保留只读审计访问由专项政策决定。

## 10. 职责分离硬门

以下组合不能因为单个用户拥有多个标签而自动允许：

- 创建提案并最终批准同一提案；禁止自审且无标签组合例外。
- 提出并最终批准同一项风险放宽。
- 提出并最终批准/执行超出专项阈值的资金划转。
- 授予自己标签、扩大自己的作用域或批准自己的 MFA 恢复。
- 用 System Admin 标签取得 Reviewer、Risk Admin 或 Treasury Admin 能力。
- 用 Treasury Admin 资金划转为活动仓位救援。
- 用 Operator 紧急动作反向开仓或扩大净仓位。
- 让策略、服务身份或任何辅助建议源自行授予人类审批权。

即使资本只属于一个所有者，也不得以“只有一个用户”为由合并禁止自审、双人资金、权限扩张、高风险初仓或生产发布等职责。缺少独立审核者时，对应动作保持关闭。

---

## 11. 授权决定与审计字段

每次允许或拒绝至少保存：

- `decision_id`、请求 ID、对象 ID 与对象版本。
- 主体 ID、主体类型、全部有效标签。
- 组织、账户、场所、板块、风险档位、金额和动作作用域。
- 渠道、设备/会话、认证方式与认证强度。
- 自审关系、复核链和职责分离结果。
- 系统风险状态、Risk Engine / Treasury Policy 结果。
- 命中的允许规则、显式拒绝和稳定原因代码。
- 权限与政策版本、请求时间、决定时间和有效期。
- 最终允许/拒绝结果及后续业务对象 ID。

审计保留、导出、脱敏、删除和证据保全引用 `DEC-GOV-002`。授权服务或审计不可用时是否允许继续新增风险，必须遵守运行和安全合同，界面不得本地伪造允许结果。

## 12. 研发验收用例

| 测试 ID | 场景 | 预期 |
| --- | --- | --- |
| `UAT-IAM-001` | 用户无标签查看账户 | 默认拒绝，不泄露账户存在性 |
| `UAT-IAM-002` | Observer 尝试创建或批准提案 | 服务端拒绝并审计 |
| `UAT-IAM-003` | Proposer 提交 MANUAL 草稿 | 作用域内允许；仍不获得批准权 |
| `UAT-IAM-004` | Proposer + Reviewer 审核本人提案 | 禁止自审，不能因标签并集自动允许 |
| `UAT-IAM-005` | Reviewer 审核超出板块/档位范围 | 拒绝并返回作用域原因 |
| `UAT-IAM-006` | Reviewer 面对 Risk Engine 拒绝 | 无任何标签可覆盖拒绝 |
| `UAT-IAM-007` | System Admin 尝试审核或资金划转 | 若无对应独立标签与作用域则拒绝 |
| `UAT-IAM-008` | Telegram 使用已过期按钮 | 拒绝，不生成新授权或订单 |
| `UAT-IAM-009` | 标签撤销后使用旧 Web 会话 | 敏感动作立即拒绝，UI 刷新权限 |
| `UAT-IAM-010` | Telegram 绑定用户被撤权 | 旧消息按钮不能继续扩权 |
| `UAT-IAM-011` | Operator 发起可能反向开仓的减仓请求 | 拒绝并进入异常/人工处置 |
| `UAT-IAM-012` | Treasury Admin 请求给活动仓救援注资 | 拒绝，不因资金标签放宽交易风险 |
| `UAT-IAM-013` | 多标签组合命中显式拒绝 | 拒绝优先，结果可重放 |
| `UAT-IAM-014` | 两名 Reviewer 对同一版本并发操作 | 各有效 vote 原子记录，按 `DEC-PROD-004` 的 quorum 产生至多一个汇总终态，不重复授权 |
| `UAT-IAM-015` | PWA 离线使用缓存权限 | 所有敏感动作禁用且不排队 |
| `UAT-IAM-016` | REDUCE_ONLY 指标恢复 | 不自动恢复权限，走正式恢复审批 |
| `UAT-IAM-017` | 审计写入失败 | 不在客户端假定允许；按运行合同降级 |
| `UAT-IAM-018` | 任意辅助建议源输出“批准” | 只作为无权限内容；不创建 vote、ApprovalDecision、授权或订单意图 |

权限测试必须覆盖单标签、全部有效多标签组合、显式拒绝、作用域边界、MFA 不足、角色撤销、跨渠道和并发，不得只测试理想单角色路径。

## 13. 已冻结决策与研究依赖

| 决策 | 对本文件的影响 |
| --- | --- |
| `DEC-PROD-001/004..013` | 内部单组织、禁止自审、固定 quorum、Telegram step-up、作用域、脱敏、离线和外部仓位规则 |
| `DEC-SEC-001/003..005` | 托管身份、Passkey/WebAuthn、双人 break-glass、Telegram 绑定和 PWA 设备安全 |
| `DEC-FUND-009` | 资金创建者不得最终批准，金额分级并与签名角色分离 |
| `DEC-GOV-001` | 按领域 RACI，高风险扩权与生产发布双人批准 |
| `DEC-GOV-002` | 审计保留期限仍需研究证据；证据生效前不删除核心审计 |
| `DEC-OPS-004` | 只有 UI/通知入口失效且 Trading、授权、Risk、账户事实与保护均健康时既有 Add 才可能继续 |

权限合同没有待产品选择项。研究期限或外部负责人事实尚未补齐时，系统仍实现完整权限模型，但受影响的导出、发布或真实写能力保持关闭。
