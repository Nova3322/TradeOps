## 1. 文档目的

本文把既有总体方案和策略合同转化为可拆分、可设计、可开发、可验收的产品需求。它回答：

- 用户是谁、要完成什么任务。
- Web / PWA 与 Telegram 分别承担什么职责。
- SYSTEM 与 MANUAL 提案如何进入同一审核、风控、执行和审计链路。
- 用户能看到什么、能发起什么操作、何时必须被拒绝或降级。
- 完整产品需要达到什么工程完成门，以及各真实资金能力需要哪些独立认证证据。

本文不重复定义风险公式、订单协议、交易所适配、数据库结构或代码实现。发生冲突时，安全与风险不变量以上位文档及后续版本化专项合同为准；页面和文案不得改变它们的语义。

产品设计选择已按[决策与研究登记](../00-governance/待确认决策清单.md)冻结。标记为 `RESEARCH_REQUIRED` 的参数不是待选产品范围，而是必须先实现其配置、验证和安全关闭能力，再以真实证据冻结数值；三项 `OPEN` 仅是需要外部输入的 Vault 部署、运营合规和实际负责人事实。

## 2. 产品定义

Trading 是一套半自动交易指挥与风险管理系统：

> 用户提出或审核交易假设；系统在有限授权内成为受管账户唯一的日常订单发送者，并负责风控、执行、自动加减仓、保护、退出、对账和审计。

完整目标同时覆盖 Binance 与 Hyperliquid 的 U 本位永续合约。Catalog 与风险模型覆盖场所实际提供的加密货币、美股及股指、贵金属、商品及商品期货参考资产，但“可发现”不等于“可实盘”；真实写权限仍只授予逐个通过认证的标的、账户、执行域和保证金拓扑。

产品按一个资本所有者、内部单组织、多用户多标签部署，不开放外部注册或第三方资金。Binance、Hyperliquid、Vault 只读、人工双向划转、自动利润归集、可选自动补充，以及桌面和手机端完整复杂提案都属于同一完整目标；自动资金能力默认关闭并独立授权。Perptape 与 Trading Console 保持独立应用和故障域，通过版本化 API、统一身份与深链协作。

工程交付不得以局部版本、单场所样板或功能拆批方式删减上述目标。影子、仿真、小额实盘和逐执行域证书是同一完整系统的能力认证环境，不是产品范围分期；工程完成不自动授予真实资金写权限。

## 3. 已冻结的产品边界

以下边界不是页面偏好，产品与研发不得绕过：

1. Web / PWA 是完整主控制台；电脑和手机使用同一账户、权限、风险状态和操作语义。
2. Telegram 是即时通知和轻量操作入口，不是第二套交易系统。
3. SYSTEM 与 MANUAL 是两种提案来源；二者在风险定仓之后进入同一冻结、审核、执行和审计链路。
4. 所有初仓都必须由人工明确批准，并再次通过 Trading Risk Engine；人工或任何辅助建议源均不能覆盖风控拒绝。
5. 自动加仓默认关闭。开启时，它属于初仓批准时签发的有限预授权，不逐次要求人工确认。
6. 自动加仓只允许盈利金字塔；30% / 50% / 100% 只解锁候选，每次 Add 按执行时的目标杠杆差额计算，不能配置成固定分层手数。
7. 任意大于零的真实 Add 成交消费一次 Add；终态零成交不消费。风险、流动性和执行约束可以安全缩量，但不能放宽风险。
8. 加仓前必须使用包含最新未实现盈亏的 Current Portfolio MTM Equity 重新校验组合预算；加仓后的最坏情况损失不能突破对应预算。
9. 止损、减仓、动态去杠杆和退出不等待新的人工批准。
10. Web、PWA、Telegram、FreqUI、Freqtrade 内置控制面和外部脚本均不能绕过 Trading 直接新增风险。
11. PWA 离线时只允许展示明确标记时间的只读快照；离线状态不得批准、恢复交易或声称操作成功。
12. 通知送达、用户阅读、操作受理、订单发送、真实成交和完成对账是不同状态，界面不得混为一谈。

产品展示必须遵守当前已冻结的三档语义：

| 风险档位 | 最大有效杠杆 | 整份经济仓位最大计划损失 | 启用自动加仓时默认最大次数 |
| --- | ---: | ---: | ---: |
| 低风险 | 3x | 1R = 初始总资金 0.5% | 1 |
| 中风险 | 5x | 2R = 初始总资金 1.0% | 2 |
| 高风险 | 10x | 3R = 初始总资金 1.5% | 3 |

`1R_0 = Total Capital Snapshot_0 × 0.5%`。Trade Funding Envelope 的 `N%` 是独立资金占用参数，不是允许亏损；正式 `N` 引用 `DEC-RISK-001`，不得把 1.5% 示例实现成默认值。每个档位的 `L_target / L_min / L_max` 精确值引用 `DEC-RISK-002`，但每次 Add“按执行时目标杠杆差额计算、而非固定百分比”的产品语义已经固定。

## 4. 产品目标与非目标

### 4.1 产品目标

- 把系统发现的候选和用户的看图假设转化为结构化、可冻结、可审核的交易提案。
- 让审核者在一个摘要中看清交易理由、反证、资金占用、最大计划损失、杠杆、加仓边界和组合影响。
- 阻止任何超额、过期、数据陈旧、无法对账或权限不足的新增风险动作。
- 在开仓后由系统持续执行保护、自动加减仓、退出与对账，使人工不需要持续盯盘下单。
- 让所有人从 Web / PWA 和 Telegram 看到同一权威状态和唯一回执。
- 在异常发生时优先保护资金，清楚展示当前限制、自动动作、人工责任和恢复条件。
- 保留从提案到结算的完整证据，使策略、审核、执行、风险和异常贡献可以复盘。

### 4.2 当前非目标

- 不保证盈利，也不把回测结果包装成收益承诺。
- 不允许用户、Telegram 或任何辅助建议源绕过 Trading 直接下单。
- 不提供亏损补仓、摊低成本或持仓期间从 Vault 救仓。
- 不把 FreqUI 作为生产主控制台。
- 当前系统不接入辅助建议源的授权、交易或资金路径，也不预建相应主体、页面、路由或指标；未来若另行接入，仍不得拥有密钥、签名、下单、资金或风控覆盖权。
- 不默认接入 CFD、股票券商或其他新执行场所。
- FundPool、FundShare、DAO、基金份额、公开募资、代客理财和第三方资产托管属于独立项目，本系统不做占位实现。
- 不提供外部多租户、计费、公开服务或第三方资金管理能力。

## 5. 用户与核心任务

一个用户可拥有多个标签，实际权限由标签允许动作、资源作用域、设备与渠道、MFA、职责分离和显式拒绝共同决定。

| 用户标签 | 核心任务 | 主要产品入口 |
| --- | --- | --- |
| `OBSERVER` | 查看信号、提案、仓位、风险、资金、异常和审计结果 | Web / PWA；Telegram 只读通知 |
| `PROPOSER` | 创建、编辑并提交 MANUAL 草稿 | Web / PWA |
| `REVIEWER` | 审核仍有效的冻结初仓提案 | Web / PWA；Telegram 受限入口 |
| `OPERATOR` | 关闭加仓、暂停新增风险、发起紧急减仓、处理异常和对账 | Web / PWA；Telegram 受限入口 |
| `RISK_ADMIN` | 管理版本化风险政策、限额、冻结与恢复流程 | Web / PWA |
| `TREASURY_ADMIN` | 发起、复核和追踪 Vault / 交易所资金划转 | Web / PWA |
| `SYSTEM_ADMIN` | 管理身份、标签、作用域、会话和系统配置 | Web / PWA |

SYSTEM 提案只能由已认证的策略 `service_principal` 创建；人类用户不能创建、提交或伪造 SYSTEM 来源。`DEC-PROD-006` 只决定对应的策略 owner、撤回、退役和责任归属，不重新打开人工创建权。

系统固定为一个资本所有者、内部单组织、多用户多标签；账户、场所与资源作用域必须显式隔离。Observer 只按作用域查看脱敏信息，默认隐藏密钥、完整地址、个人身份、完整资金金额和敏感审计字段。

## 6. 核心产品能力

### 6.1 统一总览

`PRD-DASH-001` Web / PWA 必须提供一个统一总览，至少展示：

- Trading 全局风险状态及最后更新时间。
- Binance、Hyperliquid、Freqtrade worker、市场数据、私有账户数据、Risk Engine、审计和通知健康状态。
- 当前 Current Portfolio MTM Equity、未实现盈亏、Open / Reserved / Unknown Heat 和各层预算占用。
- 四个资产板块、相关风险簇、交易场所和账户的占用与上限。
- 待审核提案、活动仓位、未完成订单、保护异常、资金在途和未处理事故数量。
- 当前用户的标签、作用域和可用操作。

验收：任何陈旧、未知或部分不可用的数据都必须在对应数字旁显示状态、来源和时间；不得用零值或空白掩盖未知。

### 6.2 候选与 SYSTEM 提案

`PRD-SIGNAL-001` 候选列表必须区分“已发现、数据合格、可交易、已形成提案、已过期、被拒绝和执行中”，并展示来源、标的身份、场所、板块、信号时间、数据健康和认证状态。

`PRD-SIGNAL-002` 候选不是订单。任何生成提案的操作都必须进入风险预检、版本冻结和人工审核，不能出现“发现即交易”的按钮或文案。

`PRD-SIGNAL-003` 相同底层资产在 Binance、Hyperliquid Core 和不同 HIP-3 DEX 上必须保留独立场所身份；界面可以聚合观察，但不能隐式合并订单或仓位。

`PRD-SIGNAL-004` 非加密参考资产可以进入发现、分类和只读研究，但何时进入真实交易必须遵循 `DEC-PROD-014`；未完成交易日历、预言机、公司行动、流动性和执行认证时，不得显示为可实盘。

### 6.3 MANUAL 人工提案

`PRD-PROP-001` MANUAL 提案仅在 Web / PWA 创建。草稿至少包含：

- 交易场所、账户、标的、板块、方向和决策周期。
- 触发价、订单类型、委托价、最大滑点、用户请求数量、`reduce_only` 和有效期。
- 初始失效价、交易假设、支持理由和主要反证。
- 用户请求的最大风险、风险档位、是否预授权自动加仓、允许次数和目标杠杆区间预览。
- 数据时间、市场状态和必要的附件或备注。

`PRD-PROP-002` 草稿保存不产生执行权。提交前必须完成字段校验、标的与板块识别、市场及账户数据新鲜度校验、执行能力检查和风险预检。

`PRD-PROP-003` 用户请求数量超过风险核准上限时必须拒绝提交为可批准版本，并展示拒绝原因和安全上限；不得静默缩量后自动执行。

`reduce_only = true` 的提案只能收紧或减少已有仓位，不能作为初仓开仓或反向建仓方式。用户请求的最大风险不得高于选定档位上限；Risk Engine 仍可使用更保守上限或拒绝。

`PRD-PROP-004` 风险预检通过后形成不可变提案版本，展示 `Total Capital Snapshot_0`、Trade Funding Envelope、冻结 1R、档位最大计划损失、预计杠杆、组合影响、授权有效期和加仓边界。

`PRD-PROP-005` 手机 PWA 必须以分步向导支持字段完整的复杂提案；无论桌面或手机布局，提交前必须展示相同的最终风险摘要。

### 6.4 初仓审核

`PRD-REVIEW-001` 审核队列必须区分 SYSTEM / MANUAL，并支持按场所、账户、板块、风险档位、有效期和风险状态筛选。

`PRD-REVIEW-002` 审核详情必须同时展示：

- 交易理由、主要反证、信号或人工假设来源。
- 数据新鲜度、可交易资格、价格与流动性状态。
- 入场、失效价、保护计划、用户请求数量、风险核准数量。
- 资金占用、冻结 1R、计划最大损失、预计杠杆；明确提示“资金占用不等于允许亏损”。
- 自动加仓开关、次数、30% / 50% / 100% 候选阶梯、目标杠杆区间和失效条件。
- 审核前后的底层资产、风险簇、板块、场所和组合最坏损失。
- 当前用户标签、作用域、自审判定、所需复核和 MFA 状态。
- 提案版本、剩余有效期和价格偏离状态。

`PRD-REVIEW-003` 审核动作只能作用于当前仍有效的冻结版本。任何事实修改都必须产生新版本；审核页面不能直接改提案后继续批准。

`PRD-REVIEW-004` 根据已确认的 `DEC-PROD-007`，审核者要求修改时不得原地编辑冻结提案：原版本保持不可变，修改后创建新版本并使旧版本失效。并发审核把单个 Reviewer vote 与汇总 ApprovalDecision 分开，审核人数和 quorum 引用 `DEC-PROD-004`；最多只能有一个汇总权威终态，其他客户端必须得到明确最终回执。

`PRD-REVIEW-005` 禁止自审；低、中风险由 1 名独立 Reviewer 审核，高风险由 2 名独立 Reviewer 审核。Risk Engine 拒绝、权限拒绝、数据未知或提案过期时，界面不得展示可绕过的批准路径。

### 6.5 仓位管理与自动加仓

`PRD-POS-001` 仓位页必须把交易所真实仓位、内部预期状态、保护状态、活动订单和对账状态分开显示。

`PRD-POS-002` 每个经济仓位至少展示：原提案、批准者、风险档位、初始与当前风险、初仓、Add 次数、目标杠杆、当前有效杠杆、保护价、未实现盈亏、已实现盈亏、费用、资金费和退出状态。

`PRD-POS-003` 自动加仓开关默认关闭。开启后必须显示已授权次数、已消费次数、剩余次数、当前里程碑、候选是否满足、未执行原因和授权失效时间。

`PRD-POS-004` 每次 Add 必须展示目标仓位、目标差额、风险或流动性安全缩量、真实成交、`target_reached` 和 Add 消费结果。界面不得把 30% / 50% / 100% 描述为必然成交。

`PRD-POS-005` 用户可以立即关闭未来自动加仓。取消、收紧止损、部分减仓、完全退出或降档采用全局、场所、账户、板块、策略、标的和单战役的固定分层作用域并向下继承；任何允许的风险收紧动作都不能隐式扩大其他授权。

`PRD-POS-006` 对系统接入前已经存在、系统外人工创建或恢复时新发现的仓位，产品必须冻结相关账户新增风险并进入人工分类；只有建立接管记录、保护和风险映射后才能管理，且不得自动加仓。

### 6.6 风险中心

`PRD-RISK-001` 风险中心必须展示 NORMAL、NO_PYRAMID、NO_NEW_POSITION、REDUCE_ONLY、KILL_SWITCH 和 UNKNOWN 的当前状态、触发原因、影响范围、自动动作、仍允许动作及恢复条件。

`PRD-RISK-002` 用户必须能同时查看冻结授权基准和包含最新未实现盈亏的动态预算，且能够解释“为什么本次提案或加仓被拒绝/缩小”。

`PRD-RISK-003` 所有拒绝必须提供稳定的原因代码和可理解说明；不得只显示“风控失败”。说明不能泄露密钥、内部防护细节或其他无权查看账户的数据。

`PRD-RISK-004` 风险状态只能自动收紧，不能在指标恢复后自动恢复增险。恢复所需审核方式引用 `DEC-SEC-003` 或 `DEC-GOV-001` 的已批准结果。

### 6.7 异常中心

`PRD-INC-001` 异常中心必须把事故与普通通知分离，并按严重度、影响范围、首次发生、持续时间、当前责任人和处理状态排序。

`PRD-INC-002` 每个异常详情必须展示：事实来源、受影响账户/场所/仓位、系统自动降级、当前允许与禁止动作、关联订单/提案/告警、处置时间线、待办动作和恢复证据。

`PRD-INC-003` 数据未知、订单结果未知、保护缺失、审计不可用、权限漂移和资金在途异常不得用普通黄色提示弱化；产品必须呈现其对新增风险的实际限制。

`PRD-INC-004` 交易所原生保护、预认证的 `reduce-only` 减仓和退出在 UI 或审批服务故障时仍必须继续，这是固定安全原则。`DEC-OPS-004` 只决定不同控制面组件故障时，既有预授权 Add 是否仍可消费；任何风险、授权或账户完整性无法验证时 Add 必须停止。产品不得把“服务不可用”误展示为“仓位已安全”。

### 6.8 资金中心

`PRD-FUND-001` 资金中心必须分开显示长期 Vault 储备、交易所运营资金、Trade Funding Envelope、在途资金、已实现利润和未实现盈亏。

`PRD-FUND-002` `EXCHANGE_ONLY` 与 `EXCHANGE_PLUS_VAULT` 风险计入模式、资金划转开关、自动利润归集和自动运营补充是独立能力，界面不得联动暗示它们同时获得授权。

`PRD-FUND-003` 人工和自动资金划转必须进入独立提案、授权、状态和对账流程；持仓期间从 Vault 救仓必须被拒绝。

`PRD-FUND-004` 每笔划转展示源端预留、在途、目的端确认、实际到账、费用和失败恢复，不允许同一资金同时出现在源端和目的端可用余额中。

### 6.9 审计与复盘

`PRD-AUDIT-001` 用户必须能按提案、仓位、订单、Add、身份、风险决定、资金划转和事故关联查看完整时间线。

`PRD-AUDIT-002` 每个允许或拒绝决定必须可回答：谁、何时、在哪个渠道、以什么身份与作用域、基于什么版本和数据、命中了什么规则、得到什么结果。

`PRD-AUDIT-003` 审计保留、导出、脱敏和删除边界按分级保留研究结果冻结；在证据生效前不得删除交易、资金、授权和安全审计，也不得以普通产品分析日志代替业务审计链。

## 7. Web / PWA 与 Telegram 渠道合同

| 能力 | Web / PWA | Telegram |
| --- | --- | --- |

| 创建 MANUAL 提案 | 支持 | 禁止 |

## 8. 非功能产品要求

### 8.1 安全与权限

- 默认拒绝、显式拒绝优先，前端隐藏按钮不能代替服务端授权。
- 高风险动作必须展示影响摘要并执行规定的 MFA、复核或动作级重新认证。
- 标签或作用域撤销后，旧页面和旧 Telegram 按钮不能继续获得扩权能力。
- 任何密钥、助记词、签名材料或提款凭据不得进入页面、通知、链接和审计明文。

### 8.2 一致性与可恢复性

- 多端必须呈现相同的提案版本、风险状态和最终决定。
- 重复点击、迟到消息、断线重连和页面刷新不能产生重复增险动作。
- 结果未知必须显示 UNKNOWN / RECONCILING，而不是成功或失败猜测。
- 重启恢复先对账；旧提案、旧按钮和旧加仓候选不得自动复活。

### 8.3 可理解性与防误操作

- 风险金额、资金占用、名义仓位、保证金、杠杆和最大计划损失必须使用不同标签。
- 危险操作不能只靠颜色区分，并必须展示作用域和不可逆后果。
- NORMAL、NO_PYRAMID、NO_NEW_POSITION、REDUCE_ONLY、KILL_SWITCH 和 UNKNOWN 必须使用一致的中文名称和视觉语言。
- 日终时区和报告币种由 `DEC-OPS-010` 确定；原始事件时间与原始结算资产仍需保留。

### 8.4 可访问性与响应式

- 全部页面遵循[用户旅程与交互规格的 UI 视觉、主题与可访问性合同](用户旅程与交互规格.md#4-ui-视觉主题与可访问性合同)：采用 thedankoe.com 启发的极简编辑式视觉，并提供信息与能力完全等价的深色、浅色主题。
- 主控制台只保留总览、机会与提案、仓位与订单、风险与异常、资金、审计、设置与权限七个一级导航域。
- 关键审核和风险信息在桌面与手机上不得因折叠而默认隐藏。
- 状态、错误和确认结果需同时使用文字、结构与图形提示，不能只使用颜色。
- 所有核心 Web 操作必须支持完整键盘导航、明确焦点、200% 文本缩放、可读标签和至少 `44×44px` 的交互目标。
- 发布尺寸至少覆盖 `1440×900`、`390×844` 和 `360px` 最小宽度；主题切换不得丢失草稿、筛选、对象版本或业务状态。

### 8.5 服务与通知

- 页面必须显示关键数据新鲜度和服务健康，不得仅显示总系统“在线”。
- 告警送达失败不得被当作风险事件已处理。
- 值守模式由 `DEC-OPS-001`、服务目标由 `DEC-OPS-002`、备用渠道由 `DEC-OPS-006`、事故等级与通知义务由 `DEC-OPS-011` 确定。

## 9. 产品成功指标

成功指标用于判断产品是否安全、可用和可审计，不构成盈利保证：

- 100% 真实增险动作可关联冻结提案、有效审批、风险决定和唯一订单意图。
- 未授权、过期、重复、越作用域或绕过风控的成功增险事件为 0。
- 真实仓位保护状态可确认率达到对应执行认证门；保护未知会自动阻断新增风险。
- SYSTEM 与 MANUAL 提案来源区分准确率 100%。
- 多端对同一业务对象的终态一致率 100%。
- 允许/拒绝动作、Add 消费、异常降级和资金划转均可重放。
- PWA 离线批准、Telegram 过期按钮成功执行、角色撤销后继续扩权事件均为 0。
- 产品可用性、通知延迟、对账时间和告警响应的数值目标在 `DEC-OPS-002` 及运行文档中冻结。

## 10. 完整产品工程完成门与能力激活门

工程完成必须一次性覆盖本文定义的 Binance、Hyperliquid、Web/PWA、Telegram、风险、执行、资金、审计、异常和恢复目标，不得用演示版、局部原型或单场所替代。完成声明至少需要：

1. 全部固定需求可追踪；研究参数具有配置、关闭、验证、证据和失效机制，外部事实缺失的能力安全关闭。
2. 全部用户旅程、七个导航域、权限矩阵、状态和异常路径通过端到端验收；深浅主题、桌面与手机、键盘和 200% 缩放均通过发布硬门。
3. Web / PWA、Telegram、FreqUI 和直接 Freqtrade API 均无法绕过 Trading 新增风险。
4. Binance 与 Hyperliquid 的目标账户、订单、成交、保护、保证金和对账链路完成实现，并能按认证单位独立授予或撤销写权限。
5. 数据陈旧、部分成交、结果未知、重启、权限撤销、通知失败和控制面故障完成演练。
6. 审计、备份、恢复、人工接管和紧急退出路径已验证。
7. Vault 四类能力完整实现且独立授权；自动加仓、自动归集和自动补充保持默认关闭。

工程完成不等于真实资金能力自动激活。每个场所、账户、保证金模式、标的、风险档位、Add 层级和资金动作仍须取得独立证书；未认证能力保持关闭，但不能据此删减完整产品的实现与测试范围。
