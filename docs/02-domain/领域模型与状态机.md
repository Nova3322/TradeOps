## 一、建模原则

1. 提案、审批、授权、风险预留、订单、仓位和资金划转是不同生命周期，不能用一个 `status` 混合表达。
2. Trading 内部意图与交易所真实结果分开；交易所是订单、成交、仓位和余额最终事实源。
3. 每个状态迁移必须有稳定身份、期望版本、actor、原因、时间和不可变事件。
4. 自动动作只能在原授权边界内消费，不能修改或扩大授权。
5. 减险优先于增险；事实未知时不盲重试。
6. 同一金额、风险或订单数量在任一时刻只属于一个互斥状态。
7. 历史状态只追加修正，不原地改写。
8. 每类业务事实只有一个权威命令写入者；审计记录随权威迁移原子追加，但不是第二套可修改写模型。
9. 查询视图、交易所镜像、缓存和报表是可重建投影，只读消费权威事实，不接受业务命令、不自行产生风险决策。

## 二、核心身份

| 身份 | 含义 | 生命周期 |
| --- | --- | --- |
| `instrument_id` | 场所、执行域和具体合约的规范身份 | Catalog 版本内稳定 |
| `underlying_id` | 标准化底层资产 | 分类政策版本内稳定 |
| `proposal_id` | 一份提案族 | 可有多个不可变版本 |
| `proposal_version_id` | 一份冻结或草稿版本 | 永不原地覆盖冻结内容 |
| `authorization_id` | 初仓或 Add 授权包 | 独立于 Approval |
| `campaign_id` | 一份经济仓位/交易战役 | 第一笔初仓成交至完全结算 |
| `add_unit_id` | Add-1/2/3 的一次消费单元 | 最多消费一次 |
| `risk_decision_id` | 一次风险求值快照 | 不可变 |
| `risk_reservation_id` | 一次 Reserved Heat 占用 | 至迁移或释放 |
| `order_intent_id` | Trading 创建的一次性 OrderIntent | 一次执行生命周期 |
| `idempotency_key` | 同一业务命令的重复识别 | 作用域内唯一 |
| `venue_order_id` | 场所订单身份 | venue/execution/account 内唯一 |
| `protection_requirement_id` | Campaign 下版本化保护义务 | 随仓位目标演进 |
| `margin_workflow_id` | 逐仓保证金复合工作流身份 | 工作流内唯一 |
| `capital_transfer_id` | 一次完整资金迁移 | 所有中转沿用同一身份 |
| `reconciliation_run_id` | 一次指定范围对账 | 有明确水位和终态 |

任何渠道不得自行构造可以绕过 Trading 的 venue order 身份；Trading 的 order intent 是业务幂等入口，venue order ID 是外部事实关联。

## 三、最小权威写模型与所有权

### 3.1 TradeProposal

拥有提案来源、创建者、冻结字段、版本、有效期、策略 / 参数版本、Instrument、方向、触发价、委托价、请求数量、`reduce_only`、失效价、用户请求最大风险、档位、Funding Envelope、1R、Add 选择，以及该冻结版本下的 `ReviewerVote` 与唯一 `ApprovalDecision`。用户最大风险不得超过档位上限；`reduce_only` 不得开仓或形成反向仓。

不拥有订单或真实仓位。审核事实没有独立业务根，以 `proposal_version_id` 定位。SYSTEM 提案所有权由 `DEC-PROD-006` 冻结；MANUAL 草稿只能由授权 Proposer 编辑。

### 3.2 ReviewerVote 与 ApprovalDecision

每个 Vote 绑定一个不可变 `proposal_version_id`，保存 Reviewer、权限作用域、MFA、自审、职责分离、选择、原因和决定时间；同一版本只有一个汇总 `ApprovalDecision`。它们是 TradeProposal 的不可变子事实，不建立独立服务、表族或平行状态根。

Reviewer 不能修改被冻结提案；退回修改按 `DEC-PROD-007` 创建新版本，旧版本失效。

### 3.3 TradingAuthorization

包含两类独立授权：

- Initial Order Authorization：短执行窗口、价格偏离、Instrument、账户、方向和数量上限。
- Add Authorization Package：初仓真实成交后激活，绑定 Campaign、方向、次数、目标杠杆区间、触发和最长持续时间。

授权上限不是 Reserved Heat。扩权必须新审批；收紧、撤销和过期立即生效。

### 3.4 Campaign

拥有交易战役身份、初仓、AddUnit、目标仓位、保护要求、退出目标、冻结 1R 和绩效归因。它维护 Trading 对生命周期的预期，但真实数量来自交易所成交和仓位投影。

同一策略、底层资产、方向和授权生命周期构成一份 Campaign。Campaign 始终锁定人工批准的 venue 与 execution domain；跨 venue 的 Instrument 保留独立订单与仓位事实，系统不做隐式换所。

`TargetPositionArbiter` 只是 Campaign 内的纯规则模块：它消费当前真实仓位、保护、硬止损、组合风险、动态去杠杆和趋势退出候选，确定性返回唯一目标仓位、紧迫度与原因。它没有独立 ID、数据表、状态机、服务或密钥，不能调用 OMS 或交易所；仅 Campaign 保存裁决后的目标与原因事实。

### 3.5 RiskDecision 与 RiskLedger

风险域只保存三类权威事实：不可变 `RiskDecisionSnapshot`、追加式 `RiskLedgerEntry/RiskReservation`、版本化 `RiskPolicy/SystemRiskState`。Authorized Capacity 属于 TradingAuthorization；Reserved/Open/Unknown Heat 属于 RiskLedger；作用域用量是账本投影。不建立覆盖全账户和全部 scope 的巨型写模型。风险计算详见《风险引擎规格》。

### 3.6 OrderIntent

OrderIntent 拥有幂等、执行路由、期望数量、`reduce_only`、有效期、场所映射和执行状态；VenueOrder 与 Fill 是其外部事实子记录。Freqtrade 是执行后端，不拥有 TradeProposal、TradingAuthorization、RiskDecision 或 RiskLedger。

### 3.7 Position and Protection Projection

Position Projection 由交易所订单、成交和仓位事实重建；Campaign 拥有保护义务，交易所拥有真实保护订单事实，Protection Projection 只读比较两者并给出覆盖结果。投影不是独立命令写模型，也不能只依赖 Freqtrade 本地数据库。

### 3.8 MarginNormalizationWorkflow

把订单腿、释放保证金、场内预留、保证金腿和最终对账组合成可恢复工作流。它因多个独立外部副作用而保留检查点，但不是独立业务聚合或通用服务。Margin Controller 只执行保证金动作；订单仍由 Freqtrade 执行。

### 3.9 CapitalTransfer

拥有独立资金提案、审批、源端预留、外部 ID、链/网络/Token、费用、在途、目的端确认和结算。不能复用交易授权。其状态及资本互斥分录的唯一权威定义在《[Vault 与 CTO 资金规范](../04-execution/Vault与CTO资金规范.md)》，本文不复制第二份状态表。

### 3.10 RiskControlChangeRequest

这是当前实现中唯一允许从 `NO_PYRAMID` 或 `REDUCE_ONLY` 恢复到新 `NORMAL` 政策、并可选择重新开启 AUTO_ADD 的窄型恢复请求；当政策已经是 `NORMAL` 但 AUTO_ADD 仍关闭时，也可只申请恢复该 Gate。它冻结 requester、原因、来源 RiskPolicy ID/version/revision、AUTO_ADD 状态/version、运行时发现的受控 scope、是否要求 LIVE scope、15 分钟冷却、24 小时有效期、对象 version 与 resulting policy；状态仅为 `PENDING_REVIEW / APPROVED / REJECTED / EXPIRED / EXECUTED`。

`Approval` 复用现有表，并以数据库 exactly-one parent 约束保证每一行只属于 TradeProposal、TransferProposal 或 RiskControlChangeRequest 之一；同一恢复请求和 Reviewer 只有一票。恢复必须由两名不同 HUMAN Reviewer 批准，请求者不能自审。批准和执行分别要求绑定 `risk.restore.review` / `risk.restore.execute`、user、request ID 和当前 request version 的短期 action grant。

## 四、跨模型不变量

- 没有有效 Frozen Proposal、Approval、Initial Authorization 和 Risk Reservation，不得发送初仓。
- Approval 只对精确 `proposal_version_id` 有效；任何风险/执行字段变化产生新版本。
- 一个 Initial Authorization 最多形成一个初仓执行结果。
- 一个 AddUnit 最多消费一次；任何非零真实成交即消费，零成交不消费，Unknown 冻结。
- 一个受管账户同一时刻只有一个活动订单发送者。
- 初仓 `reduce_only=false`；保护、减仓和退出 `reduce_only=true`。
- 仓位事实未知、保护不足或风险账本不守恒时，不得增险。
- 订单发送不释放 Reserved Heat；只有场所对账决定转 Open、Unknown 或释放。
- Campaign 完全退出前，已有仓位持续受管理，不因白名单或新信号变化被遗忘。
- 活动 Campaign 不得从 Vault 取得救援资金。
- 同一资本同一时刻只属于源端、预留、在途或目的端。
- 渠道、管理员或任何辅助建议源不能覆盖 Risk Engine 拒绝；辅助建议源不持密钥、不签名且不发送订单。
- 风险收紧、TradingAuthorization 签发和风险恢复使用同一风险容量锁序；暂停使旧授权失效，关闭 AUTO_ADD 永久标记 `add_revoked_at`。恢复只创建新政策/新 Gate version，不能复活旧 Proposal、Authorization 或 AddUnit。

## 五、Proposal 状态机

| 状态 | 含义 | 允许迁移 |
| --- | --- | --- |
| `DRAFT` | 可编辑草稿，尚未形成可审核版本 | PRECHECKED、PRECHECK_REJECTED、CANCELLED |
| `PRECHECK_REJECTED` | 字段、Catalog、数据或风险预检不合格 | 回到新 DRAFT 版本或结束 |
| `PRECHECKED` | 预检通过，等待冻结 | FROZEN、CANCELLED |
| `FROZEN` | 字段、版本和风险摘要不可变 | 进入 Approval；SUPERSEDED、EXPIRED、CANCELLED |
| `SUPERSEDED` | 被新版本替代 | 终态 |
| `EXPIRED` | 超过提案有效期 | 终态 |
| `CANCELLED` | 在未执行前合法撤回 | 终态 |

批准或拒绝由冻结 Proposal 版本下的 `ReviewerVote` 与唯一 `ApprovalDecision` 表达，不混入 Proposal 生命周期状态。冻结提案不能原地编辑。

## 六、审核事实与汇总决定

| 状态 | 含义 | 迁移条件 |
| --- | --- | --- |
| `PENDING` | 冻结版本等待合格 Reviewer | 身份、权限、MFA 和有效期持续校验 |
| `APPROVED` | 审核通过，允许尝试签发有限授权 | Risk Engine 仍可拒绝；不是成交保证 |
| `REJECTED` | 审核明确拒绝 | 终态；修改需新提案版本 |
| `RETURNED` | 要求修改 | 原版本失效，新版本重新预检 |
| `EXPIRED` | 决定前过期或版本失效 | 终态 |
| `ABANDONED` | 主动放弃 | 终态 |

并发审核必须把每个 `ReviewerVote` 与汇总 `ApprovalDecision` 分开。服务端原子记录每个仍有效的 vote，再按已确认的 quorum、拒绝和退回政策聚合出唯一权威终态；第一张赞成票在需要多人复核时不是 `APPROVED`。终态之后的迟到动作只返回已处理事实，不设渠道优先级，也不能生成第二份授权。自审、审核人数 / quorum 和 Telegram step-up 分别由 `DEC-PROD-004`、`DEC-PROD-005`、`DEC-SEC-001` 冻结。

## 七、TradingAuthorization 状态机

### 7.1 Initial Authorization

| 状态 | 含义 |
| --- | --- |
| `ACTIVE` | 已签发且仍在冻结边界内可消费 |
| `CONSUMED` | 出现非零真实初仓成交 |
| `EXPIRED` | 执行窗口或价格边界过期 |
| `REVOKED` | 人工或系统收紧撤销 |
| `INVALIDATED` | Instrument、账户、方向、版本或事实变化 |

Risk Reservation 与 OrderIntent 表达预留和发送，不复制成授权状态。发送结果 Unknown 时授权保持锁定，直到关联 OrderIntent 对账，不能重新消费。

### 7.2 Add Authorization Package

| 状态 | 含义 |
| --- | --- |
| `DORMANT` | 初仓尚未出现真实成交 |
| `ACTIVE` | 初仓成交且包仍有效 |
| `EXHAUSTED` | 所有允许 AddUnit 已消费或失效 |
| `REVOKED` | 用户关闭自动加仓或系统撤销 |
| `EXPIRED` | 最长持续时间到期 |
| `INVALIDATED` | Campaign、方向、保护、版本或事实冲突 |

NO_PYRAMID 使全部未消费 AddUnit 进入 `INVALIDATED`，剩余 Add 授权永久失效；恢复到 NORMAL 不会复活。用户主动关闭自动加仓时，包进入 `REVOKED` 且全部未消费单元失效。任何重新开启都必须新建提案版本并重新人工签发有限授权。

## 八、AddUnit 最小状态机

| 状态 | 含义 | 迁移 |
| --- | --- | --- |
| `AVAILABLE` | 单元存在且未消费；是否满足里程碑、回调、趋势、杠杆与风险门在每次评估时计算 | CLAIMED、INVALIDATED、EXPIRED |
| `CLAIMED` | 已原子绑定 Risk Reservation 与唯一 OrderIntent，不得再次领取 | CONSUMED、AVAILABLE（仅终态确认零成交且授权仍有效）、INVALIDATED、EXPIRED |
| `CONSUMED` | 已出现任意非零真实成交 | 终态 |
| `EXPIRED` / `INVALIDATED` | 机会或授权失效 | 终态 |

里程碑、回调、趋势、杠杆和风险候选条件是即时派生判定，不持久化为另一套生命周期状态。OrderIntent 的 Unknown 使已 CLAIMED 单元保持锁定，直到事实证明零成交或出现真实成交。不得为追赶 `L_target` 在同一 CONSUMED AddUnit 补单。若治理改变该语义，必须同步修改上位策略合同、风险账本、OMS 幂等和测试证书。

## 九、OrderIntent 权威引用

OrderIntent 的唯一身份是 `order_intent_id`，其详细状态、迁移与场所状态映射以《[OMS、Freqtrade 与 VenueAdapter 执行规范](../04-execution/OMS-Freqtrade-VenueAdapter执行规范.md)》第 5 节为唯一权威。本文不复制第二份状态表，只冻结：

- OrderIntent 与 Reserved Heat 原子建立；场所订单、成交和仓位是外部权威事实。
- 任何终态不能回到可发送态；重试只能查询或安全重送同一幂等身份，不得创建语义相同的新 OrderIntent。
- 结果 Unknown 在交易所事实证明零成交或真实结果前，不得释放风险或重复发送。

## 十、Campaign 与保护事实

### 10.1 Campaign 主状态

| 状态 | 含义 |
| --- | --- |
| `PENDING_ENTRY` | 已有授权但无真实仓位 |
| `OPEN` | 存在真实净仓位，持续管理保护、Add、去杠杆与退出目标 |
| `CLOSING` | 目标仓位为零，仍有退出、订单、费用或风险待对账 |
| `CLOSED` | 零仓、零未知订单、风险和财务完成对账 |

是否正在开仓/退出由活动 OrderIntent 派生；是否足额保护由 Protection Coverage 派生；Add 是否允许由 TradingAuthorization、AddUnit 与风险状态派生；对账阶段由 ReconciliationRun 表达。`FROZEN` 与 `FACTS_UNKNOWN` 是覆盖状态，不替代主状态，覆盖期间只允许对账、保护、减仓和退出。

### 10.2 Protection 状态

| 状态 | 含义 |
| --- | --- |
| `MISSING` | 真实仓位存在但没有足额有效保护 |
| `PENDING` | 正在创建/替换保护 |
| `ACTIVE` | 有效保护足额覆盖真实仓位 |
| `TRIGGERED` | 保护已触发，等待成交与对账 |
| `UNKNOWN` | 场所保护事实不能确定 |
| `CLOSED` | 仓位退出且保护清理完成 |

`coverage_ratio`、`health_reason` 与保护要求版本保存完整事实，页面可派生“部分覆盖/已降级/失败”。只要不是足额 `ACTIVE` 就禁止 Add；无法在合同窗口恢复时受控减仓或退出。逐场所保护能力由 `DEC-EXEC-004` 冻结。

## 十一、风险状态机

系统状态按严格程度为：

`NORMAL → NO_PYRAMID → NO_NEW_POSITION → REDUCE_ONLY → KILL_SWITCH`

同一风险事件中只允许向右自动收紧。恢复不是反向自动迁移，而是完成对账、根因修复、滞回、冷却和人工逐级解锁后产生新的恢复事件。

当前实现的恢复状态机为：

`PENDING_REVIEW → APPROVED → EXECUTED`，以及 `PENDING_REVIEW → REJECTED`、未在 24 小时内完成时转为/按 `EXPIRED` 拒绝。只有两名不同 HUMAN Reviewer 的批准票才能进入 `APPROVED`；每张批准票和执行都必须携带匹配当前对象 version 的动作级 step-up。最近一次相关收紧后至少冷却 15 分钟。

执行时重新锁定风险容量并比较来源 Policy/Gate version 与完整 scope，再重新读取权益、仓位、保护、订单、Unknown 和机器对账事实。生产环境若未从运行配置发现至少一个 LIVE scope，返回 `LIVE_SCOPE_CONFIGURATION_REQUIRED` 并保持关闭；任何 blocker、版本/scope 漂移均拒绝。`KILL_SWITCH` 不进入该常规恢复状态机，只能按事故恢复程序人工处置。

恢复到 NORMAL 不改变过去的撤销事实。旧 TradingAuthorization、旧 AddUnit 和旧订单意图永不重新武装；已发送或 Unknown Add 的迟到正成交仍消费收紧时保留的责任槽，不能因 `add_revoked_at` 被忽略。

任一作用域可以拥有更严格状态；有效状态取全局、venue、account、sector、strategy、instrument 和 Campaign 中最严格者。暂停/紧急作用域由 `DEC-PROD-008` 冻结。

## 十二、MarginNormalizationWorkflow 状态机

每个复合意图必须冻结 `normalization_type`：

- `REMOVE_EXCESS`：逐仓净增仓、成交和保护完成对账后，只对场所原生事实确认的 `max_removable_margin` 预留可移除容量；来源是该 isolated position，目的是同一场所已对账 free collateral。
- `READD_RELEASED`：`reduce-only` 减仓与剩余保护完成对账后，只预留“本次减仓实际释放额”中合同允许的部分；来源是同一场所已预留 free collateral，目的是同一剩余 isolated position。

两种类型都是净仓位方向中性的保证金动作，不得改变已对账净数量、放宽止损或调用 Vault。

| 状态 | 含义 |
| --- | --- |
| `PLANNED` | 冻结原仓、目标仓位、缓冲与最坏成本 |
| `FENCED` | 对账户/抵押池取得独占执行 fencing |
| `POSITION_LEG_RESERVED` | 仓位腿风险与 OrderIntent 已预留 |
| `POSITION_LEG_SENT` | Freqtrade 执行净仓位变化 |
| `POSITION_RECONCILED` | 实际数量、保护与场所原生保证金事实已确认 |
| `MARGIN_RESERVED` | `REMOVE_EXCESS` 的可移除容量，或 `READD_RELEASED` 的本次实际释放额，已为本意图独占预留 |
| `MARGIN_LEG_SENT` | Margin Controller 已发送场内动作 |
| `SETTLED` | 仓位、保证金和保护均完成对账 |
| `FAILED_SAFE` | 保证金腿失败的安全终态：`REMOVE_EXCESS` 保留已保护的原净增仓与更多保证金；`READD_RELEASED` 保留较小净仓并继续减仓 / 退出判定 |
| `UNKNOWN` | 任一腿结果不明，停止增险 |
| `FAILED` | 未产生外部影响且已证明安全失败 |

UNKNOWN 不得通过反向开仓恢复目标。逐仓参数和证书由 `DEC-EXEC-006` 冻结。

## 十三、CapitalTransfer 权威引用

CapitalTransfer 的名称、状态、迁移、超时 / reorg 行为和互斥资本分录，以《[Vault 与 CTO 资金规范](../04-execution/Vault与CTO资金规范.md)》第 7 节为唯一权威。本领域文档只冻结以下不变量，不维护并行状态机：

- 同一资本单位同一时刻只属于源端可用、源端预留、在途或目的端已结算之一。
- 未结算与 Unknown 资金不计入交易可用资本，不得被二次划转。
- 交易授权不能替代 Capital Transfer Authorization；CTO 是唯一业务写入者，Treasury 视图和账本报表均为可重建投影。

## 十四、ReconciliationRun 作业状态

| 状态 | 含义 |
| --- | --- |
| `RUNNING` | 按 phase 读取并比较 Trading、Freqtrade、venue 或链上事实；必要时追加修正分录 |
| `UNKNOWN` | 查询窗口、分页或事实不完整 |
| `SUCCEEDED` | 指定水位内差异全部解释 |
| `FAILED` | 无法完成；新增风险保持关闭 |

`COLLECTING/COMPARING/ADJUSTING` 是 `phase`，差异保存为不可变 Finding，不是第二套运行状态。重启、私有流重连、部分成交、Unknown、Campaign 关闭和资金迁移都必须触发相应对账。

## 十五、冲突优先级

多个来源同时提出仓位目标时，Campaign 内的纯规则模块 `TargetPositionArbiter` 按以下原则仲裁：

1. KILL_SWITCH / 紧急退出。
2. 硬保护止损。
3. REDUCE_ONLY / 组合风险减仓。
4. 动态去杠杆。
5. 趋势退出或普通减仓。
6. 初仓或 Add。

最终只发送最小目标剩余仓位；不得同时发送相互抵消的增仓和减仓订单。订单优先级、场所保护和取消替换仍需在执行附件认证。

## 十六、时间、版本与并发

- 所有命令携带 `idempotency_key`、`expected_version`、actor、channel 和 correlation ID。
- 冻结提案、审批、授权和 OrderIntent 均有 `valid_from`、`valid_until` 与价格偏离边界。
- 时间判断使用服务器认证时钟；行情同时保存 event time 和 observed time。
- 一个权威写模型的状态迁移按递增版本串行；版本冲突必须重读并重算。
- 跨模型增险使用 Risk Reservation 与 OrderIntent 的原子事务边界。
- 事件至少一次投递，消费者以 event/object sequence 去重。
- 任何旧版本消息都不能复活过期授权、AddUnit 或 OrderIntent。

一致性候选由 `DEC-ARCH-002` 冻结，API/Event 细节见《API事件数据与审计契约》。

## 十七、状态机验收门

详细设计必须为每条迁移列出前置条件、actor、权限、原子写入、事件、超时、补偿、告警和测试证据，并证明：

- Proposal 修改永远生成新版本，旧 Approval 不可复用。
- 初仓授权、Add 包与 AddUnit 不会重复消费。
- 部分成交、结果 Unknown、撤单竞争和重启不会重复下单或提前释放风险。
- 保护覆盖按真实仓位更新，无未保护成交被误记为正常。
- Campaign 只有在零仓、零未知订单和完成财务/风险对账后关闭。
- 风险状态不会自动放宽或复活旧授权。
- MarginNormalizationWorkflow 失败保持较小风险终态。
- Capital Transfer 在所有失败路径保持源/在途/目的互斥。
- Web、PWA、Telegram 和内部重试对同一命令得到同一业务结果。

外部事实或研究证据尚未取得时使用对应 `DEC-*` 的安全默认值；状态机实现不得自行填入生产参数。
