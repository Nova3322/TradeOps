## 一、架构目标

系统必须把“发现机会、人工决定入场、程序管理风险、执行订单、管理资金”拆成可验证的责任边界，并保证：

- Trading 是受管交易账户的唯一日常订单发送者。
- 所有初仓必须有冻结提案、人工批准、实时 Risk Engine 复核和原子风险预留。
- 自动加仓只消费原始预授权，不能自行扩大风险。
- 止损、减仓和退出不依赖 Web、Telegram、Perptape 或任何辅助建议源可用。
- Freqtrade 只作为 Binance、Hyperliquid、OKX 与 Bybit 的受控执行后端，不成为决策、审批或风险中心；每个 Worker 绑定唯一 Team/Account/Venue。
- 交易所私有事实决定订单、成交、仓位和余额；链上事实决定 Vault 余额、权限和转账。
- 批准、授权、OrderIntent、风险账本、状态迁移和资本互斥账本是 Trading 不可丢失的内部事实。
- 单所、单 worker、通知、行情或资金服务故障不会无边界扩散。

## 二、完整目标架构

完整产品范围一次定义：Binance、Hyperliquid、Web / PWA、Telegram、风险、执行和资金闭环同属目标。目标逻辑形态为：

- Trading 核心控制面采用模块化单体，保持 Proposal、Approval、Authorization、Risk、OMS 与状态机的强事务边界。
- Freqtrade worker、VenueAdapter 执行单元、Margin Controller、Capital Transfer Orchestrator、通知和数据采集按凭据与故障域隔离。
- 关系型事实库保存当前状态，不可变业务账本保存历史，transactional outbox/inbox 保证状态与事件一致；Redis 仅用于可重建缓存。
- 每个 venue × execution domain × account × margin mode × collateral pool 使用独立执行证书和订单幂等空间。

上述逻辑边界是完整目标；以下实现与生产运行事实仍需证据确认：

- 服务拆分由 `DEC-ARCH-001` 确认。
- 关系库、不可变账本、outbox/inbox 与完整事件溯源的选择由 `DEC-ARCH-002` 确认。
- 技术栈、云/区域、HA 和生产部署由 `DEC-ARCH-003` 确认。
- Trading 与 Freqtrade 的受控接口由 `DEC-EXEC-001` 确认。

这些研究项不改变产品目标，只决定具体实现与某项能力能否激活。没有当前证据的能力保持关闭，不能宣称生产拓扑或现实交易能力已认证。

## 三、逻辑分层

### 3.1 发现与市场层

**Perptape** 负责公开市场扫描、突破候选、成交量、持仓量及数据健康，不保存交易凭据，不读取私有仓位，不审批或下单。

**Trading Market Data / Instrument Catalog** 独立从目标场所取得 Instrument、合约规则、执行价格、交易时段和数据健康。Perptape 候选必须经过 Trading 的 Catalog 与实时市场复核，不能直接成为订单。

### 3.2 交互与身份层

**Web / PWA** 是主控制台，承载人工提案、审核、风险、仓位、资金、异常和审计。

**Trading Telegram Bot** 只承载通知和受限意图。它不直连 Freqtrade；批准、拒绝、关闭 Add、暂停和紧急减仓都回到 Trading 的身份、权限、幂等和风险边界。

**Identity and Authorization** 统一处理多标签 RBAC、ABAC、MFA、自审、职责分离和会话撤权。所有渠道使用同一授权结果。

### 3.3 Trading 控制面

| 模块 | 责任 | 明确不负责 |
| --- | --- | --- |
| Proposal | 接收 SYSTEM/MANUAL 草稿、版本化、冻结和过期 | 不下单、不批准自己 |
| Approval | 记录审核、MFA、自审和职责分离结果 | 不覆盖 Risk Engine |
| Authorization | 签发初仓和 Add 两种生命周期不同的有限授权 | 不产生无限期交易权 |
| Risk Engine | 定仓、分层预算、Heat、动态状态和原子预留 | 不预测方向、不持密钥 |
| Campaign Manager（内含 `TargetPositionArbiter`） | 管理 Campaign、Add、保护、动态去杠杆和退出目标；以无状态纯规则合并目标仓位 | `TargetPositionArbiter` 不是独立服务、表或领域实体；Campaign 不直接调用交易所 |
| OMS | 创建一次性 OrderIntent、幂等、路由、状态和对账 | 不自行换所或放宽价格 |
| Reconciler | 对比 Trading、Freqtrade 和场所私有事实 | 不用本地投影覆盖场所 |
| Audit/Ledger | 保存不可变审批、风险、订单、资本和状态证据 | 不作为可丢缓存 |
| Notification | Web/Push/Telegram 通知、送达与升级 | 通知送达不等于动作成功 |

### 3.4 执行面

**VenueAdapter** 归一化 Instrument、订单、错误、能力和对账边界。Binance、Hyperliquid Core 与每个 HIP-3 DEX 分别认证。

**Freqtrade worker** 只消费 Trading 已批准、已预留的一次性 OrderIntent，负责发送交易订单并回传状态。其 ROI、追踪止损、自动仓位调整、强制入场、内置 Telegram 和 FreqUI 增险能力必须关闭或在架构上不可达。

**Margin Controller** 使用场所原生能力执行增加/移除保证金和 normalization；它不能发送交易订单、不能调用 Vault，也不能在订单失败后反向增仓。

每个受管账户同一时刻只能有一个活动订单发送者。备用 worker、leader lease 与 fencing 由 `DEC-OPS-009` 冻结；未证明防双主前不得自动接管。

### 3.5 资金面

**Capital Transfer Orchestrator（CTO）** 只消费独立 Capital Transfer Authorization，管理源端、预留、在途、目的端确认和结算。

**RiskControl / NoTilt Vault** 是长期资金闸门，不管理分钟级仓位，不救援活动仓位。Vault owner、funding wallet、交易密钥与 OMS 完全分离。

Vault 完整目标能力、链资产、签名、运营资金和人工审批由 `DEC-FUND-001` 至 `DEC-FUND-009` 冻结。

## 四、事实源与存储边界

| 事实 | 权威来源 | 可重建投影 |
| --- | --- | --- |
| 公开候选与指标 | Perptape / 认证公开行情 | Trading 候选视图 |
| Instrument 身份与可交易资格 | Trading Instrument Catalog | 搜索和 UI 索引 |
| 交易价格、规则、订单、成交、仓位、余额 | 目标交易所接口 | Trading/Freqtrade 镜像 |
| 提案、审批、授权、风险预留、OrderIntent | Trading 单一事务写模型（同事务追加审计证据） | API 查询视图 |
| worker 执行进度 | Freqtrade，经 Trading 对账 | 运营面板 |
| Vault 余额、权限、请求、链上转账 | 链上事实 | CTO/Vault 投影 |
| 在途资本归属 | CTO 的 CapitalTransfer 单一写模型（同事务追加互斥资本分录） | Treasury 视图 |
| 通知送达/确认 | 通知供应商与 Trading 记录 | 通知中心 |

Redis、浏览器缓存、PWA 离线缓存、搜索索引、报表库和 Freqtrade 数据库都不能覆盖上述权威事实。每类内部事实只有一个命令写入者；不可变审计记录与权威迁移原子落库，但不构成第二套可修改写模型。所有查询视图、镜像、缓存和报表均为可重建投影，只能接受权威事实流，不接受业务命令或产生风险决策。

推荐候选的数据组件：

- 关系型主事实库。
- 只追加的审计、风险、订单和资本 Ledger。
- transactional outbox 与消费者 inbox。
- 可重建的查询投影和缓存。
- 与主库、主机不同故障域的持久备份。

最终选择受 `DEC-ARCH-002`、`DEC-OPS-003` 和 `DEC-GOV-002` 约束。

## 五、关键流程边界

### 5.1 初仓

SYSTEM 候选或 MANUAL 草稿进入 Trading，经 Catalog、数据健康、风险定仓、冻结、人工审核和下单前复核。Risk Engine 与 OMS 原子保存 Reserved Heat、OrderIntent 和待发送事件后，VenueAdapter 才能交给对应 Freqtrade worker。

任何价格、账户、Instrument、授权、规则或风险事实过期都会拒绝或使提案失效。批准后不得自动换所、追价或拆到另一执行域。

### 5.2 自动 Add

Campaign Manager 只在相应 AddUnit 已预授权、里程碑和回调合格、`L_effective < L_min`、保护存在、Risk Engine 通过时，生成到 `L_target` 的安全差额。

非零真实成交消费一次 AddUnit；零成交不消费；Unknown 冻结本级和后续增险。任何时候都不能从 Vault 向活动仓补资。

### 5.3 减仓与退出

Campaign 内的纯规则模块 `TargetPositionArbiter` 合并所有退出来源，只返回更小的单一目标仓位、紧迫度和原因，不持久化状态也不发送订单。OMS 强制 `reduce_only`；已有仓位的保护、减仓和退出不依赖交互层、Perptape、辅助建议源或新增风险审批服务。

系统整体不可用时，break-glass 只允许在交易所维护保护、减仓或退出；恢复后必须冻结并对账，政策由 `DEC-SEC-003` 和 `DEC-EXEC-003` 冻结。

### 5.4 资金划转

交易策略和 Freqtrade 不处理提款。CTO 的资金授权、签名和账本与交易授权分离；任何金额同一时刻只属于源端、在途或目的端。

初仓若依赖 Vault 资金，必须在订单发送前完成目的端到账和重新风险复核。活动仓、挂单、Unknown 或清算压力存在时拒绝 Vault → 场所补充。

### 5.5 重启恢复

所有控制面和 worker 重启先进入只对账模式。交易所重建当前仓位、订单和可查询成交；Trading 主库恢复审批、授权、OrderIntent、Risk/Capital Ledger 和状态迁移。旧提案、旧 Add 候选和旧 OrderIntent 不得在重启后自动重放。

## 六、部署与故障域

推荐至少隔离以下部署单元：

1. Web/PWA 静态前端和 API 入口。
2. Trading 核心控制面。
3. Market ingestion 与 Catalog。
4. Binance cross worker/adapter；如启用 isolated，使用另一独立单元。
5. Hyperliquid 各 account/margin/collateral 执行单元；HIP-3 继续按证书隔离。
6. Margin Controller，按场所和凭据隔离。
7. CTO 与 funding signer。
8. 通知服务。
9. 主事实库、备份和可重建缓存。

逻辑隔离不能只靠进程命名：账户、凭据、数据库、幂等空间、日志、限速、健康状态和执行证书都要与故障域一致。

账户拓扑由 `DEC-EXEC-002` 冻结。安全默认是不与人工、第二 bot 或研究环境共享受管杠杆账户。

## 七、信任边界与秘密

- Perptape、策略和任何辅助建议源不得持有交易或资金密钥，不得签名、下单或覆盖 Risk Engine。
- Risk Engine 没有交易或资金秘密。
- Freqtrade/Venue 执行单元只持对应账户的交易权限，禁止提款。
- Margin Controller 只持场所保证金能力，不持 Vault owner。
- CTO/funding signer 不能发送交易订单；owner 不进入自动服务。
- 前端、PWA 和 Telegram 不持任何交易或资金密钥。
- 数据库、消息和内部调用使用服务身份、最小权限与不可伪造审计。

身份/MFA、秘密托管、break-glass、Telegram 绑定和 PWA 设备政策分别由 `DEC-SEC-001` 至 `DEC-SEC-005` 冻结。

## 八、降级矩阵

| 故障 | 新仓/Add | 已有仓管理 | 资金动作 |
| --- | --- | --- | --- |
| Perptape 不可用 | 停止 SYSTEM 候选；MANUAL 仍需独立数据门 | 交易所数据+原生保护继续 | 不受影响 |
| 单所公开行情异常 | 冻结该执行域 | 对账、保护、减仓、退出 | 该所新划转冻结 |
| 单所私有事实未知 | 按 `DEC-OPS-005` 全局关闭新增风险 | 保守 Unknown Heat、只减仓/退出 | 相关划转冻结 |
| Risk Engine 不可用 | 全停 | 预认证保护/减仓/退出继续 | 新资金授权停止 |
| 主库/审计不可写 | 按 `DEC-OPS-007` 全停 | 安全路径继续并保留证据 | 新划转停止 |
| 单 Freqtrade worker 不可用 | 冻结该单元 | 确认原生保护，不让健康 worker 接管未知单 | 不受影响 |
| Web/Telegram 不可用 | 人工新仓受限 | 自动保护、减仓、退出继续 | 人工资金操作受限 |
| CTO/Vault/RPC 异常 | 不以预期资金开仓 | 不能提款救仓 | 停止新划转并对账 |
| Redis/查询投影丢失 | 预热完成前停新增风险 | 主事实仍可恢复安全路径 | 主账本不受影响 |

控制面失效时既有 Add 是否继续由 `DEC-OPS-004` 冻结；任何 Risk、授权、账户或保护完整性不可验证时必须停止 Add。

## 九、环境与发布拓扑

研究、历史回测、影子、模拟/测试网和生产必须使用不同账户、凭据、数据库、Bot 配置、通知路由和资金地址。

能力认证与激活不能只复制配置：

- 每个环境绑定代码、Schema、策略、风险、Catalog、Adapter、Freqtrade 和执行证书版本。
- 生产只接受已批准制品和参数登记。
- Schema/Event/API 变更必须兼容、可迁移、可回滚。
- 影子结果不能获得真实密钥；模拟成功不自动继承生产证书。
- 场所或依赖升级使受影响执行证书失效，需重新重放和影子验证。

发布审批按 `DEC-GOV-001`；生产技术和区域按 `DEC-ARCH-003`；RTO/RPO 按 `DEC-OPS-003`。

## 十、可观测性和运行责任

每个请求、裁决、意图、订单、成交、保护、Add、状态迁移和资金动作必须有 correlation/causation 身份，能够从用户动作追到交易所或链上结果。

必须监测：

- 市场与私有账户数据新鲜度。
- 风险求值、预留和作用域使用率。
- OMS/Freqtrade/Venue 延迟、部分成交、Unknown 和对账。
- 保护覆盖、清算缓冲和 Margin Controller 状态。
- 账本/outbox/inbox 积压、主库和备份健康。
- CTO 源端、在途、目的端、签名和链确认。
- 身份、MFA、拒绝、自审、break-glass 和旁路尝试。

值守、SLO、RTO/RPO、备用告警、对账和事故等级分别由 `DEC-OPS-001`、`DEC-OPS-002`、`DEC-OPS-003`、`DEC-OPS-006`、`DEC-OPS-008`、`DEC-OPS-011` 冻结。

## 十一、架构验收门

进入影子执行前必须证明：

- UI、Telegram、FreqUI、策略和任何辅助建议源均无法绕过 Trading 直接增险。
- 风险预留、OrderIntent 与 outbox 在选定一致性模型中原子成立。
- 事件重复、乱序和重启不会产生第二个订单或第二次资本移动。
- 每个账户只有一个活动发送者，防双主失败时停止新增风险。
- Freqtrade 自有策略、ROI、追踪止损和仓位调整不会与 Trading 竞争。
- 交易所/链上事实可以重建投影，但内部批准、意图、账本和迁移可从备份恢复。
- 单执行域、主库、Redis、通知和 CTO 故障分别触发预期降级。

任何范围激活真实资金前，还必须关闭 `DEC-ARCH-001` 至 `DEC-ARCH-003`、`DEC-EXEC-001`、`DEC-EXEC-002`、`DEC-EXEC-004` 至 `DEC-EXEC-006`、`DEC-SEC-001` 至 `DEC-SEC-003`，以及该认证范围适用的 `DEC-OPS-001` 至 `DEC-OPS-011`，并完成故障注入、备份恢复、防双主和 break-glass 演练。完整产品目标保持不变，证据门只决定对应能力能否激活。
