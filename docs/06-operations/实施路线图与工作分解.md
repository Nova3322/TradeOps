# 实施路线图与工作分解

> 状态：BASELINE
> 日期：2026-07-31
> 当前节点：M10 两场所最小 LIVE 闭环已验证，持续运行和其他危险能力保持关闭

## 1. 目标与非目标

完整愿景包含 Binance、Hyperliquid、Web/PWA、Telegram、自动 Add、Margin、Vault/CTO、报表和生产运维。工程不要求这些能力同时交付，而是按可运行端到端用户流程逐步完成；任何未完成能力都必须保持关闭。

本路线不以 WP 数量、迁移数量、表数量、测试数量或代码行数衡量进度。一个里程碑只有在用户能完成真实流程、拒绝路径有效、重启可恢复且证据可复查时才算完成。

## 2. 当前基线

当前已经具备：

- PostgreSQL、事务、健康检查、必要指标和安全日志；
- 内部五角色 RBAC 与账户/场所作用域；
- Proposal、Approval、RiskDecision、TradingAuthorization；
- Campaign、RiskReservation、OrderIntent、幂等回执；
- Instrument、场所订单/成交/仓位/保护/权益/资金费事实；
- 目标仓位纯仲裁、对账、sender fencing、Capability Gate、审计和 PnL；
- 不连接真实交易所的 SHADOW 端到端自动化测试。

当前已有 M1-M9 业务/运行基线、Web/PWA 静态控制台、默认关闭的真实 Telegram 私聊、AUTO_ADD/减仓/退出入口，以及 Binance Unified Account 和 Hyperliquid Core 的窄型只读/TESTNET/LIVE 合同。两场所已完成一次用户授权的小额主网开仓到退出实证；尚无生产部署、常驻 worker、托管 IdP、Secret Manager、HIP-3、Margin 或真实 Vault/CTO。

## 3. 端到端里程碑

### M1：内部提案到授权（完成）

用户流程：Proposer 创建并提交提案 → Reviewer 审核 → Operator 查看风险决定与短期授权。

交付内容：

- 内部认证和最小业务 API；
- Proposal/Approval/Risk/Authorization 页面；
- 自审、双人审批、作用域、过期和风险拒绝的可见回执；
- 用户可查询的基本审计。

退出标准：浏览器可完成完整流程；没有订单发送入口；默认 Gate 未改变。

### M2：SHADOW Campaign 运营（完成）

用户流程：Operator 由授权创建风险预留和 SHADOW OrderIntent → 录入模拟场所事实 → 查看 Campaign、目标、保护、PnL 与对账 → 处理 Unknown。

交付内容：

- Campaign/OrderIntent/场所事实/对账业务 API 与页面；
- reduce-only 目标差额流程；
- sender lease 接管、人工处理和异常指标；
- 进程重启后的状态恢复。

退出标准：整个 SHADOW 流程可操作、可拒绝、可恢复；没有真实网络副作用。

### M3：单场所只读事实（完成）

用户流程：Operator 查看一个明确测试作用域的真实订单、成交、仓位、保护和权益，并与内部预期对账。

交付内容：

- 一个只读 VenueAdapter；
- 新鲜度、去重、Unknown 和故障降级；
- 恢复发送前对账演练；
- 只针对该场所实现，不先建设通用认证平台。

退出标准：读取失败时 fail closed；事实可追踪；读取本身不授权发送。Binance Unified Account 与 Hyperliquid 默认主账户均已完成真实读取实证。

### M4/M10：Binance 受控发送（完成）

用户流程：在用户另行批准的非生产作用域内，Operator 从 Proposal 发出一笔订单，处理部分成交/Unknown，确认保护并退出。

交付内容：

- client order identity、真实 VenueAdapter 和 fencing 强制门；
- 订单、成交、保护、撤销、Unknown、恢复和 PnL；
- 对应 Capability Gate 的明确操作和审计；
- 场所规则与失败路径验证。

退出标准：单笔初仓到退出可恢复。2026-07-31 已完成最小 LIVE 开仓、保护、幂等、fencing、退出、对账与清仓；结果不自动授权持续运行、AUTO_ADD 或资金动作。

### M5/M10：第二场所与受控程序接管（完成）

用户流程：Trading 在独立 Hyperliquid Core scope 中创建并控制显式价格 IOC、保护、Unknown 恢复、对账和退出，不让适配器或 Freqtrade 成为第二订单所有者。

退出标准：Core 合同可重复、可拒绝、可恢复；Binance/Hyperliquid 事实和 sender scope 不混淆。2026-07-31 已完成 Hyperliquid 默认主账户最小 LIVE IOC、保护、退出与对账；HIP-3、保证金、资金动作和无人值守持续发送保持关闭。

### M6：AUTO_ADD、风险减仓和自动退出入口（SHADOW 工程完成）

用户流程：Proposal 冻结有限 Add 合同 → Operator 从后续 Perptape 候选发起 Add → Trading 最终风控与风险预留 → 首个正成交消费 AddUnit；Operator/Web/Mock Telegram 可提交只收紧的减仓或退出，冻结失效价与 KILL_SWITCH 不依赖 Perptape 或交互层。

退出标准：分档 AddUnit、候选版本/范围/新鲜度、盈利与保护、最终 Risk Engine、Unknown、活动 Intent、目标仲裁、reduce-only、幂等和旧 Telegram 按钮拒绝均有 PostgreSQL 自动化。`AUTO_ADD` 默认仍关闭，没有真实 Bot 或交易所副作用。

### M7 以后：资金与运行结果

下一步按独立用户结果交付 Vault/交易所资金只读、Web 资金中心、人工资金 Proposal/Approval/Authorization、双向 Mock/Sandbox 划转与资金对账；之后才开发独立 Gate 的自动利润归集和可选运营补充，再收敛实际结果、审计、运行状态和必要部署。每项都有独立权限、风险门、故障路径和默认关闭状态；不为尚未有外部参数的能力预建通用平台。

## 4. 共同硬依赖

- 身份与作用域授权先于提案、审核和操作；
- Proposal 批准与 RiskDecision 先于新增风险；
- Instrument 有效且事实新鲜先于订单意图；
- 风险预留、业务写入和幂等回执必须原子；
- 场所事实对账先于恢复发送；
- 保护未知或不足、订单 Unknown、旧 fencing token 一律 fail closed；
- 任何真实外部副作用都需要用户另行授权和对应 Gate。

## 5. 每个里程碑的质量门

1. 用户流程、角色、拒绝原因和异常处理有明确入口。
2. 核心业务不变量有自动化测试；不复制只验证字段或哈希的测试。
3. PostgreSQL 集成使用一次性 `_test` 数据库。
4. Ruff、mypy strict、unit、integration、覆盖率、Alembic、metadata 和 `git diff --check` 通过。
5. 文档只更新当前基线、核心不变量和路线，不新增微型 WP/evidence。
6. 真实外部副作用尚未存在时，不建设 Outbox/Inbox、证书状态机或通用工作流平台。

## 6. 故障降级原则

- 数据或账户事实未知：禁止新增风险；保持现有风险和人工可见异常。
- 订单结果未知：保持 Reservation/OrderIntent Unknown，不自动重试。
- 保护未知或不足：禁止新增风险并提升减仓/退出紧迫度。
- sender 失效：新 owner 必须先对账再取得更高 token。
- UI、Telegram 或辅助建议源不可用：保护、减仓、退出和对账核心不依赖它们。
- 未实现或未批准能力：Gate 保持 `DISABLED`，不以文档或配置默认值绕过。
