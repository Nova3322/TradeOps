## 1. 目的

本登记表是策略参数、风险参数与能力证书的统一目录，解决以下问题：

- 区分“设计已经固定”“等待外部事实”“等待研究”“等待执行验证”。
- 防止示例值、研究候选或交易所接口被误当成生产默认。
- 让每个运行版本可以追溯到参数、能力、证据、审批与失效条件。
- 让 Binance、Hyperliquid Core、HIP-3 DEX、margin mode、风险档位与 Add 层级分别认证。

本表不是运行时配置，也不签发交易权限。生产参数必须从已批准、不可变、带版本的配置制品发布，且其值与本表一致。

## 2. 状态与责任

### 2.1 参数状态

| 状态 | 含义 | 是否可进入真实增险 |
| --- | --- | --- |
| `FIXED` | 上位业务规则已固定 | 还需实现、测试和能力证书 |
| `EXTERNAL_FACT_REQUIRED` | 等待真实账户、链、主体或责任人事实 | 否；使用安全关闭行为 |
| `RESEARCH_PENDING` | 需预登记研究与时间外验证 | 否 |
| `SHADOW_ONLY` | 可计算或展示，不允许真实动作 | 否 |
| `CERTIFIED` | 已在明确认证单位和版本内通过 | 仅限证书范围 |
| `SUSPENDED` | 证据、健康或表现失效 | 否，只保护 / 减仓 / 退出 |
| `RETIRED` | 不再用于新提案 | 否 |

### 2.2 能力状态

| 状态 | 含义 |
| --- | --- |
| `NOT_IMPLEMENTED` | 尚无实现 |
| `IMPLEMENTED_UNVERIFIED` | 已实现但没有足够证据 |
| `VALIDATING` | 正在重放、影子、模拟或小额验证 |
| `CERTIFIED` | 在证书范围内有效 |
| `NOT_SUPPORTED` | 明确不支持 |
| `UNKNOWN` | 当前事实不可验证，按不支持处理 |
| `EXPIRED` | 版本、账户或规则变化使证书失效 |
| `SUSPENDED` | 证据或健康暂时失效；只允许保护、减仓与退出 |

### 2.3 清单状态与能力状态的映射

逐场所认证清单使用的是“检查项状态”，不是产品能力状态：

| 检查项写法 | 规范检查项状态 | 对能力状态的含义 |
| --- | --- | --- |
| 已定 | `FIXED_DESIGN` | 只说明设计已固定，不证明已经实现 |
| 待验证 | `UNVERIFIED` | 证据项未完成；不能据此把能力写成 `VALIDATING` |
| 不支持 | `NOT_SUPPORTED` | 对应能力不提供，并需安全降级 |
| 不适用 | `NOT_APPLICABLE` | 该检查项不属于本认证单位，必须说明原因 |

没有实现证据时，汇总 `capability_status` 必须是 `NOT_IMPLEMENTED`。已有实现但证据不足才可为 `IMPLEMENTED_UNVERIFIED`；实际进入重放、影子、模拟或小额验证后才可为 `VALIDATING`。认证清单中的“待验证”绝不等同于能力已经实现。

### 2.4 负责人

每行至少指定业务负责人、策略研究负责人、风险负责人、执行负责人中的适用角色；涉及资金或权限时追加资金 / 安全负责人。负责人不是越权审批人。

## 12. 登记维护规则

- 所有参数必须有单位、适用范围、负责人、来源与状态。
- 示例值必须明确标记，不能进入运行时默认。
- 一个参数变化时，要列出受影响的策略、风险、执行、审核和资金证书。
- 外部运行事实不作为长期参数硬编码；交易规则、杠杆档位、余额与市场状态每次实时读取并保存版本快照。
- 证据失效、规则漂移、账户抽象变化或版本升级时，状态先改为 `EXPIRED / UNKNOWN`，不能等待事故后补记。
- 任何 `EXTERNAL_FACT_REQUIRED / RESEARCH_PENDING` 项目在真实执行路径中的安全值都是关闭能力或拒绝增险，不允许开发团队自行代填。
- 每次发布前，需求追踪矩阵必须证明所有使用到的参数均为 `FIXED` 或在该认证单位内 `CERTIFIED`。
