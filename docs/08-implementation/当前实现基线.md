# 当前实现基线

> 状态：BASELINE
> 日期：2026-07-31
> 适用范围：当前 `main` 分支的 SHADOW 核心、M9 结果/审计/运行恢复基线，以及 Binance Unified Account 与 Hyperliquid Core 默认关闭的 TESTNET/LIVE 窄合同

## 产品边界

本项目服务一个资本所有者和一个内部组织。内部用户按账户、场所作用域承担观察、提案、审核、操作和系统管理职责；不开放外部注册，不管理第三方资金，不建设多租户、通用合规、通用认证或通用策略平台。

完整产品愿景继续包含 Binance、Hyperliquid、Web/PWA、Telegram、VenueAdapter、Margin、Vault/CTO 和报表，但必须按可运行的端到端用户流程逐步实现。尚未开发的能力保持关闭，也不为它预建通用实体。

## 当前可运行入口

- 进程入口：`trading-api = trading_control_plane.__main__:main`。
- HTTP 入口：健康检查/指标；内部会话；Perptape 主站机会与显式 SHADOW/TESTNET/LIVE Proposal；Proposal、Review、RiskDecision、TradingAuthorization、Campaign；资金事实、资金提案/复核/授权、Mock 划转和 NoTilt 三链状态/同步/未签名交易计划；按环境实际结果、作用域审计和运行状态；Binance 与 Hyperliquid Core 的只读、发送、取消、Unknown 恢复、保护和保护取消 API。
- Web/PWA 入口：机会、人工提案、审核、Campaign、仓位/保护、订单/成交、风险/目标、异常处理、资金中心、Binance 只读事实和 `/results` 结果/审计/运行状态；Service Worker 只缓存带版本的静态壳，不缓存业务 API。
- 业务入口：HTTP API 与 Python 内部 API `TradingService` 共用同一事务、RBAC 和领域不变量。
- 计算入口：`evaluate_risk`、`select_target_position`、`compute_pnl`。
- 数据库：PostgreSQL；Alembic head 为 `20260731_0002`。增量迁移保留已经存在的本地用户与 Telegram 绑定，并增加多资产 USD 估值字段。
- Schema：26 张业务表，另有 Alembic 版本表。M7 的三张资金生命周期表分别保存 Proposal、Authorization 与 Transfer；M8 只新增一张跨重启保存运营阈值和地址引用的 `capital_automation_policies`。Vault 与场所余额继续共用 `account_equities` 外部事实表。
- 发送边界：SHADOW 仍只记录合成事实；TESTNET 和 LIVE 分别要求独立的运行配置，LIVE 还必须通过数据库 `LIVE_ORDER_SEND` Gate、短期授权、最新风险事实和 sender fencing。所有开关初始关闭。
- Binance 边界：标准账户继续使用 `BinanceReadOnlyClient`/`BinanceTestnetClient`；Unified Account 使用官方 PAPI 的 `BinancePortfolioMarginReadOnlyClient` 与 `BinancePortfolioMarginClient`，实现 UM 查询、query-before-send、MARKET、撤销、Unknown 恢复、reduce-only `STOP_MARKET` 保护和保护取消。没有资金划转方法。
- Hyperliquid 边界：主账户是默认事实与执行作用域；API Wallet 可通过 `userRole` 解析所属主账户，可选子账户必须显式配置并通过 `vaultAddress` 发送。Core Info 历史查询使用有界 30 天窗口和 429 退避；Exchange 使用官方 SDK 签名、显式价格 IOC、稳定 cloid、`cancelByCloid` 和 reduce-only trigger 保护。非空 `dex`、HIP-3、隐含滑点、保证金控制与资金动作均不存在。
- 身份边界：正式环境预留托管 IdP/Passkey 会话边界；本地/测试可显式启用 Mock 登录与对象版本绑定的 Mock step-up，生产环境禁止 Mock。HUMAN 只能创建 MANUAL Proposal；SYSTEM Proposal 只能由 Perptape SERVICE principal 创建。
- Perptape 边界：只读调用现有 `GET /api/v1/breakouts`；HH/LL 映射 LONG/SHORT，源时间、就绪度、合同版本和深链随 Proposal 冻结，信号不直接形成订单。
- Telegram 边界：保留 `MockTelegramGateway` 供自动化测试，并新增默认关闭的真实 Bot API 私聊长轮询。真实通道支持用户名白名单首次绑定、持久数字 chat ID、提案审核深链以及绑定内部用户、动作、Campaign target version 和短有效期的只收紧风险按钮；群聊、转发和跨账号操作拒绝。正式 IdP/Passkey、Webhook 部署和持久送达重试仍未实现，本地绑定不能冒充生产强认证。
- 资金边界：`MockCapitalTransferAdapter` 只接受 SHADOW/TESTNET。NoTilt 边界使用官方 `@notilt/sdk`，固定支持 Ethereum/BSC/Arbitrum 的官方部署、Registry、Vault budget 和 deposit/release 未签名交易构造；服务无 NoTilt 私钥字段，不签名、不广播，也没有 owner/白名单管理/Panic/Full Exit/任意合约入口。`CAPITAL_TRANSFER` 保持关闭；当前没有完整的链上回执、交易所提币/充值和两端确认链路。

## 当前数据真源

当前 Schema 只持久化需要跨重启保留的权威状态或外部事实：

- 内部用户、角色与账户/场所作用域；
- Proposal、Approval、RiskPolicy、RiskDecision、TradingAuthorization；
- Campaign 的当前目标、版本、原因、紧迫度和 PnL；
- RiskReservation、OrderIntent、CommandReceipt；
- VenueOrder、VenueFill、Position、ProtectionOrder、AccountEquity、FundingPayment；
- ReconciliationRun、SenderLease、CapabilityGate、AuditEvent。
- TransferProposal、TransferAuthorization、CapitalTransfer；Vault 与场所资本事实复用 AccountEquity，不另建余额快照平台。
- CapitalAutomationPolicy 只保存一个环境/账户/场所/资产作用域的当前运营下沿、目标、上沿、Vault 最低储备、单次限额和两端引用；候选结果仍进入现有 TransferProposal，不建立自动化流水平台。

可重新计算的风险步骤、目标候选、减仓计划、投影、绑定、证明哈希和证据包不单独持久化。

## 安全默认

- `LIVE_ORDER_SEND`、`CAPITAL_TRANSFER`、`AUTO_ADD`、`AUTO_PROFIT_SWEEP` 与 `AUTO_OPERATING_REFILL` 在初始 Schema 中均为 `DISABLED`。
- RiskDecision 的数量、风险占用、新鲜度、仓位、权益和保护状态均由服务端读取 PostgreSQL；调用者不能提供这些事实。
- 风险决定后、创建 INITIAL/ADD OrderIntent 前会在同一风险容量锁内重新读取政策、授权、事实、活动 Campaign/Intent 和全局占用；变化后 fail closed。
- Campaign、Authorization、Position、Equity、Order、Fill 和 Funding 均保留 `SHADOW|TESTNET|LIVE` 环境边界；同账户同标的的不同环境事实不能互相覆盖或参与同一轮对账。
- Position、Protection 和 Equity 的 `observed_at` 表示本进程成功接收当前快照的时间；VenueOrder/Fill/Funding 保留场所事件时间，所有记录另有本地 `updated_at`。最多 30 秒的有界时钟偏差可容忍，陈旧、异常未来或未知事实阻断新增风险。
- 未知或陈旧事实、保护不足、未解决 Unknown、过期/越权授权和旧 fencing token 均阻断新增风险或发送。
- Binance TESTNET/LIVE 的稳定客户端订单标识由 `OrderIntent` UUID 派生；PAPI LIVE 标识不超过官方 32 字符上限。每次发送先按该标识查询，确认不存在才创建。写请求结果不确定时进入 `UNKNOWN`，保持风险占用，恢复入口只查询、不盲重发。
- Hyperliquid TESTNET/LIVE 以 `0x + OrderIntent UUID` 形成 128-bit cloid，同样先查后发；OrderIntent 保存从 Proposal 冻结或减仓动作显式提供的 `limit_price`。没有显式价格、价格/数量精度不合法、Core 域不匹配或 signer 缺失时在外部调用前拒绝。
- 原生保护以当前非零仓位派生稳定标识：Binance PAPI 使用定量 reduce-only `STOP_MARKET`，Hyperliquid 使用 reduce-only trigger market。保护不足、拒绝或 Unknown 会被当前保护事实和 reconciliation 阻断；目标不为零时禁止取消保护。
- `ReconciliationRun.MATCH` 只能由全 execution scope 的一致事务计算产生；人工 `RESOLVED` 不等于 MATCH，也不能授权 sender 接管。
- Capability Gate 合法启用不会使数据库 readiness 失败，但 Gate 永远不能替代授权、最终风险检查、对账或 fencing。
- 幂等回执与业务写入处于同一 PostgreSQL 事务。
- AUTO_ADD 的 Proposal 必须冻结总数量、初仓数量、AddUnit 数、候选触发价和失效价；低/中/高风险最多分别授权 1/2/3 个 AddUnit。Add 还必须绑定新的同场所、同标的、同方向 Perptape READY 候选并通过当前盈利、保护、新鲜度、Unknown、活动 Intent、风险容量和最终 Risk Engine 检查。AddUnit 在首个正成交时原子消费，意图创建和零成交取消/拒绝都不消费。
- Web/Mock Telegram 的减仓入口在一个事务中把当前目标候选交给 `TargetPositionArbiter` 并生成唯一 reduce-only Intent；冻结失效价或 KILL_SWITCH 触发的退出只读取 Trading 的场所仓位和政策事实，不依赖 Perptape、Web 或 Telegram 持续可用。重复命令返回同一回执，旧 Telegram target version 拒绝。
- 当前没有 Outbox/Inbox；等真实异步消费者或不可逆外部副作用出现时再按实际合同实现。
- `TREASURY_ADMIN` 是独立资金角色；SYSTEM_ADMIN 不因系统管理权限自动获得资金查看、复核、授权或执行权限。资金提案需要两名不同 Treasury Reviewer，创建者不能审核、授权或执行同一笔划转。
- 源端一旦预留立即从资金中心的有效可用额扣除；`SUBMITTED`/`IN_FLIGHT`/`UNKNOWN` 只计入在途或占用，不在源端与目的端重复计入。目的端权威余额事实和资金 scope 对账同时满足后才可结算；Unknown 不自动释放或重发。
- Vault→场所和场所→Vault 均要求空仓、无活动或 Unknown 订单；场所→Vault 还要求机器计算的 MATCH。资金路径不能用于活动仓位救援，TradingAuthorization 不能代替资金授权。
- `AUTO_PROFIT_SWEEP` 与 `AUTO_OPERATING_REFILL` 独立默认关闭。启用其中一个也只能计算对应非生产候选：利润归集使用已关闭 Campaign 的净实际 PnL 并扣除既有归集，不使用浮盈；运营补充要求净已实现 PnL 非负，不能追损或救援活动仓。候选自动冻结为待复核 Proposal，仍需两名 Treasury Reviewer、独立 TransferAuthorization 和另一操作者。

## 当前 M2 用户流程

Operator 可以从有效 TradingAuthorization 原子创建 Campaign、RiskReservation 和 INITIAL OrderIntent；获取单一 sender lease 后只记录合成 SHADOW Order，再显式录入合成成交、仓位、保护、权益和资金费事实。Campaign 页面可计算唯一目标、生成 reduce-only 意图、运行全 scope 对账、刷新 PnL 并在平仓、终态 EXIT 和计算所得 MATCH 同时满足后关闭 Campaign。

`UNKNOWN` 的 OrderIntent、VenueOrder、RiskReservation 和 Campaign 会保持风险占用；Web 不提供重发或释放按钮，异常页从权威当前状态派生阻断项。M2 自动化测试覆盖完整初仓到退出流程及 Unknown 拒绝路径；页面已经在宽屏和手机视口检查。所有事实均明确标记为 SHADOW 合成事实。

## 当前 M3 用户流程

内部 Operator 可在 `/venues/binance` 查看配置状态和当前已持久化的 Binance Instrument、仓位/保护、订单、成交、权益及资金费。只有只读开关、凭据和明确 `TESTNET|LIVE` 环境同时配置后，页面才提供同步动作。同步按场所外部 ID 去重，外部未绑定订单或非零仓位进入环境隔离的 scope reconciliation；非零仓位缺少保护时保存 `UNKNOWN` 并 fail closed。Hedge Mode 非零双向仓位不会被错误折叠为净仓，而是明确拒绝。

自动化使用官方端点形状的本地合同响应和一次性 PostgreSQL 验证签名、字段映射、重复同步、RBAC、环境隔离、对账与禁用路径。2026-07-31 另以 Unified Account 主账户完成最小 LIVE 读取、开仓、幂等回放、保护、退出、保护取消、对账、PnL 与空仓实证；凭据未写入仓库或报告。

## 当前 M4 用户流程

在显式开启 `TRADING_BINANCE_TESTNET_ORDER_SEND_ENABLED` 且配置独立 TESTNET 凭据后，Operator 可对 `TESTNET:account:BINANCE` scope 获取 sender lease，从已审核、已授权的 TESTNET OrderIntent 执行 query-before-send。订单、部分成交、零成交取消、明确拒绝、Unknown、重启查询恢复、原生保护、退出、scope reconciliation 和 Campaign PnL 均落在现有核心实体中；没有增加业务表或通用 VenueAdapter 平台。

自动化使用官方请求形状、状态化本地合同和一次性 PostgreSQL 跑通初仓、保护、补全成交、退出、资金费、对账、PnL 与关闭；同时验证旧 fencing token 在外部调用前拒绝、Unknown 不释放风险且重启不二次写、部分成交取消保留 OPEN 风险、明确零成交拒绝才释放风险。LIVE 最小实证只证明该账户/标的/时刻的窄闭环，不证明持续运行、收益或其他账户模式。

## 当前 M5 用户流程

Hyperliquid 以独立窄适配器接入，不建立任意交易所平台。Core Info 读取 instrument、订单、成交、单向仓位、权益、资金费和 trigger 保护，按 `TESTNET|LIVE` 与 Binance 分域持久化；API 主机与事实环境不一致时拒绝。Core TESTNET 订单使用显式价格 IOC、稳定 cloid、query-before-send、`cancelByCloid`、Unknown 查询恢复和 reduce-only trigger 保护。Trading 仍是 Proposal、Campaign、Reservation、OrderIntent、目标、对账和 PnL 的唯一权威所有者，适配器不能自行生成机会或订单。

自动化使用官方请求/响应形状、状态化本地 Core 合同和一次性 PostgreSQL 跑通 Proposal→双人审核→RiskDecision→TradingAuthorization→RiskReservation→IOC→VenueFill/Position→保护→对账→退出→资金费/PnL；另验证 fencing 在网络前拒绝、Unknown 重启只按 cloid 查询且不二次发送。2026-07-31 另以 API Wallet 和默认主账户完成最小 LIVE 闭环；Core 结果不认证 HIP-3、Margin、持续运行或盈利。

## 当前 M6 用户流程

Proposal 页面可以冻结“总数量上限、初仓数量、是否允许 AUTO_ADD、分档 AddUnit、Add 触发价和失效价”，Reviewer 审核后由 TradingAuthorization 进一步收紧 AddUnit。Campaign 页面只展示当前同范围的 Perptape READY 后续候选；Operator 提交候选和数量后，Trading 在同一事务边界重新检查 Gate、授权、剩余数量、盈利仓位、足额保护、新鲜事实、风险政策、活动 Intent 和最终 Risk Engine，再创建 Add Reservation/Intent。首个正成交消费一个 AddUnit，后续部分成交不重复消费。

Operator 可以从 Web 一次提交目标剩余仓位并原子形成唯一 reduce-only Intent，也可以评估 Proposal 冻结失效价或 KILL_SWITCH 并形成 EXIT；这些收紧风险动作不要求 Perptape 可用。Mock 与真实私聊 Telegram 通知都携带用户、动作、Campaign target version 和短有效期绑定的 action reference，可关闭本 Campaign 后续 Add、提交预定义紧急减仓/退出；重复点击返回原回执，旧版本新命令拒绝。SYSTEM_ADMIN 另有只关闭全局 AUTO_ADD、只切换到 REDUCE_ONLY 的 Web/API 入口，不能由这些入口恢复新增风险。

自动化使用一次性 PostgreSQL 跑通初仓→Perptape Add→两次部分成交→AddUnit 单次消费→Web 原子减仓→Telegram 紧急减仓→冻结失效自动 EXIT，并验证低风险 AddUnit 上限、同 key 冲突、旧 Telegram 按钮、Perptape 不可用时停止 Add 但不阻断退出。所有订单事实仍为 SHADOW；没有连接 Perptape 真实服务、Telegram 网络或交易所。

## 当前 M7 用户流程

Treasury Admin 可在 `/capital` 查看 Binance、Hyperliquid、NoTilt Vault 和总 LIVE USD 净值、源端预留与在途金额，创建人工双向划转提案。任何必需来源缺失或估值过期时净值显示 `INCOMPLETE`；Vault 未处于当前 active assignment/受控状态时阻断新增风险。提案提交后必须由两名不同 Treasury Admin 复核，再由非创建者签发独立、短期、定额且绑定源端/目的端/资产/网络的 TransferAuthorization。另一名资金操作者只能执行 SHADOW/TESTNET Mock，或在显式 `CAPITAL_TRANSFER` Gate 下生成交给独立钱包确认的 NoTilt 未签名交易计划。

Vault→场所和场所→Vault 都会在预留时检查真实空仓、无活动/Unknown 订单；后者还要求同 scope 机器对账 MATCH。源端预留、提交、在途、目的端确认、Unknown 与结算使用一条权威 CapitalTransfer 生命周期；目的端余额事实不足或对账不一致时保持差异，Unknown 保留源端占用且没有重发入口。资金 Telegram 只发通知，不包含批准或执行 action reference。

自动化使用一次性 PostgreSQL 跑通两个方向的 Proposal→双人复核→TransferAuthorization→源端预留→Mock 提交→在途→目的端事实→对账→结算，并验证 NoTilt Registry/Vault 读取、多资产估值、两场所+Vault 管理资本、默认 Gate 拒绝、未签名计划和重复请求幂等。当前 Arbitrum assignment 尚未激活、没有 Vault 地址，也没有链上 request/execute 回执到场所到账的完整对账；`CAPITAL_TRANSFER` 仍为 `DISABLED`。

## 当前 M8 用户流程

Treasury Admin 可在资金中心保存一个 SHADOW/TESTNET 运营资金策略，查看 `AUTO_PROFIT_SWEEP` 和 `AUTO_OPERATING_REFILL` 两个独立 Gate，并在 Gate 另行启用后显式评估候选。评估会锁定作用域，要求新鲜空仓事实、无活动/Unknown 订单、无未结束 Campaign、无在途/Unknown 资金和新鲜机器 MATCH。

利润归集只取“场所超过运营上沿且回到目标后仍可划出的金额、已关闭 Campaign 的累计净实际 PnL、剩余未归集利润和单次上限”中的安全最小值。运营补充只取“目标缺口、Vault 超过最低储备的可用额和单次上限”中的安全最小值；净已实现亏损直接阻断。两个方向都只生成待双人复核的 TransferProposal，不自动签发授权、不调用 Mock/真实 Adapter。

当前没有常驻调度器，也没有真实链路参数。两项 Gate 初始均为 `DISABLED`，策略只接受 SHADOW/TESTNET；自动化成功测试不能冒充真实利润归集或资金补充。

## 当前 M9 用户流程

内部用户可在 `/results` 严格选择 `SHADOW`、`TESTNET` 或 `LIVE`，查看该环境 Campaign 的 Perptape/人工来源、冻结版本、风险档位、成交量、手续费、资金费、滑点、已实现/未实现/最终 PnL。查询 API 还可按 SYSTEM/MANUAL、来源类型/候选/版本、场所、账户、标的、方向、风险档位、Campaign 和更新时间范围精确过滤。汇总按结算币种分开，已关闭 Campaign 只计算绝对累计 PnL 与绝对回撤；由于当前没有权威期初资本和 FX 真源，页面明确不伪造跨币种合计或百分比收益/回撤。SHADOW、TESTNET 与 LIVE 均显示不同实际性声明，非生产事实不能冒充实盘盈利。

同一页展示当前用户可见业务对象的 `audit_events` 时间线，以及数据库 readiness、Alembic revision、26 张业务表、五个 Capability Gate 和外部边界是否配置。运行状态只返回布尔配置结果，不返回 API secret、private key 或凭据内容；没有新增审计投影、结果快照、绩效账本或常驻 worker。

仓库提供 PostgreSQL custom-format 备份和仅允许 `*_test` 目标的恢复脚本。2026-07-19 本地演练已将一次性测试库恢复到另一可丢弃库，验证 revision `20260718_0001`、26 张业务表、五个默认关闭 Gate、readiness 与 `alembic check`。一次本地单进程观测中，API 在 20 次 readiness 请求后约为 91,440 KiB RSS、0.1% CPU；测试 PostgreSQL 容器约为 166.9 MiB、0.03% CPU、7 个进程。这是开发机单点观测，不是容量承诺或生产 SLO。

- 托管 IdP/真实 Passkey、Telegram Webhook 部署、持久送达重试与生产强身份绑定；
- 常驻市场数据/执行 worker、进程监督、凭据轮换与生产 Secret Manager、Freqtrade 执行后端；
- Hyperliquid HIP-3、isolated/cross margin 管理、API Wallet 生命周期和正式生产认证；
- 真实测试网账户实证、长期实盘保护生命周期管理、无人值守恢复和生产账户接管编排；
- AUTO_ADD 的常驻调度器与真实场所运行实证；当前已实现默认关闭的 Perptape 窄候选、Web/Mock Telegram 用户入口和 SHADOW 事务语义，不是独立策略；
- 生效的 NoTilt assignment 与实际 Vault 地址、链上 request/execute 回执验证、真实交易所提币/充值 API 和两端确认；当前已有官方三链读取、Web 净值、Mock 双向流程与外部钱包未签名交易交接，但不签名、不广播；
- 自动资金常驻调度、真实参数认证、真实 Adapter 提交和目的端实证；当前只有默认关闭的非生产候选计算、API/Web 入口与 PostgreSQL 状态；
- 跨币种 FX 真源、权威期初资本、百分比收益/回撤、生产级报表调度和外部财务账本；当前只报告分币种已记录事实；
- 生产部署、生产数据库兼容链、实盘认证和盈利保证。

这些缺口不能被 Mock 身份、本地 Telegram 白名单绑定、健康检查、SHADOW 场所事实或文档描述冒充为已实现能力。
