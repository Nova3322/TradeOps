# 当前实现基线

> 状态：BASELINE
> 日期：2026-07-19
> 适用范围：当前 `main` 分支的预生产 SHADOW 交易核心

## 产品边界

本项目服务一个资本所有者和一个内部组织。内部用户按账户、场所作用域承担观察、提案、审核、操作和系统管理职责；不开放外部注册，不管理第三方资金，不建设多租户、通用合规、通用认证或通用策略平台。

完整产品愿景继续包含 Binance、Hyperliquid、Web/PWA、Telegram、VenueAdapter、Margin、Vault/CTO 和报表，但必须按可运行的端到端用户流程逐步实现。尚未开发的能力保持关闭，也不为它预建通用实体。

## 当前可运行入口

- 进程入口：`trading-api = trading_control_plane.__main__:main`。
- HTTP 入口：健康检查/指标；内部会话；Perptape 机会；Proposal、Review、RiskDecision、TradingAuthorization、SHADOW Campaign、场所事实、订单、保护、目标、对账与 PnL API。
- Web/PWA 入口：机会、人工提案、审核、Campaign、仓位/保护、订单/成交、风险/目标和异常处理；Service Worker 只缓存带版本的静态壳，不缓存业务 API。
- 业务入口：HTTP API 与 Python 内部 API `TradingService` 共用同一事务、RBAC 和领域不变量。
- 计算入口：`evaluate_risk`、`select_target_position`、`compute_pnl`。
- 数据库：PostgreSQL；Alembic head 为 `20260718_0001`。
- Schema：22 张业务表，另有 Alembic 版本表。
- 发送边界：只有 `record_shadow_order`，只记录合成 SHADOW 场所事实，不连接交易所、不发送真实订单。
- 身份边界：正式环境预留托管 IdP/Passkey 会话边界；本地/测试可显式启用 Mock 登录与对象版本绑定的 Mock step-up，生产环境禁止 Mock。HUMAN 只能创建 MANUAL Proposal；SYSTEM Proposal 只能由 Perptape SERVICE principal 创建。
- Perptape 边界：只读调用现有 `GET /api/v1/breakouts`；HH/LL 映射 LONG/SHORT，源时间、就绪度、合同版本和深链随 Proposal 冻结，信号不直接形成订单。
- Telegram 边界：当前 `MockTelegramGateway` 不联网，覆盖提案、SHADOW 成交、保护、Unknown、对账异常和关闭通知；review code 不能替代批准所需的 step-up grant，通知不能直接执行订单动作。

## 当前数据真源

当前 Schema 只持久化需要跨重启保留的权威状态或外部事实：

- 内部用户、角色与账户/场所作用域；
- Proposal、Approval、RiskPolicy、RiskDecision、TradingAuthorization；
- Campaign 的当前目标、版本、原因、紧迫度和 PnL；
- RiskReservation、OrderIntent、CommandReceipt；
- VenueOrder、VenueFill、Position、ProtectionOrder、AccountEquity、FundingPayment；
- ReconciliationRun、SenderLease、CapabilityGate、AuditEvent。

可重新计算的风险步骤、目标候选、减仓计划、投影、绑定、证明哈希和证据包不单独持久化。

## 安全默认

- `LIVE_ORDER_SEND`、`CAPITAL_TRANSFER`、`AUTO_ADD` 在初始 Schema 中均为 `DISABLED`。
- RiskDecision 的数量、风险占用、新鲜度、仓位、权益和保护状态均由服务端读取 PostgreSQL；调用者不能提供这些事实。
- 风险决定后、创建 INITIAL/ADD OrderIntent 前会在同一风险容量锁内重新读取政策、授权、事实、活动 Campaign/Intent 和全局占用；变化后 fail closed。
- Position、Protection、Equity 和 VenueOrder 区分场所 `observed_at` 与本地 `updated_at`，陈旧或未知事实阻断新增风险。
- 未知或陈旧事实、保护不足、未解决 Unknown、过期/越权授权和旧 fencing token 均阻断新增风险或发送。
- `ReconciliationRun.MATCH` 只能由全 execution scope 的一致事务计算产生；人工 `RESOLVED` 不等于 MATCH，也不能授权 sender 接管。
- Capability Gate 合法启用不会使数据库 readiness 失败，但 Gate 永远不能替代授权、最终风险检查、对账或 fencing。
- 幂等回执与业务写入处于同一 PostgreSQL 事务。
- 当前没有 Outbox/Inbox；等真实异步消费者或不可逆外部副作用出现时再按实际合同实现。

## 当前 M2 用户流程

Operator 可以从有效 TradingAuthorization 原子创建 Campaign、RiskReservation 和 INITIAL OrderIntent；获取单一 sender lease 后只记录合成 SHADOW Order，再显式录入合成成交、仓位、保护、权益和资金费事实。Campaign 页面可计算唯一目标、生成 reduce-only 意图、运行全 scope 对账、刷新 PnL 并在平仓、终态 EXIT 和计算所得 MATCH 同时满足后关闭 Campaign。

`UNKNOWN` 的 OrderIntent、VenueOrder、RiskReservation 和 Campaign 会保持风险占用；Web 不提供重发或释放按钮，异常页从权威当前状态派生阻断项。M2 自动化测试覆盖完整初仓到退出流程及 Unknown 拒绝路径；页面已经在宽屏和手机视口检查。所有事实均明确标记为 SHADOW 合成事实。

## 当前明确未实现

- 托管 IdP/真实 Passkey、真实 Telegram Bot 与真实消息送达；
- 市场数据采集器、真实 Binance/Hyperliquid VenueAdapter、Freqtrade/OMS 发送链；
- 实盘订单、真实保护订单管理、真实账户恢复编排；
- 自动 Add 的策略触发器和用户入口、资金划转、Vault/CTO、Margin Controller；当前只实现默认关闭的 SHADOW Add 硬门与事务语义；
- 生产部署、生产数据库兼容链、实盘认证和盈利保证。

这些缺口不能被 Mock 身份、Mock Telegram、健康检查、SHADOW 场所事实或文档描述冒充为已实现能力。
