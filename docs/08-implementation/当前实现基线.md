# 当前实现基线

> 状态：BASELINE
> 日期：2026-08-11
> 适用范围：当前 TradingOPS 分支的 Workspace / Team 控制面、完整 SHADOW 工作流、分环境结果与风险事件报表、团队通知，以及默认关闭的 TESTNET/LIVE 窄合同

## 产品边界

本项目服务一个资本所有者和一个内部组织。内部用户按账户、场所作用域承担观察、提案、审核、操作和系统管理职责；不开放外部注册，不管理第三方资金，不建设多租户、通用合规、通用认证或通用策略平台。

完整产品愿景继续包含 Binance、Hyperliquid、Web/PWA、Telegram、VenueAdapter、Margin、Vault/CTO 和报表，但必须按可运行的端到端用户流程逐步实现。尚未开发的能力保持关闭，也不为它预建通用实体。

## 当前可运行入口

- 进程入口：`trading-api = trading_control_plane.__main__:main`；独立只读同步入口为 `trading-sync-worker = trading_control_plane.runtime:main`；最小权限通知入口为 `trading-notification-worker = trading_control_plane.notification_runtime:main`。两个 worker 均默认关闭并支持 `--once` 验收。
- 运维入口：`trading-doctor` 只读验证配置、Schema revision、五个数据库 Gate、进程运输开关和连接能力矩阵，不投影 URL、Token、API Key、私钥、加密密钥或指纹。`./scripts/run_compose.sh` 以一条命令启动 PostgreSQL、一次性迁移/安全初始化和非 root 只读根文件系统 API；默认只绑定本机并硬关闭所有危险运输开关。
- HTTP 入口：健康检查/指标；HUMAN 会话与 Team Agent Bearer 身份；Agent 创建/最小角色/精确账户范围/Token 轮换，以及 Agent 冻结提案和幂等独立审核；Team Shadow 启用状态/显式启用、虚拟资金与空仓初始化、确定性成交模拟；Perptape 主站机会与显式 SHADOW/TESTNET/LIVE Proposal；Proposal、Review、RiskDecision、TradingAuthorization、Campaign；风险控制状态和受复核恢复请求/复核/执行；资金事实、资金提案/复核/授权、Mock 划转和 NoTilt 三链状态/同步/持久化未签名计划/链上回执确认；按环境实际结果、作用域审计和运行状态；四场所只读事实，以及 Binance 与 Hyperliquid Core 的发送、取消、Unknown 恢复、保护和保护取消 API。
- Web/PWA 一级导航只保留五个用户任务：`/` 今日、`/signals` 信号、`/proposals` 提案、`/campaigns` 交易、`/results` 复盘；右上角 `/settings` 按当前角色聚合团队设置与四步影子就绪路径。审核队列成为提案内的“待我审核”，仓位/订单/保护/异常成为交易内标签；成员与 Agent、交易账户、风控、通知、影子/真实模式、资金和诊断继续使用原路由，但只从设置或异常上下文渐进展示。24 条既有 SPA 路由及其服务端 capability 校验均保留，不以隐藏导航代替后端拒绝。Agent 明文 Token 只存在于首次创建/轮换响应和当次 DOM，不写入 local/session storage，刷新后必须轮换才能重新获得。旧 `/exceptions` 只做安全兼容跳转；Service Worker 只缓存带版本的静态壳，不缓存业务 API。
- 业务入口：HTTP API 与 Python 内部 API `TradingService` 共用同一事务、RBAC 和领域不变量。
- 计算入口：`evaluate_risk`、`select_target_position`、`compute_pnl`。
- 数据库：PostgreSQL；Alembic head 为 `20260811_0028`。Workspace、Team、团队权限、信号源、交易账户、账户事实、风险政策、提案—执行主链、资金工作流根、sender lease、Perptape 当前 feed 与运行源健康使用非空团队边界；账户探针健康带精确 Account/Venue。Team 以 `SETUP / SHADOW / LIVE` 表达执行模式，Shadow 继续复用既有账户事实、执行聚合、报表和审计，没有新增模拟账本或可修改报表真源。Agent 复用 `users`，仅增加服务种类和 keyed digest、摘要、版本、创建/到期/最近使用时间；数据库不保存明文 Token。
- Schema：42 张业务/运行表，另有 Alembic 版本表。Workspace、Team、成员关系、团队角色、交易账户、团队信号源、冻结 SignalEvent 和通知路由都有独立安全边界；Proposal、Campaign、RiskDecision 和账户事实继续作为报表真源。通知只增加具有独立配置生命周期的 `notification_routes` 与外部副作用恢复生命周期的 `notification_deliveries`；没有建立第二套业务事件账本。Vault 与场所余额共用 `account_equities` 外部事实表；`perptape_feeds` 每个 Team 只有一行当前 feed，用于跨 API/worker 进程共享一致事实，不是历史快照平台。
- 发送边界：SHADOW 的确定性模拟器只在数据库事务中生成 `SHADOW` Order/Fill、仓位、保护、PnL 和虚拟净值变化，不导入或调用场所连接器；Team Shadow 模式同时拒绝 TESTNET/LIVE 对象。TESTNET 和 LIVE 分别要求独立运行配置，LIVE 还必须通过数据库 `LIVE_ORDER_SEND` Gate、短期授权、最新风险事实和 sender fencing。所有开关初始关闭。
- Binance 边界：标准账户继续使用 `BinanceReadOnlyClient`/`BinanceTestnetClient`；Unified Account 使用官方 PAPI 的 `BinancePortfolioMarginReadOnlyClient` 与 `BinancePortfolioMarginClient`，实现 UM 查询、query-before-send、MARKET、撤销、Unknown 恢复、reduce-only `STOP_MARKET` 保护和保护取消。没有资金划转方法。
- Hyperliquid 边界：主账户是默认事实与执行作用域；API Wallet 可通过 `userRole` 解析所属主账户，可选子账户必须显式配置并通过 `vaultAddress` 发送。Core Info 历史查询使用有界 30 天窗口和 429 退避；Exchange 使用官方 SDK 签名、显式价格 IOC、稳定 cloid、`cancelByCloid` 和 reduce-only trigger 保护。非空 `dex`、HIP-3、隐含滑点、保证金控制与资金动作均不存在。
- 身份边界：正式环境预留托管 IdP/Passkey 会话边界；本地/测试可显式启用 Mock 登录与对象版本绑定的 Mock step-up，生产环境禁止 Mock。`SignedTokenService` 仅以本地 HMAC 验证 HUMAN action grant 的 user/action/object/version/TTL；Agent Bearer Token 使用凭据主密钥派生的 HMAC digest，只在创建/轮换时返回一次。Agent 固定一个 Team 与精确 Account/Venue，只允许 OBSERVER/PROPOSER/REVIEWER；没有 OPERATOR、TREASURY_ADMIN 或 SYSTEM_ADMIN，不能签发人工 step-up、读取明文场所凭据、风控决定、下单或资金操作。Agent 提案复用 SYSTEM Proposal 并原子冻结为 `PENDING_REVIEW`，模型/版本/request/generated_at 随 payload 冻结；审核复用同一 Approval、自审拒绝、账户 RBAC、幂等回执与 AuditEvent。正式 HUMAN issuer、IdP/WebAuthn 和外部签名验证仍未实现，因此生产风险恢复保持不可用/fail closed。
- Perptape 边界：只读调用现有 `GET /api/v1/breakouts`；HH/LL 映射 LONG/SHORT，候选 ID 同时包含源场所 raw symbol 与 canonical symbol。同一 canonical symbol 下不同报价合约保持不同身份；旧版不含 raw symbol 的 ID 只有唯一匹配当前候选，且既有 Proposal 的 instrument/venue/direction 与冻结候选身份快照全部精确一致时才兼容，歧义或不一致时明确拒绝。源时间、就绪度、合同版本和深链随 Proposal 冻结，信号不直接形成订单。
- 运行同步边界：`runtime.py` 在部署总开关打开后枚举显式启用的 Team/Account 数据库绑定，以精确范围 INTERNAL principal 和凭据/账户版本读取 Binance、Hyperliquid、OKX 或 Bybit；Team Perptape 使用独立 PROPOSER principal 持续轮询。OKX 只接受 USDT 线性 SWAP，Bybit 只接受 Unified USDT 线性永续；非支持敞口、目录/Mark 覆盖不完整和不完整历史均 fail closed。无数据库绑定时保留部署级 Perptape、Binance/Hyperliquid 与 NoTilt Vault 兼容模式。两种模式都复用现有事实写入与 scope reconciliation，不导入执行客户端、不调用订单发送、不签名或广播资金交易。凭据轮换和失败验证撤销账户绑定；绑定状态不冒充进程活性或交易就绪。
- Telegram 边界：保留 `MockTelegramGateway` 供自动化测试，并提供默认关闭的真实 Bot API 私聊长轮询。review-only 通道使用中文 HTML 审核卡和 `/start`、`/help`、`/status`、`/todo`，支持用户名白名单首次绑定、持久数字 chat ID，以及冻结提案的两步批准/拒绝。每次操作重验内部身份、对象版本、有效期、幂等和独立审核；创建者不能自审。Campaign、资金、风险 Gate、成员权限、签名和广播入口全部抑制。统一通知另有独立 Telegram/Slack/Lark/邮件路由和耐久送达 worker，但它没有审核动作入口。正式 IdP/Passkey 和 Telegram Webhook 部署仍未实现，本地绑定不能冒充生产强认证。
- 通知边界：`NotificationRoute` 是 Team 级目的地、事件选择、启用状态和版本化密文真源；`NotificationDelivery` 冻结模板、业务对象版本、作用域、语义哈希、幂等键和投递状态。提案提交、风险决定、Campaign 状态、Webhook 信号、账户连接失败与资金状态复用同一 Team 路由；明确限速最多重试五次，路由改变取消旧 delivery，网络或 worker 中断导致的不确定结果进入 `OUTCOME_UNKNOWN` 且不盲目重发。通知 worker 不导入交易/资金适配器；查询投影不返回凭据。
- 资金边界：`MockCapitalTransferAdapter` 只接受 SHADOW/TESTNET。NoTilt 边界使用官方 `@notilt/sdk`，固定支持 Ethereum/BSC/Arbitrum 的官方部署、Registry、Vault budget、deposit/release 未签名交易构造和固定函数链上回执验证；服务无 NoTilt 私钥字段，不签名、不广播，也没有 owner/白名单管理/Panic/Full Exit/任意合约入口。计划和回执状态跨重启保存，确认深度按链配置，重复 tx hash 幂等且不能跨转账重放。`CAPITAL_TRANSFER` 保持关闭；当前仍没有交易所提币/充值和外部钱包到交易所的完整两端链路。

## 当前数据真源

当前 Schema 只持久化需要跨重启保留的权威状态或外部事实：

- 内部用户、角色与账户/场所作用域；
- Proposal、Approval、RiskPolicy、RiskDecision、TradingAuthorization；
- RiskControlChangeRequest 冻结来源 RiskPolicy/AUTO_ADD 版本、恢复 scope、冷却、有效期和执行结果；Approval 复用同一表但 exactly-one 归属于交易提案、资金提案或风险恢复请求。
- Campaign 的当前目标、版本、原因、紧迫度和 PnL；
- RiskReservation、OrderIntent、CommandReceipt；
- VenueOrder、VenueFill、Position、ProtectionOrder、AccountEquity、FundingPayment；
- ReconciliationRun、SenderLease、CapabilityGate、AuditEvent。
- TransferProposal、TransferAuthorization、CapitalTransfer；Vault 与场所资本事实复用 AccountEquity，不另建余额快照平台。
- CapitalAutomationPolicy 只保存一个环境/账户/场所/资产作用域的当前运营下沿、目标、上沿、Vault 最低储备、单次限额和两端引用；候选结果仍进入现有 TransferProposal，不建立自动化流水平台。
- NotificationRoute 与 NotificationDelivery 只保存团队通知配置和外部副作用恢复状态；事件身份复用同事务 `CommandReceipt`，不另建可修改业务事件真源。

可重新计算的风险步骤、目标候选、减仓计划、投影、绑定、证明哈希和证据包不单独持久化。

## 安全默认

- `LIVE_ORDER_SEND`、`CAPITAL_TRANSFER`、`AUTO_ADD`、`AUTO_PROFIT_SWEEP` 与 `AUTO_OPERATING_REFILL` 在初始 Schema 中均为 `DISABLED`。
- 风险收紧、签发 TradingAuthorization 和风险恢复共享固定风险容量锁序，避免并发死锁或恢复与新授权交错。暂停新增风险会使尚未过期的旧 TradingAuthorization 失效；关闭 AUTO_ADD 会永久写入 `add_revoked_at`，恢复不会复活旧 Authorization 或 AddUnit，但已发送/Unknown 的正成交仍消耗原有责任槽。
- RiskDecision 的数量、风险占用、新鲜度、仓位、权益和保护状态均由服务端读取 PostgreSQL；调用者不能提供这些事实。
- 风险决定后、创建 INITIAL/ADD OrderIntent 前会在同一风险容量锁内重新读取政策、授权、事实、活动 Campaign/Intent 和全局占用；变化后 fail closed。
- Campaign、Authorization、Position、Equity、Order、Fill 和 Funding 均保留 `SHADOW|TESTNET|LIVE` 环境边界；同账户同标的的不同环境事实不能互相覆盖或参与同一轮对账。
- Position、Protection 和 Equity 的 `observed_at` 表示本进程成功接收当前快照的时间；VenueOrder/Fill/Funding 保留场所事件时间，所有记录另有本地 `updated_at`。最多 30 秒的有界时钟偏差可容忍，陈旧、异常未来或未知事实阻断新增风险。
- 未知或陈旧事实、保护不足、未解决 Unknown、过期/越权授权和旧 fencing token 均阻断新增风险或发送。
- Binance TESTNET/LIVE 的稳定客户端订单标识由 `OrderIntent` UUID 派生；PAPI LIVE 标识不超过官方 32 字符上限。每次发送先按该标识查询，确认不存在才创建。写请求结果不确定时进入 `UNKNOWN`，保持风险占用，恢复入口只查询、不盲重发。
- Hyperliquid TESTNET/LIVE 以 `0x + OrderIntent UUID` 形成 128-bit cloid，同样先查后发；OrderIntent 保存从 Proposal 冻结或减仓动作显式提供的 `limit_price`。没有显式价格、价格/数量精度不合法、Core 域不匹配或 signer 缺失时在外部调用前拒绝。
- 原生保护以当前非零仓位派生稳定标识：Binance PAPI 使用定量 reduce-only `STOP_MARKET`，Hyperliquid 使用 reduce-only trigger market。保护不足、拒绝或 Unknown 会被当前保护事实和 reconciliation 阻断；目标不为零时禁止取消保护。
- `ReconciliationRun.MATCH` 只能由全 execution scope 的一致事务计算产生；人工 `RESOLVED` 不等于 MATCH，也不能授权 sender 接管。
- Capability Gate 合法启用不会使数据库 readiness 失败，但 Gate 永远不能替代授权、最终风险检查、对账或 fencing。
- 幂等回执与业务写入处于同一 PostgreSQL 事务。
- AUTO_ADD 的 Proposal 必须冻结总数量、初仓数量、AddUnit 数、候选触发价和失效价；低/中/高风险最多分别授权 1/2/3 个 AddUnit。Add 还必须绑定新的同场所、同标的、同方向 Perptape READY 候选并通过当前盈利、保护、新鲜度、Unknown、活动 Intent、风险容量和最终 Risk Engine 检查。AddUnit 在首个正成交时原子消费，意图创建和零成交取消/拒绝都不消费。
- Web/Mock Telegram 的减仓入口在一个事务中把当前目标候选交给 `TargetPositionArbiter` 并生成唯一 reduce-only Intent；冻结失效价或 KILL_SWITCH 触发的退出只读取 Trading 的场所仓位和政策事实，不依赖 Perptape、Web 或 Telegram 持续可用。重复命令返回同一回执，旧 Telegram target version 拒绝。
- 当前只为已经存在的外部通知副作用实现窄型 durable delivery outbox；没有通用 DomainEvent、Inbox 或任意工作流平台。
- `SYSTEM_ADMIN` 是唯一最高管理员角色，并拥有成员管理与资金中心权限；其他角色只获得显式角色能力。所有资金动作仍需实时校验、最终确认和独立 Gate，管理员身份不能绕过资金安全条件。旧资金提案流程仍要求不同 Reviewer，创建者不能审核、授权或执行同一笔划转。
- 源端一旦预留立即从资金中心的有效可用额扣除；`SUBMITTED`/`IN_FLIGHT`/`UNKNOWN` 只计入在途或占用，不在源端与目的端重复计入。目的端权威余额事实和资金 scope 对账同时满足后才可结算；Unknown 不自动释放或重发。
- Vault→场所和场所→Vault 均要求空仓、无活动或 Unknown 订单；场所→Vault 还要求机器计算的 MATCH。资金路径不能用于活动仓位救援，TradingAuthorization 不能代替资金授权。
- `AUTO_PROFIT_SWEEP` 与 `AUTO_OPERATING_REFILL` 独立默认关闭。启用其中一个也只能计算对应非生产候选：利润归集使用已关闭 Campaign 的净实际 PnL 并扣除既有归集，不使用浮盈；运营补充要求净已实现 PnL 非负，不能追损或救援活动仓。候选自动冻结为待复核 Proposal，仍需两名 Treasury Reviewer、独立 TransferAuthorization 和另一操作者。

## 当前 M2 用户流程

Operator 可以从有效 TradingAuthorization 原子创建 Campaign、RiskReservation 和 INITIAL OrderIntent；获取单一 sender lease 后只记录合成 SHADOW Order，再显式录入合成成交、仓位、保护、权益和资金费事实。Campaign 页面可计算唯一目标、生成 reduce-only 意图、运行全 scope 对账、刷新 PnL 并在平仓、终态 EXIT 和计算所得 MATCH 同时满足后关闭 Campaign。

`UNKNOWN` 的 OrderIntent、VenueOrder、RiskReservation 和 Campaign 会保持风险占用；Web 不提供重发或释放按钮，运行告警详情从权威当前状态派生阻断项并归属于交易任务。M2 自动化测试覆盖完整初仓到退出流程及 Unknown 拒绝路径；所有事实均明确标记为 SHADOW 合成事实。

## 当前 M3 用户流程

## 当前 M10 用户流程

具备 Team 级 `notification.view` 的成员可在 `/notifications` 查看四类通道能力、路由脱敏状态和 delivery 历史；只有 `notification.manage` 可创建、更新、轮换凭据或发送测试。每个路由选择统一事件类型，配置和更新使用幂等键与预期版本。服务端只接受 Slack/Lark 官方 HTTPS Webhook、Telegram Bot/Chat、以及要求 TLS 的公开 DNS SMTP 配置；任何渠道都没有交易、资金、签名或广播权限。

源业务事务与通知 delivery 原子提交。模板、payload、对象版本、route version、Team/Account/Venue/Environment、correlation ID 和幂等身份在入队时冻结；路由轮换后旧 delivery 取消，明确 429 有界重试，未知结果不自动重发。页面把 `PENDING`、`RETRY_WAIT`、`SENDING`、`SENT`、`DEAD_LETTER`、`OUTCOME_UNKNOWN` 与 `CANCELLED` 分开呈现。资金事件已接入同一 Team 路由；当前没有真实外部渠道凭据和生产 worker 部署实证。

Binance/Hyperliquid 的 LIVE 写入另要求精确 `ExchangeAccount` 处于 `ELIGIBLE`。只有当前 Team/Account/Venue 的 `account.manage` 管理员可在 Team 已进入 LIVE、凭据已加密且验证成功、连续只读绑定及其最小 INTERNAL principal 均有效时显式启用；这一步不改变全局 `LIVE_ORDER_SEND` Gate、进程发送开关、sender lease、授权或风控。凭据轮换会重置为 `DISABLED`，连接验证失败或停用连续只读绑定会转为 `BLOCKED`；服务端在每次 LIVE 发送前重新校验全部账户事实。OKX/Bybit 仍无写入 Adapter，API 与页面均保持不可启用，不以其只读能力冒充交易能力。

## 当前受复核风险恢复流程

`/risk` 逐项展示实时恢复条件、当前状态、精确原因、负责角色和下一步。HUMAN SYSTEM_ADMIN 可在所有实时安全条件满足时通过绑定当前版本的 `risk.restore.direct` grant 直接恢复；操作人员只能创建冻结的 `RiskControlChangeRequest`，申请人不得自审，必须由具备独立审核职责的他人审核后执行。两条路径都写入统一审计。

恢复事务会重新锁定风险容量，比较来源政策、revision、AUTO_ADD 状态/version 和完整 scope，并重算仓位、权益、保护、订单、Unknown 与机器对账 blocker；任一漂移或未知均 fail closed。生产环境要求至少一个由运行配置发现的 LIVE scope，缺失时返回 `LIVE_SCOPE_CONFIGURATION_REQUIRED`；`KILL_SWITCH` 明确要求人工事故恢复，不允许走常规流程。任何恢复只创建新的 NORMAL RiskPolicy，AUTO_ADD 始终保持关闭；旧提案、旧 TradingAuthorization 和旧 AddUnit 永不复活。

资金中心同时完成表现边界收敛：默认视图和净值只消费 LIVE 事实，SHADOW/TESTNET 不计入真实净值；未配置或未同步 Vault 时保留 Vault 槽位并显示 `— · MISSING`，总净值保持不完整，绝不把缺失显示为零。三方趋势按各自观测时间合并，只有三方都曾出现有效事实后才形成汇总点。
