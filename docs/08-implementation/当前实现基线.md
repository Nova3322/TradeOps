# 当前实现基线

> 状态：BASELINE
> 日期：2026-07-19
> 适用范围：当前 `main` 分支的 SHADOW 核心、Binance 与 Hyperliquid Core 的只读边界和默认关闭的 TESTNET 订单合同

## 产品边界

本项目服务一个资本所有者和一个内部组织。内部用户按账户、场所作用域承担观察、提案、审核、操作和系统管理职责；不开放外部注册，不管理第三方资金，不建设多租户、通用合规、通用认证或通用策略平台。

完整产品愿景继续包含 Binance、Hyperliquid、Web/PWA、Telegram、VenueAdapter、Margin、Vault/CTO 和报表，但必须按可运行的端到端用户流程逐步实现。尚未开发的能力保持关闭，也不为它预建通用实体。

## 当前可运行入口

- 进程入口：`trading-api = trading_control_plane.__main__:main`。
- HTTP 入口：健康检查/指标；内部会话；Perptape 机会；Proposal、Review、RiskDecision、TradingAuthorization、SHADOW/TESTNET Campaign；Binance 与 Hyperliquid Core 的只读、发送、取消、恢复和保护 API。
- Web/PWA 入口：机会、人工提案、审核、Campaign、仓位/保护、订单/成交、风险/目标、异常处理和 Binance 只读事实；Service Worker 只缓存带版本的静态壳，不缓存业务 API。
- 业务入口：HTTP API 与 Python 内部 API `TradingService` 共用同一事务、RBAC 和领域不变量。
- 计算入口：`evaluate_risk`、`select_target_position`、`compute_pnl`。
- 数据库：PostgreSQL；Alembic head 为 `20260718_0001`。
- Schema：22 张业务表，另有 Alembic 版本表。
- 发送边界：SHADOW 仍只记录合成事实；Binance 与 Hyperliquid 客户端分别只接受各自官方 TESTNET 主机。两个 TESTNET 发送开关默认关闭，LIVE 没有发送入口。
- Binance 边界：`BinanceReadOnlyClient` 只公开 GET 型 `read_snapshot`；`BinanceTestnetClient` 只实现 TESTNET 订单查询、创建、取消和原生 `STOP_MARKET closePosition` 保护。两者都没有保证金或资金划转方法。
- Hyperliquid 边界：`HyperliquidReadOnlyClient` 只使用 Core `POST /info`；`HyperliquidTestnetClient` 只构造 Core `POST /exchange` 的 IOC、`cancelByCloid` 和 trigger 保护动作，签名由部署时注入的官方兼容 signer 完成。客户端拒绝主网发送主机和非空 `dex`；HIP-3、默认滑点、市价替代价格、保证金与资金动作均不存在。
- 身份边界：正式环境预留托管 IdP/Passkey 会话边界；本地/测试可显式启用 Mock 登录与对象版本绑定的 Mock step-up，生产环境禁止 Mock。HUMAN 只能创建 MANUAL Proposal；SYSTEM Proposal 只能由 Perptape SERVICE principal 创建。
- Perptape 边界：只读调用现有 `GET /api/v1/breakouts`；HH/LL 映射 LONG/SHORT，源时间、就绪度、合同版本和深链随 Proposal 冻结，信号不直接形成订单。
- Telegram 边界：当前 `MockTelegramGateway` 不联网，覆盖提案、SHADOW 成交、保护、Unknown、对账异常和关闭通知；review code 不能替代批准所需的 step-up grant，通知不能直接执行订单动作。

## 当前数据真源

当前 Schema 只持久化需要跨重启保留的权威状态或外部事实：

- 内部用户、角色与账户/场所作用域；
- Proposal、Approval、RiskPolicy、RiskDecision、TradingAuthorization；
- Campaign 的当前目标、版本、原因、紧迫度和 PnL；
- RiskReservation、OrderIntent、CommandReceipt；
- VenueOrder、VenueFill、Position、ProtectionOrder、AccountEquity、FundingPayment；
- ReconciliationRun、SenderLease、CapabilityGate、AuditEvent。

可重新计算的风险步骤、目标候选、减仓计划、投影、绑定、证明哈希和证据包不单独持久化。

## 安全默认

- `LIVE_ORDER_SEND`、`CAPITAL_TRANSFER`、`AUTO_ADD` 在初始 Schema 中均为 `DISABLED`。
- RiskDecision 的数量、风险占用、新鲜度、仓位、权益和保护状态均由服务端读取 PostgreSQL；调用者不能提供这些事实。
- 风险决定后、创建 INITIAL/ADD OrderIntent 前会在同一风险容量锁内重新读取政策、授权、事实、活动 Campaign/Intent 和全局占用；变化后 fail closed。
- Campaign、Authorization、Position、Equity、Order、Fill 和 Funding 均保留 `SHADOW|TESTNET|LIVE` 环境边界；同账户同标的的不同环境事实不能互相覆盖或参与同一轮对账。
- Position、Protection、Equity 和 VenueOrder 区分场所 `observed_at` 与本地 `updated_at`，陈旧或未知事实阻断新增风险。
- 未知或陈旧事实、保护不足、未解决 Unknown、过期/越权授权和旧 fencing token 均阻断新增风险或发送。
- Binance TESTNET 的稳定客户端订单标识由 `OrderIntent` UUID 派生；每次发送先按该标识查询，确认不存在才创建。写请求结果不确定时进入 `UNKNOWN`，保持风险占用，恢复入口只查询、不盲重发。
- Hyperliquid TESTNET 以 `0x + OrderIntent UUID` 形成 128-bit cloid，同样先查后发；OrderIntent 保存从 Proposal 冻结或减仓动作显式提供的 `limit_price`。没有显式价格、价格/数量精度不合法、Core 域不匹配或 signer 缺失时在外部调用前拒绝。
- TESTNET 原生保护以当前非零仓位派生稳定标识，并使用 `STOP_MARKET + closePosition`；保护不足、拒绝或 Unknown 会被当前保护事实和 reconciliation 阻断。
- `ReconciliationRun.MATCH` 只能由全 execution scope 的一致事务计算产生；人工 `RESOLVED` 不等于 MATCH，也不能授权 sender 接管。
- Capability Gate 合法启用不会使数据库 readiness 失败，但 Gate 永远不能替代授权、最终风险检查、对账或 fencing。
- 幂等回执与业务写入处于同一 PostgreSQL 事务。
- 当前没有 Outbox/Inbox；等真实异步消费者或不可逆外部副作用出现时再按实际合同实现。

## 当前 M2 用户流程

Operator 可以从有效 TradingAuthorization 原子创建 Campaign、RiskReservation 和 INITIAL OrderIntent；获取单一 sender lease 后只记录合成 SHADOW Order，再显式录入合成成交、仓位、保护、权益和资金费事实。Campaign 页面可计算唯一目标、生成 reduce-only 意图、运行全 scope 对账、刷新 PnL 并在平仓、终态 EXIT 和计算所得 MATCH 同时满足后关闭 Campaign。

`UNKNOWN` 的 OrderIntent、VenueOrder、RiskReservation 和 Campaign 会保持风险占用；Web 不提供重发或释放按钮，异常页从权威当前状态派生阻断项。M2 自动化测试覆盖完整初仓到退出流程及 Unknown 拒绝路径；页面已经在宽屏和手机视口检查。所有事实均明确标记为 SHADOW 合成事实。

## 当前 M3 用户流程

内部 Operator 可在 `/venues/binance` 查看配置状态和当前已持久化的 Binance Instrument、仓位/保护、订单、成交、权益及资金费。只有只读开关、凭据和明确 `TESTNET|LIVE` 环境同时配置后，页面才提供同步动作。同步按场所外部 ID 去重，外部未绑定订单或非零仓位进入环境隔离的 scope reconciliation；非零仓位缺少保护时保存 `UNKNOWN` 并 fail closed。Hedge Mode 非零双向仓位不会被错误折叠为净仓，而是明确拒绝。

当前自动化使用官方端点形状的本地合同响应和一次性 PostgreSQL 验证签名、字段映射、重复同步、RBAC、环境隔离、对账与禁用路径。仓库未配置或使用任何真实 Binance 凭据，因此这不代表真实账户已经联通。

## 当前 M4 用户流程

在显式开启 `TRADING_BINANCE_TESTNET_ORDER_SEND_ENABLED` 且配置独立 TESTNET 凭据后，Operator 可对 `TESTNET:account:BINANCE` scope 获取 sender lease，从已审核、已授权的 TESTNET OrderIntent 执行 query-before-send。订单、部分成交、零成交取消、明确拒绝、Unknown、重启查询恢复、原生保护、退出、scope reconciliation 和 Campaign PnL 均落在现有核心实体中；没有增加业务表或通用 VenueAdapter 平台。

自动化使用官方请求形状、状态化本地 TESTNET 合同和一次性 PostgreSQL 跑通初仓部分成交、保护、补全成交、退出、资金费、对账、PnL 与关闭；同时验证旧 fencing token 在外部调用前拒绝、Unknown 不释放风险且重启不二次 POST、部分成交取消保留 OPEN 风险、明确零成交拒绝才释放风险。当前没有 Binance 测试账户或凭据，未发出真实测试网订单；这些结果属于合同级 TESTNET 环境验证，不能冒充交易所账户实证或实盘盈利。

## 当前 M5 用户流程

Hyperliquid 以独立窄适配器接入，不建立任意交易所平台。Core Info 读取 instrument、订单、成交、单向仓位、权益、资金费和 trigger 保护，按 `TESTNET|LIVE` 与 Binance 分域持久化；API 主机与事实环境不一致时拒绝。Core TESTNET 订单使用显式价格 IOC、稳定 cloid、query-before-send、`cancelByCloid`、Unknown 查询恢复和 reduce-only trigger 保护。Trading 仍是 Proposal、Campaign、Reservation、OrderIntent、目标、对账和 PnL 的唯一权威所有者，适配器不能自行生成机会或订单。

自动化使用官方请求/响应形状、注入式假 signer、状态化本地 Core 合同和一次性 PostgreSQL 跑通 Proposal→双人审核→RiskDecision→TradingAuthorization→RiskReservation→IOC→VenueFill/Position→保护→对账→退出→资金费/PnL；另验证 fencing 在网络前拒绝、Unknown 重启只按 cloid 查询且不二次发送、HIP-3/主网主机/隐含滑点均不可用。仓库没有真实 Hyperliquid 账户、API Wallet 或 signer 运行集成，未发出真实测试网订单；Core 合同测试不认证 HIP-3、isolated margin、实盘或盈利。
