## 问题与交付边界

WP-0006 的 `execution.fact.record.v1` 能根据 `ExecutionFact` 推进 `OrderIntentState` 和 Heat 桶，但它只保存
一个可由调用方填写的 `reconciliation_run_ref` 字符串。WP-0008、WP-0009 后，旧入口仍没有数据库外键或
服务校验把事实绑定到 ShadowDispatchClaim、当前 sender lease、ReconciliationRun 和具体输入水位，因此
理论上可以绕过新的 sender/reconciliation authority。

本包关闭该绕过路径。唯一新写入口改为 `execution.fact.record-reconciled.v2`，新事实必须沿以下不可替换链路
进入现有 OrderIntent/Heat 状态机：

```text
immutable ShadowDispatchClaim for this OrderIntent
  -> same exact scope + lease ID + fencing token
  -> latest RUNNING ReconciliationRun descended from claim-authorizing success
  -> phase COMPARING or ADJUSTING
  -> exact COMPLETE input for the required private fact source
  -> v2 ExecutionFact with all IDs and canonical hashes
  -> existing OrderIntentState + RiskExposureState transition
```

本包没有创建第二套订单状态机，也没有新增平行 VenueOrder/Fill 投影。它收紧现有事实入口，使后续真实
VenueOrder、Fill、Position、Protection 正规化工作只能通过同一权威链推进状态。

## 固定事实种类与来源矩阵

新合同固定五类事实：

- `WORKER_RECEIPT`；
- `VENUE_ORDER`；
- `VENUE_FILL`；
- `VENUE_POSITION`；
- `VENUE_PROTECTION`。

状态只接受下列 kind/source 组合：

| 目标状态 | fact kind | Reconciliation source |
| --- | --- | --- |
| `DISPATCHING` | `WORKER_RECEIPT` | `WORKER_LOCAL` |
| `VENUE_ACKNOWLEDGED`、`CANCEL_PENDING` | `VENUE_ORDER` | `VENUE_ORDERS` |
| `CANCELLED_ZERO_FILL`、`REJECTED_ZERO_FILL` | `VENUE_ORDER` | `VENUE_ORDERS` |
| `PARTIALLY_FILLED`、`FILLED`、`CANCELLED_PARTIAL` | `VENUE_FILL` | `VENUE_FILLS` |
| `RESULT_UNKNOWN` | `WORKER_RECEIPT` 或 `VENUE_ORDER` | 对应 `WORKER_LOCAL` 或 `VENUE_ORDERS` |
| `POSITION_RECONCILED` | `VENUE_POSITION` | `VENUE_POSITIONS` |
| `PROTECTION_CONFIRMED`、`COMPLETED` | `VENUE_PROTECTION` | `VENUE_PROTECTION` |
| `FAILED_SAFE` | worker/order/position/protection 的受限集合 | 与 kind 精确对应 |

`INTENT_CREATED` 不能由执行事实重新写入。成交数量、零成交证明、terminal、position/protection 等原有
语义检查继续生效；矩阵只收紧权威来源，不替代 WP-0006 的数量和 Heat 守恒规则。

## v2 不可变绑定

每条新 `ExecutionFact` 保存：

- `fact_contract_version=2` 和固定 `fact_kind`；
- `shadow_dispatch_claim_id` 与 `dispatch_claim_hash`；
- `reconciliation_run_id` 与 `reconciliation_run_hash`；
- `reconciliation_input_id`、`reconciliation_source_type` 与 `reconciliation_input_hash`；
- 原有 route、external fact identity、数量、状态证明、payload/evidence hash 和时间。

服务在插入前重新验证：

1. claim 属于同一个 OrderIntent 和 organization，保持 `SHADOW`、禁止 external send、live gate disabled；
2. run 与 claim 的 exact scope、lease ID、fencing token 完全一致，且严格在 claim 后启动；
3. run 是该 scope 最新 run，仍为 `RUNNING`，phase 只能是 `COMPARING` 或 `ADJUSTING`；
4. 递归 supersedes 链必须包含 claim 采用的成功 run，不能接入旁支或旧 lease 历史；
5. input 属于该 run，来源精确匹配、状态为 `COMPLETE`、source version 与 canonical hash 相等；
6. fact event time 必须落在 input 的观察水位区间、不得早于 claim，且 run 不能超过 deadline；
7. sender scope 当前仍由同一 lease/token 持有，且没有过期或被 fence；
8. OrderIntent route、fact kind、source 和 target status 全部兼容。

相同 external fact identity 的重新读取只有在上述 v2 绑定与 payload/evidence hash 完全相同时返回
`ALREADY_RECORDED`。不同 run/input/hash 或语义复用同一 external identity 会返回冲突，不能静默覆盖。

## 旧入口与兼容性

`execution.fact.record.v1` 不再是服务可接受命令。`RecordExecutionFactRequest` 采用 `extra=forbid`，旧
`reconciliation_run_ref` 不能进入 v2 payload。

迁移为已有 ExecutionFact 标记 `fact_contract_version=1`，保留其不可变历史，但所有新数据库 insert trigger
都要求 v2 完整绑定。也就是说：

- 历史 v1 行可以查询和审计；
- v1 服务命令稳定返回 `COMMAND_TYPE_MISMATCH`；
- 绕过服务直接插入 v1 行由 PostgreSQL trigger 拒绝；
- 历史 v1 行不能作为未来 claim、run 或新事实的授权依据。

## 数据库完整性

迁移 `20260718_0010` 为 `execution_facts` 增加版本、kind、三类外键和三类 canonical hash，建立
reconciliation binding 索引，并新增 insert guard。数据库独立复核：

- 所有新行必须为 v2；
- claim、run、input 外键存在；
- claim/order intent、organization、route 和 non-live 属性相等；
- run/claim lease、token、scope、hash、最新性、active phase 与递归 lineage 相等；
- input/run/source/status/version/hash/水位相等；
- current sender authority 未过期、未释放、未 fence；
- fact kind/source/status 符合固定矩阵。

原有 `execution_facts` immutable trigger、OrderIntent state guard、RiskExposure state guard、风险账本守恒和
deferred graph constraints 不变。因此绕过应用服务既不能插入弱事实，也不能单独更新状态投影。

## 命令、错误、监控与追踪

唯一 writer 仍是 `execution-reconciliation-service` 内部主体。命令沿用 durable receipt、immutable audit、
transactional outbox、idempotency、correlation 和 causation 合同。

新增稳定错误覆盖：claim 缺失/不匹配、run 缺失/不匹配/非 active/非最新、lineage 不匹配、input 缺失/
不匹配、事实超出 input 水位、source/status 不兼容和 sender lease 失效。旧 v1 使用固定 command mismatch，
不会回落到弱路径。

新增指标：

```text
trading_execution_fact_bindings_total{fact_kind,source_type,result}
```

原有 `trading_execution_fact_results_total{target_status,result}` 保留。标签均为固定枚举或受限结果，不引入
claim/run/input ID 等高基数字段。

追踪更新：`REQ-EXEC-006/008/009`、`REQ-DATA-003`、`REQ-OPS-002/004`，以及
`TEST-003/004/008/009/011/016`、`EVID-004/006/009/011`。

## 迁移与回滚

应用回滚应优先保留 0010 schema 和事实绑定。只有停止 v2 writer、确认没有 active run、导出所需审计事实、
确认降级后不会继续接受执行事实，并保持所有现实 capability gate 关闭后，才可执行：

```bash
TRADING_DATABASE_URL="$DATABASE_URL" uv run alembic downgrade 20260718_0009
```

降级会删除 v2 绑定列和数据库 insert guard，保留原有 ExecutionFact 基础列。由于这会移除防绕过约束，降级
环境必须停止执行事实 writer；它不是继续运行旧 v1 writer 的许可。重新升级不会补造 claim/run/input，也
不会把历史 v1 行提升为 v2。

## 明确未实现与现实边界

- 真实 VenueOrder、Fill、Position、Balance、Protection 正规化表和原始 payload 持久化；
- Binance、Hyperliquid Core/HIP-3 私有 REST/WebSocket collector、分页、限速与 eventual-consistency 处理；
- Freqtrade plugin/sidecar、受控 command outbox、真实发送瞬间 fencing 和 sender 进程编排；
- native protection、reduce-only、退出、保证金和资金操作的独立恢复链；
- production/test/research 账户和凭据的真实部署隔离；
- Web/PWA、Telegram、Margin Controller、Vault/CTO、Catalog、PnL、正式告警和演练。

测试中的 `COMPLETE` input、Binance route、account、worker、credential fingerprint、payload ref 和 hash 均为
虚构本地证据。本包不能证明任何交易所返回过订单或成交，不能打开 `LIVE_ORDER_SEND`，不能发送真实订单，
不能把任何认证单位标记为 real-money ready。
