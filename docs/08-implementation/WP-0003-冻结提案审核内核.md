# WP-0003：冻结提案审核内核

> 状态：Implemented
> 需求引用：`PRD-PROP-004`、`PRD-REVIEW-003..005`、`DEC-PROD-004/005/007`、`UAT-IAM-004..006/008/014`
> 上位合同：《领域模型与状态机》《身份权限与审批矩阵》《API 事件数据与审计契约》

## 交付合同

本包只审核数据库中已经存在的不可变 `FrozenProposalVersion`：

```text
FROZEN proposal version + exact risk_summary_hash
  -> current proposal state / expiry / system risk state
  -> current RBAC + ABAC + explicit deny + no-self-review
  -> bound Passkey/WebAuthn assurance for APPROVE
  -> immutable ReviewerVote
  -> one ApprovalDecision (1 / 1 / 2 quorum)
  -> audit + outbox in the same transaction
```

它不提供草稿、预检或冻结 API。当前测试由夹具插入合法冻结快照；后续 Proposal/Risk 工作包必须通过同一表合同产生它们，不能让客户端或 Telegram 自行写入。

## 冻结提案合同

`proposal_versions` 保存提案来源、版本、创建者/策略 owner、账户、场所、执行域、Instrument、板块、方向、价格、数量、失效价、交易假设、风险档位、Add 选择、策略/目录/执行版本，以及冻结风险摘要。

数据库直接约束：

- 初仓 `reduce_only=false`；减仓用途必须 `reduce_only=true` 且不得启用 Add；本审核内核只接受 `INITIAL_ENTRY`。
- 风险核准数量必须大于零且不超过用户请求数量。
- 低/中/高请求上限分别不超过 1R / 2R / 3R，Add 次数不超过 1 / 2 / 3。
- `1R_0 = Total Capital Snapshot_0 × 0.5%`。
- 低/中/高 `Frozen Trade Loss Cap = 1R_0 × 1 / 2 / 3`。
- 目标杠杆上限分别为 3x / 5x / 10x。
- Funding Envelope 不得为负或超过冻结总资本；它仍不是允许亏损。
- SYSTEM 提案必须绑定 `strategy_id + strategy_version + service_principal + human business owner`。
- 冻结快照和风险摘要分别保存 canonical hash；审核前服务端重新计算并比对。
- 冻结行由数据库触发器禁止 UPDATE / DELETE，生命周期状态单独保存并只允许从 `FROZEN` 单向进入终态。

## 审核与聚合政策

- 每个 ReviewerVote 精确绑定 `proposal_version_id`、风险摘要 hash、Reviewer、授权决定、MFA 引用、渠道、原因和时间。
- 同一 Reviewer 对同一版本最多一票；同选择重试返回已有事实，改变选择返回 `VOTE_CONFLICT`。
- 低/中风险一张合格赞成票形成 `APPROVED`；高风险第一票仍为 `PENDING`，第二名独立 Reviewer 才形成 `APPROVED`。
- 任意一名合格 Reviewer 的 `REJECT` 或 `RETURN` 立即形成保守终态；修改必须创建新提案版本。
- 两名 Reviewer 并发时锁定同一冻结版本和汇总决定，原子记录各自 vote，最多形成一个终态。
- 终态后的迟到动作只返回已有终态，不追加 vote、不改变 quorum，也不消耗另一份批准证据。
- `ReviewerVote` 由数据库禁止 UPDATE / DELETE；`ApprovalDecision` 只允许 `PENDING` 单向更新，终态不可修改或删除。

`APPROVED` 只表示人工审核事实。响应和事件显式写入 `trading_authorization_created=false`；数据库没有 `trading_authorizations` 表，本包不会签发初仓/Add 授权、预留 Heat 或创建 OrderIntent。

## 风险和渠道硬门

- 缺少 `system_risk_states` 行按 `UNKNOWN` 处理；只有当前 `NORMAL` 能批准初仓。
- `NO_NEW_POSITION`、`REDUCE_ONLY`、`KILL_SWITCH` 或 `UNKNOWN` 不能被 Reviewer 人数、管理员或渠道覆盖。
- MANUAL 创建者不能自审；SYSTEM 服务主体不具有人类 Reviewer 权限。
- Web/PWA 在线批准与 Telegram 批准都需要精确绑定对象版本的动作级认证。
- Telegram 未完成 `PASSKEY_WEBAUTHN + ACTION_STEP_UP` 时返回 `MFA_REQUIRED`，不能仅凭 chat identity 生成 vote。
- 拒绝和退回属于收紧动作，可按上位合同使用较轻认证，但仍需当前 Reviewer 标签、作用域和显式拒绝检查。
