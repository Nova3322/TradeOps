# 核心业务不变量

> 状态：BASELINE
> 日期：2026-07-18
> 原则：保留业务语义，尽量用核心对象字段、纯函数、事务和普通查询表达

| 能力 | 权威实现与状态 | 关键自动化验证 |
| --- | --- | --- |
| 基础运行 | `config`、`database`、`api`、`logging`、`metrics` | 配置拒绝非 PostgreSQL；健康检查；Schema revision 与默认门检查 |
| 内部身份与 RBAC | `User`、`RoleAssignment`、`TradingService.can_user` | 五角色、账户/场所作用域、默认拒绝 |
| Proposal | `Proposal` 当前状态、版本、冻结 payload | DRAFT 到审核终态；幂等创建不复制 Proposal |
| Approval | `Approval` + Proposal 状态 | 禁止自审；高风险需要两个不同 Reviewer |
| Risk Engine | `evaluate_risk` 纯函数；`RiskPolicy`、`RiskDecision` | 相同输入相同结果；允许、缩量、拒绝；拒绝原因稳定 |
| System Risk State | `RiskPolicy.system_state` | KILL_SWITCH、REDUCE_ONLY、NO_PYRAMID 阻断对应新增风险 |
| 原子风险预留 | `RiskReservation` | Reservation、OrderIntent、CommandReceipt 原子写入；Unknown 不释放 |
| TradingAuthorization | 有范围、数量/风险上限、有效期和 Add 次数的短期行 | 过期、越权、超量和关闭的 AUTO_ADD 均拒绝 |
| Campaign | 一笔经济交易的 Proposal/Authorization/Intent/Fill/Position/PnL 关联 | SHADOW 全流程测试贯穿并保存最终 PnL |
| TargetPositionArbiter | `select_target_position` 纯函数；Campaign 只保存当前目标 | 选择最小目标、最高紧迫度并合并原因 |
| OrderIntent | 一张表保存有限当前状态；场所事实分表 | 活动意图阻止重复减仓；部分/全部成交更新唯一当前状态 |
| 幂等命令 | `CommandReceipt` + PostgreSQL advisory transaction lock | 同 key 同语义返回原回执；不同语义明确冲突 |
| Instrument Catalog | `Instrument` | 场所/标的身份、tick/lot/min notional/multiplier/collateral/active/更新时间 |
| 场所事实 | VenueOrder/Fill、Position、Equity、Protection、Funding | 成交去重；订单/成交、仓位、保护差异可对账 |
| 保护状态 | `ProtectionOrder` 与当前 Position 关联 | 未知或覆盖不足被对账识别并禁止依赖其增险 |
| PnL 与成本 | `compute_pnl` + Campaign 汇总 | 成交、手续费、资金费、滑点、已实现/未实现/总 PnL |
| reconciliation | `ReconciliationRun.differences` | MATCH、DIFFERENCE、UNKNOWN、MANUAL_REQUIRED、RESOLVED |
| sender fencing | 每执行作用域一行 `SenderLease` | 新 owner 接管后 token 单调增加；旧 token、过期 lease 被拒绝 |
| Capability Gate | 三行简单开关 | 三个危险能力迁移后默认关闭；变更记录操作者、原因和时间 |
| 基本审计 | `AuditEvent` + 核心记录字段 | actor、时间、原因、correlation/idempotency、版本和关键状态变化落库 |

## 跨能力硬门

1. 信号和人工输入只能创建 Proposal，不能直接产生真实订单。
2. Proposal 创建者不能审核自己的 Proposal；高风险必须由两个不同 Reviewer 批准。
3. Risk Engine 是确定性纯计算；陈旧事实、未知仓位或未知保护一律不能新增风险。
4. Approval 只签发短期、有限范围的 TradingAuthorization，不产生永久交易权限。
5. Reservation、OrderIntent 和幂等回执必须在同一事务提交或回滚。
6. 订单结果 Unknown 时保留风险容量，不自动重发；只有确认零成交的取消/拒绝才释放全部预留。
7. 多个退出/减仓候选只计算一个最小目标仓位；Campaign 只保存当前目标，不保存可重建计划。
8. 一个 Campaign 存在活动 OrderIntent 时不得生成第二个减仓意图。
9. 场所真实订单、成交、仓位、保护、权益和资金费与内部预期分开保存，并由对账比较。
10. 恢复发送前必须先对账；每个 execution scope 只有一个有效 lease owner，旧 token 永远不能发送。
11. 未保护、保护不足或保护未知的真实仓位不得新增风险。
12. Capability Gate 不替代业务授权、风险判断、对账或 fencing；三个危险能力默认关闭。

## SHADOW 端到端验证

核心集成测试覆盖：

```text
Proposal
  → Approval
  → RiskDecision
  → TradingAuthorization
  → RiskReservation + OrderIntent
  → synthetic VenueOrder + VenueFill
  → Position + Protection + Equity + Funding
  → Reconciliation
  → Campaign PnL
```

该流程只写一次性 PostgreSQL 测试库和 SHADOW 事实，不连接真实交易所，也不发送真实订单。
