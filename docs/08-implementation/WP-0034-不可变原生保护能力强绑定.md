# WP-0034：不可变原生保护能力强绑定

> 后续状态：WP-0035 已将风险/意图命令升级为 v8，删除 caller `facts`，并由不可变完整
> [Risk Fact Set](WP-0035-不可变Risk-Fact-Set强绑定.md) 提供服务端九类 observation。本文件保留 WP-0034
> 的 v7 历史合同。

## 1. 交付目标与边界

WP-0033 后，`RiskPrecheckRequest.protection_available` 仍允许调用方用布尔值声称当前账户、worker 和标的具备
原生保护能力。WP-0034 删除这个字段，新增 SHADOW-only、不可变、版本化的原生保护能力记录，并在提案预检
和最终 ORDER_PRECHECK 的同一数据库事务内按 exact scope 独立解析。

本包只关闭“原生保护能力真源”边界，不声称完成：

- Binance、Hyperliquid 或其他场所的真实保护单发送与确认；
- 真实账户、凭证、worker、适配器或标的能力认证；
- 部分成交后的持续保护编排、保护替换、退出仲裁或恢复；
- production、small-live 或现实资金能力。

所有能力记录固定为 `environment=SHADOW`、`real_funds_eligible=false`。迁移不 seed 任何能力行，SHADOW
测试中的 `CERTIFIED` 只表示本地测试合同完整，不构成真实场所认证或实盘授权。

## 2. v7 命令合同

```text
risk.precheck.evaluate.v7      payload_schema_version=7
execution.intent.create.v7     payload_schema_version=7
```

v1 至 v6 命令返回 `COMMAND_TYPE_MISMATCH`，v7 携带非 7 schema 返回
`PAYLOAD_SCHEMA_VERSION_MISMATCH`。`RiskPrecheckRequest` 删除：

```text
protection_available
```

请求模型继续使用 `extra="forbid"`。风险请求携带旧布尔值返回 `RISK_INPUT_INVALID`；执行请求嵌套旧布尔值
返回 `EXECUTION_INPUT_INVALID`，不会静默忽略或回退为 caller-trusted 语义。

能力写入口独立使用：

```text
instrument_catalog.protection-capability.register.v1
payload_schema_version=1
service_principal=venue-capability-catalog-service
```

命令绑定 record UUID、organization scope、固定 object version，并通过 advisory transaction lock 阻止同一
exact capability version 的并发重复注册。幂等 receipt、audit event 和 outbox event 继续由统一命令执行器保证。

## 3. 不可变原生保护能力记录

迁移 `20260718_0029` 新增 `instrument_protection_capability_records`。每行以 composite foreign key 绑定
不可变 Instrument Catalog 记录，并保存：

- organization、venue、execution domain、canonical instrument、account；
- account abstraction、position mode、margin mode、collateral scope/pool；
- catalog/classification version、Catalog record ID/hash；
- position-management template、execution capability、adapter、worker/config 版本；
- credential fingerprint、account capability、credential permission profile；
- Freqtrade worker 与 venue client 版本；
- capability status、native protection、conditional order、reduce-only；
- partial-fill protection、protection replacement、确认窗口；
- trigger price types、protection order types、valid window；
- record/evidence hash 与 evidence/source 引用。

数据库和 Pydantic 双层约束保证：

- 只能写 SHADOW 且不能具备现实资金资格；
- 所有 hash 长度、有效期、确认窗口、数组类型和 canonical sorted unique 受约束；
- exact scope/version 唯一，record identity/version 可被决策外键引用；
- `UPDATE`/`DELETE` 由 trigger 拒绝，能力变化必须创建新版本；
- 表中已有事实时 downgrade 明确失败，避免历史证据被静默删除。

## 4. Exact capability 解析与失败关闭

解析器先要求 Instrument Catalog validation 有效，再按以下主键范围查询唯一能力记录：

```text
organization_id
venue
execution_domain
canonical_instrument_id
account_id
position_mode
margin_mode
collateral_pool_id
catalog_version
classification_version
position_management_template_version
```

找到记录后，服务端重建并校验 record/evidence hash、SHADOW 环境、有效期和完整能力；再与冻结 binding 比较
account abstraction、collateral scope、execution capability、adapter、worker/config、credential fingerprint、
account capability、credential permission profile、Freqtrade worker 和 venue client 版本。只有状态为
`CERTIFIED` 且下列五项都为 true 才通过：

```text
native_protection_supported
conditional_orders_supported
reduce_only_supported
partial_fill_protection_supported
protection_replacement_supported
```

记录缺失、过期、hash 失败、Catalog 绑定缺失/不匹配、作用域漂移、状态不可用或任一能力不支持，都会保留
详细 reason code，并由 Risk Engine 统一关闭新增风险：

```text
primary_reason_code = PROTECTION_UNAVAILABLE
final_quantity      = 0
valid_until         = decision_time
```

如果 Catalog 本身无效，`INSTRUMENT_UNCLASSIFIED` 仍保持更高优先级；保护 validator 同时记录
`PROTECTION_CATALOG_BINDING_UNAVAILABLE`，不会伪造独立能力事实。

## 5. 决策证据、有效期与迁移

`RiskEvaluationInput` 保存完整 `protection_capability` validation snapshot。`risk_decision_snapshots` 和
`execution_risk_decisions` 新增历史兼容列：

```text
protection_capability_record_id
protection_capability_version
protection_capability_record_hash
```

三列必须全空或完整，并以 composite foreign key 绑定不可变能力记录。旧历史行允许全空；v7 找到记录时写入
exact ID、position-management template version 和 hash。ALLOW 有效期继续取 Risk Policy、Capability
Certificate、Instrument Catalog、Protection Capability、事实与当前保护投影中最早截止点。

新增指标：

```text
trading_protection_capability_registrations_total{result}
trading_protection_capability_validations_total{result,primary_reason}
```

存在能力事实时，migration downgrade 拒绝。只有在一次性测试环境中明确清空事实后，才允许
`0029 -> 0028 -> 0029` 往返；生产回滚不得删除历史事实或重新启用 v6 caller boolean。

## 6. 需求追踪

| 权威要求 | 本包证据 |
| --- | --- |
| 初仓必须具备原生保护能力 | proposal 与 final precheck 都从 exact durable capability 独立验证 |
| 场所能力不得跨账户/凭证/worker 外推 | account、credential、worker、adapter 和版本全量比较 |
| 部分成交也必须可保护 | `partial_fill_protection_supported=true` 是放行必要条件 |
| 保护替换和 reduce-only 必须存在 | 两项能力缺失均详细失败关闭 |
| 能力变化不改写历史 | immutable row、exact version unique、decision composite FK |
| 能力到期不得被更长策略覆盖 | ALLOW `valid_until` 由 exact capability validity 收紧 |

## 7. 明确未完成范围

- 真实 Venue Capability 探测、认证证据采集和 lifecycle invalidation 未实现；
- 真实 native protection sender、部分成交保护编排、替换和确认窗口监控未实现；
- Catalog/Capability/Certificate 漂移后的主动失效传播与持续风险监控未实现；
- 事实 observation、ADD trend/equity 等剩余调用方输入仍需后续可信真源包；
- 正式 FX/USD、稳定币折扣/脱锚、真实 OMS/Freqtrade/VenueAdapter、Web/PWA、Telegram、Margin、
  Vault/CTO、PnL 与运维仍未完成；
- `LIVE_ORDER_SEND`、`CAPITAL_TRANSFER`、`AUTO_ADD` 继续为 `DISABLED`。

类型检查、数据库约束与测试。只有用户未来明确重新授权后，才会另行考虑 Codex Security。
