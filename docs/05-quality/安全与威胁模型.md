## 1. 目标与非目标

本文把既有安全原则转化为可验证的威胁、控制和上线门。核心目标是：即使单个界面、通知渠道、服务、凭据或操作者失效，也不能未经授权扩大仓位、风险或资金权限；系统必须能够停止增险、保持保护、减仓、退出、对账并留下完整证据。

本文不证明策略盈利，不替代交易所、智能合约或第三方组件的专项审计，也不假定任何交易所 API Key 天然具备应用层声称的细粒度权限。

## 2. 安全不变量

以下要求不允许被产品便利性、人工批准、辅助建议源或故障模式绕过：

1. **唯一日常订单出口**：所有正常交易订单必须沿 `Trading → Risk Engine → OMS → VenueAdapter → Freqtrade worker → 交易所` 发送。
2. **默认拒绝，显式拒绝优先**：标签权限并集仍必须与账户、场所、板块、档位、金额、动作、时间和渠道作用域取交集。
3. **风险只可自动收紧**：扩大最大亏损、档位、Add 次数、场所、有效期或资金权限必须形成新版本并重新批准。
4. **事实不确定时不增险**：仓位、订单、余额、保护、授权或审计状态为 Unknown 时禁止新增风险。
5. **交易权与资金权分离**：交易服务不能提款；CTO 不能交易；Vault owner / 主钱包私钥不能进入自动服务。
6. **保护、减仓和退出优先**：控制面或审核服务故障不得阻断已认证的保护、reduce-only 减仓和退出路径。
7. **幂等与单一发送者**：同一执行意图只可消费一次；结果未知时查询原意图，不盲目重试；同一账户同一时刻只有一个活动发送者。
8. **审计不可成为旁路**：所有允许、拒绝、修改、下单、资金和 break-glass 动作都必须关联身份、版本、原因和真实结果。
9. **活动仓位不得由 Vault 救援**：资金划转与交易授权是两个状态机，Vault 不向活动仓位追加资金。

## 3. 资产与保护等级

| 等级 | 资产 | 主要安全目标 |
| --- | --- | --- |
| A0 | 交易 API 凭据、CTO funding / 提款凭据、Vault owner / whitelist 钱包、break-glass 凭据、签名密钥 | 不泄漏、不可混权、可立即撤销、使用可归责 |
| A1 | Proposal、Approval、Authorization、风险政策、OMS 意图、仓位与资金账本、审计链 | 完整性、顺序性、不可重放、可恢复 |
| A2 | 用户身份、标签、作用域、MFA、会话、Telegram 绑定、PWA 设备 | 防冒用、防越权、可撤权、最小披露 |
| A3 | 行情、Market Catalog、预言机、交易规则、策略与成本版本 | 来源可证、时效可判定、污染时 fail closed |
| A4 | 绩效、告警、运行日志、支持与事故记录 | 准确、可关联、按政策保留和脱敏 |

资金与仓位损失、未授权增险、审计链断裂、长期资金控制权泄漏均按最高等级影响处理。

## 4. 信任边界与数据流

```text
用户 / 审核者
  ├─ Web / PWA ─┐
  └─ Telegram ──┴→ 身份与策略执行点 → Trading API
                                         ├→ Risk Engine
Perptape / 行情 / 规则 ─→ 数据入口 ──────┤
                                         ├→ OMS → VenueAdapter → Freqtrade → 交易所
                                         ├→ Margin Controller → 交易所保证金动作
                                         ├→ CTO → 交易所 / 链 / Vault
                                         └→ 事件账本 / 审计 / 可观测性
```

边界要求：

- 公网入口、控制面、风险决策、订单执行、资金执行和审计存储属于不同信任域。
- Binance、Hyperliquid Core、每个 HIP-3 DEX、cross / isolated 账户和研究 / 模拟 / 生产环境分别隔离凭据、幂等空间和故障域。
- FreqUI、Freqtrade REST、内置 Telegram、数据库管理工具和运维入口不得成为第二条生产交易链。
- 第三方返回的成功只代表请求结果；真实仓位、挂单、成交和余额以场所私有事实为准。

## 5. 威胁场景与强制控制

| ID | 威胁 | 主要后果 | 强制控制 | 失败状态 |
| --- | --- | --- | --- | --- |
| THR-001 | Web、Telegram、FreqUI 或脚本绕过 Trading 下单 | 未授权增险 | 网络隔离、凭据隔离、唯一入口、交易所账户独占、旁路探测 | KILL_SWITCH，撤销增险订单并对账 |
| THR-002 | 重放批准按钮、API 请求或旧订单意图 | 重复开仓 / Add | 提案哈希、一次性 nonce、幂等键、到期、原子消费、真实成交核验 | 冻结对象，进入 Unknown Heat |
| THR-003 | 标签叠加、自审或作用域错误 | 越权批准 | 默认拒绝、拒绝优先、版本化策略、职责分离、step-up MFA | 拒绝动作并产生安全告警 |
| THR-004 | Telegram 账号被接管或 Bot webhook 被伪造 | 冒名审核 / 紧急动作 | 账号绑定、私聊限制、回调签名、一次性动作、短有效期、MFA、绑定恢复流程 | 撤销会话与绑定，暂停新增风险 |
| THR-005 | PWA 离线缓存、旧 service worker 或设备丢失 | 使用旧状态批准 | 离线只读、服务端最终校验、敏感数据不持久缓存、设备撤权、版本强制失效 | 禁止批准和恢复动作 |
| THR-006 | 交易或资金密钥泄漏 | 盗单 / 盗资 | 最小权限、环境隔离、独立账户、Secrets/KMS、硬件或多签托管、受限签名器、轮换、地址白名单、异常行为监控 | 撤销密钥、冻结账户、事故响应 |
| THR-007 | 内部人员滥用 break-glass | 绕过审批 | 专用凭据、只保护 / 减仓 / 退出、限时授权、双人启用、完整录像或审计、恢复另行双人批准 | 使用即冻结，完成对账和复盘后恢复 |
| THR-008 | Risk Engine、账本或审计结果被篡改 | 风险绕过 / 无法归责 | 版本签名、追加写、独立审计副本、前后值、correlation ID、完整性校验 | 禁止增险 |
| THR-009 | 私有流陈旧、乱序或伪成功 | 重复订单 / 错误风险 | 多源时间戳、序列校验、快照修复、Unknown Heat、查询而非重试 | 受影响范围冻结或全局停止增险 |
| THR-010 | 双 worker、脑裂或恢复重放 | 双倍仓位 | fencing token、租约、账户独占、恢复只对账、旧意图不可重放 | KILL_SWITCH |
| THR-011 | Vault / CTO 金额双计、地址或链被替换 | 虚增资本 / 错误转账 | 源端预留、唯一 transfer ID、冻结地址资产网络、两端确认、交易权资金权分离 | 停止划转并归零未知贡献 |
| THR-012 | 日志泄漏私钥、token、订单或个人数据 | 凭据与隐私泄漏 | 结构化脱敏、禁止 secret 入日志、访问控制、保留和删除政策 | 撤销凭据并启动安全事故 |
| THR-013 | 依赖、镜像或更新被污染 | 执行语义被替换 | 锁定版本、来源校验、制品签名、SBOM、漏洞扫描、重放与灰度 | 认证失效并回滚 |
| THR-014 | 流量洪泛、告警轰炸或资源耗尽 | 安全链路不可用 | 限流、优先队列、资源隔离、告警去重；保护与退出高于展示和提案 | 停止新增风险，保持退出链 |

## 6. 身份、MFA 与会话

`DEC-SEC-001` 已确认托管身份源与 Passkey/WebAuthn 主认证；高风险动作使用短时 step-up。具体供应商和部署事实不改变以下合同。

- 用户可拥有多个标签，但每个动作必须重新计算 `标签允许并集 ∩ ABAC 作用域 - 显式拒绝`。
- `SYSTEM_ADMIN` 不自动继承提案、审核、风险、交易或资金权限。
- 提案者自审、风险放宽、资金划转、权限变更和 break-glass 使用均是独立策略，不因一个人拥有多个标签而自动通过。
- 高风险批准、恢复 KILL_SWITCH、标签 / 作用域变更、资金动作和设备恢复要求 step-up MFA；确切范围由 `DEC-SEC-001` 与 `DEC-SEC-003` 冻结。
- 会话必须支持绝对到期、空闲到期、风险事件强制撤销、标签变化立即重算和单设备撤权。
- 用户离职、设备丢失、MFA 丢失和身份提供方故障必须有恢复流程；恢复不能顺带恢复旧批准、旧授权或旧 Telegram 绑定。

## 7. Telegram 安全合同

Telegram 绑定与恢复方式由 `DEC-SEC-004` 冻结。无论采用何种实现，都必须满足：

- 只允许与已验证系统身份绑定的私聊主体操作；群组消息不能批准交易。
- 按钮绑定唯一 proposal / operation ID、冻结版本哈希、用户、作用域、动作、有效期和 nonce。
- Telegram 不能创建完整人工提案、提高风险、恢复开仓、增加 Add 或直接调用 Freqtrade。
- 重复、延迟、转发、截图或跨账号使用按钮均不得生效。
- 高风险动作回到 Web / PWA 执行强 MFA；Telegram 只显示最小必要交易信息。
- Bot token / webhook secret 泄漏不应等于获得交易权限；泄漏时可独立撤销 Bot 而不影响保护和退出。
- 仅 UI、Telegram 或辅助通知源失效，且 Trading、授权、Risk、账户事实和保护全部健康时，既有 Add 才可能按 `DEC-OPS-004` 继续；任一核心事实不可验证即停止，客户端不得自行推断。

## 8. PWA 与设备安全合同

`DEC-SEC-005` 已确认注册设备、加密短缓存和远程撤销；敏感动作仍由服务器 step-up。

- PWA 离线时只能显示明确标注时间的只读快照，不得离线批准、解除风险状态或确认紧急动作成功。
- 浏览器存储不保存交易、资金、Vault 或长期身份私钥；敏感 token 使用受保护的短生命周期会话。
- Service worker 缓存不得覆盖服务端授权、风险、仓位和订单事实；关键版本失效时必须强制刷新或拒绝操作。
- 防护范围至少包括 CSRF、XSS、点击劫持、开放重定向、会话固定、供应链脚本和敏感信息缓存。
- 新设备、设备恢复、异常地理位置或高风险动作触发 step-up MFA 和安全通知。

## 9. 凭据、签名与秘密治理

`DEC-SEC-002` 已确认按密钥类别组合托管：生产交易 API 密钥进入 Secrets/KMS，资金 owner 使用多签或硬件托管，自动资金签名器权限最小化。具体供应商由部署研究决定，不改变下列边界。

- 每个环境、交易所、账户、worker 和资金执行域使用独立凭据。
- 交易凭据禁止提款；CTO 凭据不能交易；Vault owner / 主钱包私钥保持离线或人工托管。
- 自动资金路径使用预批准的低额度专用 funding wallet；软件限制与场所 / 合约硬限制必须分别标注。
- secret 不进入 Git、镜像、可提交配置样例、前端、日志、告警、错误追踪或测试快照。本地开发秘密只允许按 [运行手册](../06-operations/SLO可观测性故障恢复与Runbook.md#54-本地开发凭据与轮换) 存入被 Git 忽略的 `.env.local`。
- 建立凭据清单，记录所有者、用途、作用域、创建、轮换、撤销、最后使用和依赖服务。
- 密钥轮换必须支持双版本短暂过渡、旧密钥确认失效和无持仓 / 只减仓窗口；不能在结果未知时同时启用两个活动订单发送者。
- 生产、测试、研究账户和资金完全隔离；生产数据进入非生产环境前必须脱敏。

## 10. Break-glass 与人工接管

`DEC-SEC-003` 已确认双人启用、短时专用凭据、仅减险动作以及恢复另行双人批准。

Break-glass 不是第二套日常控制面，只能在 Trading 整体不可用且真实风险需要处置时使用：

1. 宣布事故并把受影响账户置为 KILL_SWITCH。
2. 取得限时、专用凭据；只允许确认保护、撤销增险、reduce-only 减仓或退出。
3. 禁止开仓、加仓、换所补救、提高杠杆、放宽止损、CTO / Vault 划转或提款。
4. 每个动作记录操作者、理由、时间、场所回执和仓位结果。
5. 使用后立即撤销凭据；系统恢复时先冻结、重建事实并对账。
6. 完成事故复盘和明确恢复批准前不得重新开放增险。

若交易所无法在凭据层硬性限制 reduce-only，必须用独立账户、限额、审批和监控补强，并把剩余风险写入上线例外，不能声称已获得硬隔离。

## 11. 审计、隐私与取证

- 审计事件至少包含：事件 ID、correlation ID、发生与接收时间、身份 / 服务主体、标签与作用域、渠道、源 IP / 设备、对象和版本、前后值、政策结果、允许 / 拒绝原因、MFA / 复核、执行意图、场所回执和真实终态。
- 审批、风险预留、订单、保护、资金、权限、配置、告警、事故和 break-glass 事件必须能够串成单一时间线。
- 审计采用追加写和独立故障域备份；保留期、脱敏、导出、legal hold 与删除冲突由 `DEC-GOV-002` 决定。
- `DEC-OPS-007` 已确认：审计或主业务持久存储不可写、不可验证完整性时，必须停止初仓和 Add。第二耐久副本只用于证据保全与恢复，不构成继续增险的例外；已有保护、预认证 `reduce-only` 减仓、退出和对账走故障路径。
- secret、完整 token、私钥、助记词和不必要个人数据永不写入审计正文。
- 时间同步异常使受影响执行域停止增险；恢复后必须验证事件顺序和签名时间。

## 12. 安全验证与上线硬门

真实资金前至少需要以下证据：

- 权限矩阵、显式拒绝、自审限制、MFA、会话撤权和 Telegram / PWA 绑定测试通过。
- 所有正常与诊断入口均无法绕过 Trading 形成增险订单。
- 幂等、重放、部分成交、结果未知、双 worker 和重启恢复测试通过。
- 凭据扫描无生产 secret；密钥轮换、撤销、泄漏和 break-glass 演练通过。
- 原生保护、reduce-only、退出和人工接管在 Binance 与 Hyperliquid 各自认证。
- 审计链完整性、异地恢复、时间同步异常和取证导出通过。
- 第三方依赖清单、版本锁定、漏洞处置和制品完整性流程通过。
- `INC-P0` 安全缺陷为零；未修复剩余风险必须有所有者、期限、补偿控制和书面接受，且不得违反安全不变量。

安全测试细节以 `docs/05-quality/测试验证与发布计划.md` 为准。
